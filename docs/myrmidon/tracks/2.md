**Функции:** P3 (вместе с вендорскими коммитами #13891 и #13793), P1, P2, P11, X2.

Перед началом прочитай [README](../README.md), [ROADMAP](../ROADMAP.md),
[CONVENTIONS](../CONVENTIONS.md). Этот файл самодостаточен для работы трека.

## Цель

Перенести в исходники с тестами наши правки ядра, которые сейчас живут заплатками поверх
собранного JS:

- прогон стартует при длинной истории задачи;
- аренды окружения освобождаются;
- побудка адресата карточки не гаснет;
- пропущенный дамп БД догоняется.

Проверить, что вендорский режим плана работает с `hermes_local`.

### Шаг 2. P3 — предел истории продолжения

Проблема: сборщик продолжения прогона (`server/src/services/execution-continuation.ts`) кладёт
в промпт всю историю задачи. На длинных задачах промпт переходит системный предел длины
аргумента, и процесс агента не стартует (`spawn E2BIG`).

Что сделать:

1. Сверь, что из заплатки уже закрыли вендорские коммиты шага 1. Переписывай только
   недостающее.
2. Предел истории продолжения — настройка `MYRMIDON_CONTINUATION_HISTORY_LIMIT`, по умолчанию
   30 записей, `0` — без предела.
3. При обрезке сохраняются исходный запрос задачи и последний запрос. В контексте есть явная
   пометка, сколько записей пропущено.
4. Передача промпта Hermes через stdin и проверка размера конверта — не здесь: это P4, трек 3.

**Готово, когда:**

- тест: 500 комментариев → в продолжении не больше предела, исходный и последний запросы на
  месте, есть пометка о пропуске; на коде вендора тест красный;
- тест: `0` отключает предел;
- строка в SETTINGS.md.

### Шаг 3. P1 — аренды окружения при отмене и паузе

Проблема: ни отмена прогона (`cancelRunInternal`), ни пауза агента
(`cancelActiveForAgentInternal`) не освобождают аренду окружения. Задача навсегда остаётся
«занятой» (`execution_owner_active`), побудки откладываются, комментарий владельца её не
разблокирует.

Что сделать, в `server/src/services/heartbeat.ts`:

1. В обоих путях отмены вызвать освобождение аренд прогона
   (`releaseEnvironmentLeasesForRun`) **до** освобождения исполнения задачи — так же, как это
   делает путь финализации.
2. Подметание зависших аренд:
   - активная аренда на завершённом прогоне, у которого процесс и группа процессов мертвы, а
     с завершения прошло больше запаса, освобождается как `expired` с причиной
     `stale_active_lease_sweep`;
   - сначала выполняется очистка окружения по записанным данным;
   - вызывается из обхода осиротевших прогонов на каждом тике планировщика;
   - за тик обрабатывается не больше 50 аренд.
   
   Живой процесс или прогон в процессе сервера — пропуск. Ошибка очистки — аренда остаётся
   активной до следующего тика, в журнал пишется только вид ошибки.
3. Запас — настройка `MYRMIDON_STALE_LEASE_GRACE_MS`, по умолчанию 10 минут.
4. Новую функцию подметания вынеси в отдельный файл (`server/src/myrmidon/…`), если это
   позволяет устройство сервиса. В `heartbeat.ts` остаются только вызовы.

**Готово, когда:** тесты (ориентир — 12 проверок из `tests/` каталога P1) зелёные, на коде
вендора красные:

- отмена освобождает аренду;
- пауза освобождает аренду;
- зависшая аренда подметается;
- живая аренда не трогается;
- ошибка очистки откладывает освобождение.

### Шаг 4. P2 — побудка адресата карточки

Проблема: побудка агента-адресата карточки подтверждения (`wakeReason: interaction_pending`)
гасится проверкой владения задачей, если адресат — не исполнитель. Прогон отменяется с
`issue_assignee_changed`, карточка остаётся без ответа. Существующий обход для побудок из
комментариев этот случай не покрывает.

Что сделать: в `server/src/modules/run-dispatch/domain/policy.ts` и
`server/src/modules/run-dispatch/adapters/postgres.ts` — признак «побудка адресата ожидающей
карточки», который обходит проверку смены исполнителя. Логику и имена возьми из диффа P2.
Остальные случаи смены исполнителя работают как у вендора.

**Готово, когда:**

- тест: побудка адресата-неисполнителя по ожидающей карточке доходит до прогона;
- тест: обычная побудка после смены исполнителя по-прежнему отменяется;
- на коде вендора первый тест красный.

### Шаг 5. P11 — догон пропущенного дампа БД

Что даёт:

- если сервер был выключен во время слота резервной копии, при старте он догоняет пропущенный
  дамп;
- пропуск слота виден в `/api/health`;
- первый тик планировщика считается от времени последнего дампа.

Что сделать:

1. Перенеси исходник из `*-src.patch` каталога P11: новый модуль догона, правки
   `server/src/index.ts`, `server/src/routes/health.ts`,
   `server/src/services/database-backup-health.ts`, `server/src/routes/openapi.ts` (схема ответа
   health: `gapThresholdHours`, `database_backup_slot_missed`).
2. Окно догона — настройка `MYRMIDON_DB_BACKUP_CATCHUP_WINDOW` (формат выбери сам, например
   `UTC 01:00-01:15`). **По умолчанию выключено.**
3. Убери из кода и логов всё, что привязано к нашему развёртыванию: часовой пояс по
   умолчанию, тексты про наш хост.

**Готово, когда:**

- тесты из каталога P11, переписанные на нейтральные данные, зелёные;
- тест: без настройки догон не выполняется;
- тест: пропуск слота виден в ответе health;
- строка в SETTINGS.md.

### Шаг 6. X2 — режим плана

У вендора есть режим работы задачи `planning`: константа `ISSUE_WORK_MODES`, указания плана в
промпте побудки из `packages/adapter-utils/src/server-utils.ts`. Есть и экспериментальные
настройки `enableIssuePlanDecompositions`, `enableFirstTaskPlanProposal`.

1. Проверь тестом, что для `hermes_local` у задачи в режиме `planning` указания плана попадают
   в промпт прогона.
2. Если не попадают, нужна правка в `packages/adapters/hermes/src/server/execute.ts` — это файл
   трека 3. Сделай её только после слияния P4, одной точкой вызова, отдельным маленьким PR.
3. В SETTINGS.md, раздел «Настройки вендора», запиши, как включить режим плана и связанные
   экспериментальные настройки.

**Готово, когда:** есть тест «задача в режиме плана → в промпте `hermes_local` есть указания
плана» и заполнена строка в SETTINGS.md.
