# Трек 4 — чаты и навыки

**Функции:** P7b (вендорский #13654), P7, P8, H4, H1.

Перед началом прочитай [README](../README.md), [ROADMAP](../ROADMAP.md),
[CONVENTIONS](../CONVENTIONS.md). Этот файл самодостаточен для работы трека.

## Цель

- Telegram не теряет вложения молча и принимает большие файлы через свой Bot API.
- Чат агента открывается без ошибки.
- Промпт у всех локальных адаптеров идёт через stdin.
- Навыки Hermes ставятся в профиль своего агента, и агенты не стирают навыки друг друга.

## Шаги

### Шаг 1. P7b — открытие чата агента без 500

У вендора исправлено коммитом `6d0342868` (#13654, «Skip task-only connector reads for agent
chat views»). В нашей базе 916.1 его нет.

1. Перенеси коммит: `git cherry-pick -x 6d0342868` после `git fetch` из репозитория вендора
   или `git am -3` файла из каталога P7b. Затрагивает `server/src/routes/chat-channels.ts`,
   `server/src/routes/email.ts`, `server/src/routes/openapi.ts`, два компонента `ui/`, тесты.
2. Нашу прежнюю заплатку не переносить, если вендорский коммит лёг.

**Готово, когда:** коммит в `main`, его тесты (`task-connector-read-routes.test.ts` и тест
`ui/`) зелёные. В DIVERGENCE.md строка `vendor:6d0342868`.

### Шаг 2. P7 — отправитель видит, что вложение не импортировано

Проблема: текст сообщения из Telegram доходит, а вложение отброшено (велико, не скачалось,
неподдерживаемый тип). Отправитель получает обычное «принято» и о потере файла не узнаёт.

Что сделать: перенести `ope2580-src.patch` в `server/src/services/chat-channels.ts`.

- Закрытый список причин, которые можно показать отправителю: `attachment_limit`,
  `storage_unavailable`, `declared_too_large`, `download_unavailable`, `unsupported_type`,
  `empty_download`, `downloaded_too_large`, `processing_failed`. Прочие коды наружу не выходят.
- Уведомление — отдельное действие провайдера (`thread_message`) в тот же тред. Тело
  принятого комментария не меняется.
- До 3 файлов по имени и причине, остальные — «and N more». Хранится не больше 50 записей.
- Ключ идемпотентности `provider_effect:attachment-omission-notice:<deliveryId>`: повтор
  доставки не печатает уведомление дважды.
- Встроено в обе ветки приёма: свежий приём и повтор по уже связанному сообщению.
- Только для `provider === "telegram"`.

Перед переносом проверь, не появилось ли у вендора своего такого уведомления.
Интеграционный тест из патча — в отдельный файл `*.myrmidon.test.ts`, если это не ломает его
фикстуры; иначе — минимальное дополнение вендорского файла.

**Готово, когда:** интеграционный тест зелёный, на коде вендора красный. Тексты на английском,
без наших имён файлов и ботов.

### Шаг 3. P8 — файлы Telegram до 2 ГБ через свой Bot API

Вендор уже патчит `@chat-adapter/telegram@4.39.0` через `pnpm.patchedDependencies`. Его патч
зажимает размер скачивания 25 МБ. Облачный Bot API и так не отдаёт файлы больше 20 МБ, а свой
Bot API (адрес — вендорская переменная `TELEGRAM_API_BASE_URL`) отдаёт до 2 ГБ.

Что сделать:

1. Замени `patches/@chat-adapter__telegram@4.39.0.patch` версией из каталога P8: вендорский
   патч плюс две строки — предел берётся из переменной окружения.
2. Имя переменной — по правилам проекта: `MYRMIDON_TELEGRAM_FILE_LIMIT_BYTES`. В каталоге P8 она
   называется `TELEGRAM_FILE_LIMIT_OVERRIDE_BYTES`. Поправь патч и укажи смену имени в PR,
   раздел «Риски»: эксплуатации нужно переименовать переменную при выкате.
3. Без переменной — поведение вендора (25 МБ).
4. `pnpm install` пересчитает хэш патча в `pnpm-lock.yaml`. Закоммить lock-файл. Подмена
   файлов в `node_modules` недопустима.
5. Проверь, что текст уведомления P7 указывает действующий предел.

**Готово, когда:**

- тест: с переменной = 2 ГБ адаптер принимает `maxDownloadBytes` до 2 ГБ;
- тест: без переменной — зажим 25 МБ;
- `pnpm install --frozen-lockfile` на чистом клоне проходит;
- строка в SETTINGS.md.

### Шаг 4. H4 — промпт через stdin у всех локальных адаптеров

Проблема: адаптер, который передаёт промпт аргументом командной строки, на длинном промпте
упирается в системный предел длины аргумента (`E2BIG`). Промпт в аргументах к тому же виден
другим процессам в списке процессов. Для Hermes это решает P4 (трек 3). Здесь — остальные
локальные адаптеры: `claude-local`, `codex-local`, `cursor-local`, `gemini-local`,
`grok-local`, `kimi-local`, `opencode-local`, `pi-local`.

1. Сначала опись: как каждый адаптер сейчас передаёт промпт и что умеет его CLI (stdin, файл,
   аргумент). Опись — в описании первого PR шага.
2. Где CLI читает stdin — перевести на stdin.
3. Где не читает — временный файл с правами 0600, удалить после выхода. Если и это невозможно —
   проверка размера до запуска с понятной ошибкой.
4. Общий код — в новом файле `packages/adapter-utils/src/myrmidon-prompt-transport.ts`. В
   `execute.ts` адаптеров — только вызовы с меткой `myrmidon(H4)`.

**Готово, когда:**

- тест для каждого адаптера: промпт на 300 КБ не попадает в аргументы процесса, процесс
  получает его целиком;
- на коде вендора красный хотя бы один тест для каждого адаптера, где передача через аргумент
  была;
- для адаптеров, где изменения не нужны, это видно из описи.

### Шаг 5. H1 — навыки в профиль своего агента

Факты, проверенные по коду 916.1 и документации Hermes:

- Адаптер `hermes_local` (`packages/adapters/hermes/src/server/skills.ts`) ставит ссылки на
  навыки в `<HOME>/.hermes/skills`: берёт только `env.HOME`, иначе домашний каталог процесса.
  `HERMES_HOME` он не читает.
- Hermes с профилями читает навыки из `<HERMES_HOME>/skills`. По документации Hermes, профиль
  изолируется `HERMES_HOME`, а `HOME` намеренно остаётся общим.
- Итог при общем `HOME` у многих агентов:
  - навыки пишутся в общий каталог, который Hermes этих агентов не читает;
  - каждый прогон удаляет из общего каталога чужие ссылки: адаптер удаляет управляемые ссылки,
    которых нет в наборе текущего агента.
- У вендора не исправлено даже в `master` на 27.09. Родственный открытый PR — #6230 (свой
  `HERMES_HOME` на агента).
- Если в профиле на месте управляемого навыка лежит **настоящий каталог** (например,
  `skills/paperclip`), создание ссылки даёт `skipped`, затем reconcile падает с
  «occupied by another installation», и прогон не стартует («Cannot start without the
  required Paperclip-managed skills»).
- P4 (трек 3) создаёт для прогона временный `HERMES_HOME`, где `skills` — ссылка на каталог
  профиля. Значит, навыки надо ставить в **постоянный** профиль агента (`HERMES_HOME` из
  `adapterConfig.env`), а не во временный каталог прогона.

Что сделать:

1. В `skills.ts`: каталог навыков — `<HERMES_HOME>/skills`, если у агента задан `HERMES_HOME`,
   иначе поведение вендора `<HOME>/.hermes/skills`. То же для перечисления навыков (`listSkills`).
2. Конфликт с настоящим каталогом в профиле: если на месте управляемого навыка лежит
   настоящий каталог, переименовать его в `<имя>.pre-myrmidon-<дата>` и поставить управляемую
   ссылку. В журнал прогона — одна строка без путей пользователя. Чужое содержимое не удалять
   никогда.
3. Удаляются только управляемые ссылки в каталоге **этого** агента.
4. Документ `docs/myrmidon/migrations/h1-hermes-skills.md`:
   - что произойдёт при первом прогоне после обновления;
   - что делать со старыми ссылками в общем `<HOME>/.hermes/skills` — безвредны; при желании
     скрипт очистки с `--dry-run`, если сделаешь его;
   - как локальные копии навыков в профиле затеняют управляемые: правило «Local precedence» у
     Hermes;
   - как откатить.
   
   Без путей наших серверов.

**Готово, когда:** тесты зелёные, на коде вендора красные (кроме случая без `HERMES_HOME`):

- два агента с общим `HOME` и разными `HERMES_HOME`: у каждого в `<HERMES_HOME>/skills` только
  его навыки;
- прогон одного не удаляет ссылки другого;
- настоящий каталог на месте управляемого навыка: бэкап, ссылка, прогон стартует;
- без `HERMES_HOME` — поведение вендора.

Документ миграции есть.
