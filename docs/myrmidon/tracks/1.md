# Трек 1 — платформа

**Функции:** R1 (CI, образ, проверки), TEL (телеметрия выключена), BR (минимальный
ребрендинг), R4 (выкат по отпечатку образа и откат).

Перед началом прочитай [README](../README.md), [ROADMAP](../ROADMAP.md),
[CONVENTIONS](../CONVENTIONS.md). Этот файл самодостаточен для работы трека.

## Цель

Репозиторий становится продуктом:

- каждый PR проверяется CI;
- образ собирается в GitHub Actions и публикуется в `ghcr.io/itkadr-git/myrmidon`;
- лицензии зависимостей и утечки секретов проверяются автоматически;
- совместимость плагинов проверяется при каждом изменении;
- телеметрия вендору выключена;
- выкат и откат описаны и оформлены скриптами без наших адресов.

Пока CI нет, остальные треки прикладывают вывод тестов к PR вручную. Поэтому базовый CI —
**первым делом**.

## Входы

- Код вендора в `main`: `.github/workflows/*`, `Dockerfile`, `packages/shared/src/telemetry/`,
  `cli/src/telemetry.ts`, `server/src/services/feedback-share-client.ts`,
  `server/src/config.ts`.
- `AGENTS.md` вендора, раздел 5.7 «три пути данных»: телеметрия, трассировка и журнал прогона —
  разные вещи. Трогаем только телеметрию.
- `myrmidon-deploy/patches/T1-telemetry-off/` — вендорские оригиналы файлов телеметрии (если
  появится README — это источник правды).
- Плагины, которые у нас стоят (публичные пакеты npm; версии — те, что работают сейчас):
  `@vectorize-io/hindsight-paperclip@0.3.0`, `@pingstray/paperclip-lang-ru@1.0.23`,
  `paperclip-claude-auth@1.1.1`, `paperclip-plugin-telegram@0.8.1`.
- Требования вендора к сборке: Node ≥ 24.11, pnpm 9.15.4 (через corepack), Rust для
  `paperclip-runner`, `NODE_OPTIONS=--max-old-space-size=4096` для сборки сервера.

**Что делает сопровождающий проекта до начала или в начале трека** — от сессии не зависит, но
проверь и отметь в отчёте, если не сделано:

- выключены workflow вендора, которые у нас запускаются сами и требуют секретов вендора:
  - по расписанию: `release.yml`, `runner-chaos-evals.yml`, `runner-full-stack-e2e.yml`,
    `runner-live-evals.yml`, `runner-protocol-live-evals.yml`;
  - на PR: `commitperclip-review.yml` (`pull_request_target`);
- включён ruleset `main-protection`;
- по желанию: секрет репозитория со списком запрещённых шаблонов (шаг 2).

## Шаги

Каждый шаг — отдельный PR. Порядок важен только для шага 1.

### Шаг 1. Базовый CI (первым, как можно раньше)

1. Разберись с `pr.yml` вендора. Он вызывает
   `paperclipai/paperclip/.github/workflows/pr-trusted.yml@master`, то есть CI форка зависит от
   репозитория вендора. Выбери одно:
   - переключить `pr.yml` на локальный `./.github/workflows/pr-trusted.yml`;
   - выключить `pr.yml` и завести свой `.github/workflows/myrmidon-ci.yml`.
   
   Критерии выбора: работает без секретов вендора, укладывается по времени (ориентир — до
   40 минут), даёт понятные имена проверок.
2. Обязательные проверки на `pull_request` и `push` в `main`:
   - `pnpm install --frozen-lockfile`;
   - `pnpm -r typecheck`;
   - `pnpm test:run`;
   - `pnpm build`.
   
   Тесты, которым нужны секреты или живая сеть вендора, пропускай явно и перечисли в
   `docs/myrmidon/ci.md` с причиной.
   
   Отдельная проверка — тесты наших скриптов: `node --test` по `scripts/myrmidon/`, файлы
   `*.test.mjs`. Их пишут трек 1 (выкат) и трек 5 (перенос вендора). Пока файлов нет, проверка
   проходит пусто.
3. Workflow вендора с триггером на `master` (у нас ветка `main`) не срабатывают — не трогай их.
   Workflow, которые у нас сработали бы и упали без секретов вендора, перечисли в
   `docs/myrmidon/ci.md`. Там же дай команды для их выключения через API GitHub (для сопровождающего).
   Файлы вендора без нужды не удаляй и не правь: каждое такое изменение — конфликт при
   переносе.
4. Необязательно, но полезно: `CLAUDE.md` в корне — короткий указатель для будущих сессий на
   `docs/myrmidon/README.md`, `CONVENTIONS.md` и `AGENTS.md`. У вендора такого файла нет,
   конфликтов не будет.

**Готово, когда:**

- CI запускается на PR и на `main`;
- на `main` он зелёный;
- в черновом PR с нарочно сломанным тестом CI красный (PR потом закрыть без слияния, ссылку
  дать в отчёте);
- имена обязательных проверок перечислены в отчёте — сопровождающий добавит их в ruleset.

### Шаг 2. Лицензии, секреты, внутренние адреса

1. **Лицензии зависимостей.** `pnpm licenses list --prod --json` плюс скрипт
   `scripts/myrmidon/check-licenses.mjs` с политикой `scripts/myrmidon/license-policy.json`:
   - разрешены MIT, ISC, BSD-2/3-Clause, Apache-2.0, 0BSD, CC0-1.0, Unlicense, BlueOak-1.0.0,
     Python-2.0, OFL-1.1 (шрифты);
   - запрещены GPL, AGPL, SSPL, отсутствующая или неизвестная лицензия;
   - исключения — списком, с причиной на каждое.
   
   Новых зависимостей для проверки не добавлять.
2. **Поиск секретов.** gitleaks закреплённой версии, бинарник проверяется по sha256.
   Сканируется дифф PR; при `push` в `main` — новые коммиты. Однократно просканируй всю
   историю и приложи итог к отчёту: сколько находок и их класс, **без самих значений**.
   Ложные срабатывания на тестовых данных вендора — в `.gitleaks.toml` с комментарием.
3. **Внутренние адреса.** Шаблоны берутся из секрета репозитория (например,
   `MYRMIDON_FORBIDDEN_PATTERNS`, по строке на шаблон), чтобы сам список не лежал в открытом
   репозитории. Проверка ищет совпадения в диффе PR. Если секрет не задан, job пропускается с
   предупреждением, а не падает. Плюс общая проверка частных IP-диапазонов в диффе
   (`10.*`, `172.16–31.*`, `192.168.*`) с исключениями для тестов вендора.

**Готово, когда:** три проверки работают в CI. Каждая краснеет на нарочно добавленной находке
в черновом PR (после проверки PR закрыт):

- заведомо ненастоящий «секрет» в формате, который ловит gitleaks;
- запрещённая лицензия в фикстуре;
- адрес `10.1.2.3`.

Если защита push у GitHub не пропустит тестовый «секрет», проверь gitleaks локально в сессии и
приложи вывод.

### Шаг 3. Совместимость плагинов

1. Список плагинов с версиями — `scripts/myrmidon/plugin-compat/plugins.json` (см. «Входы»).
2. Job CI ставит каждый плагин в чистый каталог и проверяет его против текущего SDK плагинов
   из репозитория:
   - манифест проходит проверку;
   - модуль воркера загружается;
   - в идеале — сервер со встроенным postgres стартует с установленным плагином, и плагин
     доходит до рабочего состояния.
   
   Механизм выбери по коду SDK (`packages/plugins/sdk`) и опиши в `docs/myrmidon/ci.md`.
3. hindsight — обязательный. Остальные можно пометить «предупреждение, не блок», если их
   поломка не наша.

**Готово, когда:** job зелёный на `main`. Если в фикстуре манифеста hindsight нарочно сломать
обязательное поле, job красный.

### Шаг 4. Образ

1. Сборка образа в Actions из `Dockerfile` вендора:
   - только amd64;
   - публикация в `ghcr.io/itkadr-git/myrmidon`;
   - `docker.yml` вендора уже строит `ghcr.io/${{ github.repository }}` — адаптируй его или
     заведи `myrmidon-image.yml`; объясни выбор в `docs/myrmidon/ci.md`.
2. Теги образа:
   - `sha-<короткий коммит>` на каждый `push` в `main`;
   - `main` — плавающий;
   - `<версия вендора>-myr.<N>` на git-тег выпуска того же вида (первый выпуск —
     `2026.916.1-myr.1`).
3. `PAPERCLIP_BUILD_VERSION` и `PAPERCLIP_BUILD_COMMIT` берутся из git, чтобы `/api/health`
   показывал версию и коммит.
4. Метки OCI: `org.opencontainers.image.title=Myrmidon`, `source` — адрес репозитория,
   `licenses=MIT`, отдельной меткой — версия вендора в основе.
5. Версии CLI в `production`-стадии закрепить аргументами сборки: сейчас они ставятся
   `@latest`, и сборка невоспроизводима. По умолчанию — версии на момент правки.
6. **Не добавлять** в образ медиа-инструменты (ffmpeg, yt-dlp, генераторы) — это отдельный
   сервис вне форка.
7. В сводке job — digest образа.

**Готово, когда:**

- образ опубликован;
- `docker run` этого образа (в CI, короткий smoke) отвечает на `/api/health` версией и
  коммитом, совпадающими с ожидаемыми;
- digest есть в сводке job;
- образ не собирается на PR из чужих форков.

### Шаг 5. Телеметрия выключена

Вендорская телеметрия отправляет события на адреса вендора по умолчанию. Они захардкожены:

- `packages/shared/src/telemetry/client.ts` — два адреса приёма: `telemetry.paperclip.ing` и
  запасной `*.execute-api.us-east-1.amazonaws.com`;
- `server/src/services/feedback-share-client.ts` — выгрузка отзывов на `telemetry.paperclip.ing`;
- `packages/shared/src/announcements.ts`, `server/src/services/announcement-feed.ts` — лента
  объявлений с `pages.paperclip.ing`, включена по умолчанию (`server/src/config.ts`). Это не
  телеметрия, но это обращение к вендору: по умолчанию выключить, адрес по умолчанию убрать.

Точные строки и полный список файлов — в `myrmidon-deploy/patches/T1-telemetry-off/README.md`.

1. Адреса вендора из кода убрать. Адреса приёма по умолчанию нет.
2. По умолчанию телеметрия выключена: и в сервере, и в CLI (`cli/src/telemetry.ts`; CLI пишет
   `telemetry: {enabled: true}` в новый конфиг в `onboard.ts`, `configure.ts`,
   `commands/worktree-lib.ts`). Включить
   можно только двумя действиями сразу: флаг включения и явный адрес приёма. Одного флага мало.
3. Места вызова телеметрии по коду **не трогать**: они вызывают клиент, а клиент без адреса
   ничего не делает. Так меньше конфликтов при переносе вендора.
4. Обновить `packages/shared/src/telemetry/README.md` и `docs/feedback-voting.md`: у нас по
   умолчанию выключено.
5. Тесты вендора, которые ждут адрес вендора, поправить минимально. Наши тесты —
   в `*.myrmidon.test.ts`.

Трассировку (OpenTelemetry, `server/src/instrumentation.ts`) и журнал прогона не трогать.

**Готово, когда:**

- тест: без настроек событие телеметрии и выгрузка отзывов не вызывают `fetch`; на коде
  вендора тест красный;
- тест: с флагом, но без адреса — тоже ничего не отправляется;
- `grep -rnE "telemetry\.paperclip\.ing|execute-api\.us-east-1\.amazonaws\.com|pages\.paperclip\.ing"`
  по `server/ cli/ packages/ ui/` без тестов пуст (история в `releases/` не в счёт);
- тест: без настроек лента объявлений не запрашивается.

### Шаг 6. Минимальный ребрендинг

1. Главная страница репозитория — `.github/README.md`: GitHub показывает его раньше корневого
   `README.md`. Корневой README вендора остаётся нетронутым, при переносе конфликтов не будет.
   В `.github/README.md`:
   - что такое Myrmidon;
   - что он основан на Paperclip 2026.916.1 под MIT;
   - что он не связан с вендором;
   - ссылки на `docs/myrmidon/`.
   
   Без внутренних подробностей.
2. `NOTICE` в корне:
   - Myrmidon (c) 2026 участники проекта;
   - основан на Paperclip, Copyright (c) 2025 Paperclip AI, MIT;
   - указатели на сторонние уведомления в дереве: `packages/adapters/hermes/LICENSE`,
     `ui/public/fonts/NOTICE.md`, `ui/public/brands/adapters/LICENSE`,
     `ui/public/brands/apps/LOBE-LICENSE`,
     `packages/paperclip-runner/devtools/issue-thread/src/fonts/NOTICE.md`.
3. `LICENSE` вендора не менять. Имена пакетов, CLI, `PAPERCLIP_*`, тексты интерфейса не
   менять.

**Готово, когда:** на главной странице репозитория виден README Myrmidon, `NOTICE` на месте,
`LICENSE` не изменён.

### Шаг 7. Выкат по отпечатку образа и откат (R4)

Облачная сессия не видит наших серверов. Поэтому здесь только универсальные скрипты и описание;
наши значения сопровождающий положит в `myrmidon-deploy`.

1. `scripts/myrmidon/deploy/`, bash со строгим режимом или Node без зависимостей:
   - `deploy.sh --digest sha256:… [--dry-run]` выполняет:
     1. проверку, что образ с этим digest тянется;
     2. запоминание текущего digest как «предыдущего»;
     3. дамп БД перед выкатом через подключаемую команду из файла настроек, с проверкой, что
        дамп не пустой;
     4. вход в обслуживание через подключаемый хук (когда появится R3 из трека 5 — его API
        `/api/myrmidon/maintenance`, контракт возьми из
        `docs/myrmidon/design/maintenance-mode.md`), иначе хук «пауза»;
     5. ожидание нуля идущих прогонов с таймаутом;
     6. смену образа одной строкой в файле override и пересоздание только сервиса сервера;
     7. проверку `/api/health`: статус, версия и коммит совпадают с ожидаемыми;
     8. выход из обслуживания.
   - `rollback.sh` — возврат на предыдущий digest. Восстановление дампа — только явным флагом
     и с подтверждением: миграции односторонние.
   - `verify-health.sh --expect-version … --expect-commit …`.
   - Файл настроек-пример `deploy.env.example` с плейсхолдерами: каталог compose, имя сервиса,
     адрес health, команды дампа и хуков.
2. `docs/myrmidon/deploy.md`:
   - порядок выката и отката;
   - что проверять после выката;
   - **стенд проверки выпуска на отдельной ВМ:** требования к ресурсам в общем виде,
     разворачивание образа на копии последнего дампа, внешние интеграции выключены (чаты,
     почта, агенты на паузе), smoke-проверки (health, миграции прошли, список агентов, открыть
     задачу, короткий прогон тестовым адаптером), критерии «можно выкатывать».
3. Тесты скриптов в CI: shellcheck (если bash) и тесты с поддельными `docker`, `curl` и
   командой дампа в `PATH`:
   - успешный выкат;
   - несовпадение версии в health → выход с ошибкой и подсказка отката;
   - пустой дамп → отказ до смены образа;
   - `--dry-run` ничего не меняет и печатает план.

**Готово, когда:** скрипты и документ в `main`, тесты зелёные в CI, в скриптах и документе нет
наших адресов и имён.

## Чего не делать

- Не трогать код других треков: адаптеры, heartbeat, шлюз инструментов, чаты, навыки.
- Не удалять и не править workflow вендора без нужды: выключение — через настройки
  репозитория, силами сопровождающего.
- Не добавлять в образ медиа-инструменты и наши плагины. Плагины ставятся в томе при
  развёртывании.
- Не публиковать образ в пространстве имён вендора.
- Не менять `LICENSE`, имена пакетов и CLI.
- Не класть в скрипты и документы наши адреса, имена хостов и пути.
- Не собирать образ в сессии: только в Actions.

## Отчёт

- В каждом PR — описание по шаблону из CONVENTIONS.
- В конце:
  - список PR;
  - имена обязательных проверок CI для ruleset;
  - список workflow вендора, которые сопровождающему нужно выключить;
  - итог полного скана gitleaks (без значений);
  - digest первого образа из `main`;
  - что проверить на стенде.
