# Трек 6 — безопасность и модели

**Функции:** S2 (окружение прогона), S4 (агент не меняет свои настройки), S5 (маскирование
секретов), M1 (модели в карточке агента).

Перед началом прочитай [README](../README.md), [ROADMAP](../ROADMAP.md),
[CONVENTIONS](../CONVENTIONS.md). Этот файл самодостаточен для работы трека.

## Цель

- Прогон агента не получает секреты сервера.
- Агент не может менять свою настройку, а неверная модель не сохраняется.
- Значения секретов не оседают в журналах, результатах и сообщениях.
- Модели для текста, зрения, видео, слуха, голоса, резервные модели и уровень рассуждений задаются в
  карточке агента и доходят до прогона `hermes_local`.

## Входы

- Заплаток нет, это новая работа. Опора — открытые PR вендора, идеи брать, не код целиком:
  - #10052 — не отдавать процессу Hermes окружение сервера: белый список плюс флаг
    `inheritProcessEnv`;
  - #11311 — пароли из строк подключения к БД в транскриптах;
  - #13936 — учётные данные в адресах git.
- Факты 916.1, проверенные по коду:
  - адаптер Hermes строит окружение процесса из `{...process.env}`
    (`packages/adapters/hermes/src/server/execute.ts`). Остальные локальные адаптеры — так же:
    `{ ...process.env, ...env }` в своих `execute.ts`;
  - вендорский `sanitizeInheritedPaperclipEnv`
    (`packages/adapter-utils/src/server-utils.ts`) убирает только переменные `PAPERCLIP_*`.
    `DATABASE_URL`, `BETTER_AUTH_SECRET`, облачные ключи сервера проходят в прогон;
  - секреты сервера, которые не должны попасть в прогон: `DATABASE_URL`,
    `BETTER_AUTH_SECRET`, `PAPERCLIP_AGENT_JWT_SECRET`, `PAPERCLIP_DECISION_SIGNING_SECRET`,
    `PAPERCLIP_TOOL_ACTION_SIGNING_SECRET`, `PAPERCLIP_WORKSPACE_HANDOFF_SECRET`,
    `PAPERCLIP_SECRETS_MASTER_KEY`, `PAPERCLIP_SECRETS_MASTER_KEY_FILE`, `AWS_*`, ключи
    провайдеров моделей уровня сервера;
  - самоизменение агента разрешено решениями `allow_self` в
    `server/src/services/authorization.ts`;
  - маскирование у вендора: `server/src/redaction.ts`, `server/src/log-redaction.ts`,
    `server/src/middleware/redact-sensitive.ts` и маскирующий слой ответов API
    (вендорский #9860).
- Ключи конфигурации Hermes для M1 — по документации Hermes Agent:
  - `model.default` — основная модель;
  - `auxiliary.vision.{provider,model}` — зрение;
  - `stt.*` — слух, `tts.*` — голос;
  - `fallback_model` — одна запись или цепочка;
  - `agent.reasoning_effort` — уровень рассуждений.
  
  Сверь с документацией версии, на которую опираешься, и запиши в PR, что проверил.

## Шаги

### Шаг 1. S2 — прогон видит только своё окружение

1. Новый модуль `packages/adapter-utils/src/myrmidon-run-env.ts`. Функция строит окружение
   процесса прогона из трёх источников:
   - **базовые переменные по списку разрешённых:** `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`,
     `LANG`, `LC_*`, `TZ`, `TERM`, `TMPDIR`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`,
     `SSL_CERT_DIR`, `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` и их строчные варианты;
   - **окружение из `adapterConfig.env` агента** — вместе с секретами, привязанными к агенту
     (сервер их уже разворачивает);
   - **переменные прогона, которые ставит сам сервер** (`PAPERCLIP_*` этого прогона).
   
   Всё прочее из окружения сервера отбрасывается.
2. Расширение списка — настройка `MYRMIDON_RUN_ENV_ALLOW` (имена через запятую, без
   значений).
3. Флаг на агента `adapterConfig.inheritProcessEnv: true` — старое поведение. По умолчанию
   `false`. Включается только администратором (связано с S4), каждое включение пишется в
   журнал.
4. Переходный период: в журнал сервера на уровне debug — **имена** отброшенных переменных, без
   значений. Эксплуатация увидит, чего не хватает прогонам.
5. Применить:
   - у `hermes_local` — после P4;
   - у локальных адаптеров `claude`, `codex`, `cursor`, `gemini`, `grok`, `kimi`, `opencode`,
     `pi` — вызов модуля вместо `{...process.env, ...}`, метка `myrmidon(S2)`.
6. Проверь пути запуска в песочнице и на удалённой машине
   (`packages/adapter-utils/src/execution-target.ts`, `sandbox-managed-runtime.ts`, `ssh.ts`):
   не уходит ли туда окружение сервера. Если уходит — то же правило. Если трогать опасно —
   строка в «Известные пробелы» DIVERGENCE.md.

**Готово, когда:** тесты зелёные, на коде вендора красные.

- «Прогон не видит пароль базы». В `process.env` теста заданы `DATABASE_URL`,
  `BETTER_AUTH_SECRET`, `PAPERCLIP_AGENT_JWT_SECRET`, `PAPERCLIP_DECISION_SIGNING_SECRET`,
  `PAPERCLIP_TOOL_ACTION_SIGNING_SECRET`, `PAPERCLIP_SECRETS_MASTER_KEY`. Поддельный CLI
  адаптера печатает имена своих переменных — ни одной из этих там нет. Переменные
  `adapterConfig.env` и прогона есть.
- `MYRMIDON_RUN_ENV_ALLOW` добавляет имя.
- `inheritProcessEnv` возвращает старое поведение, агент сам его включить не может.
- Тест есть для `hermes_local` и хотя бы для двух других адаптеров.

### Шаг 2. S4 — агент не меняет свои настройки, модель проверяется при сохранении

1. В `server/src/services/authorization.ts` решения `allow_self` для изменения карточки и
   конфигурации адаптера агентом **самим себе** запрещены. Разрешённые поля — явный список,
   по умолчанию пустой, константой в модуле `server/src/myrmidon/agent-self-update.ts`.
   Чтение своей карточки остаётся.
2. Проверка модели при сохранении карточки (`server/src/routes/agents.ts` или сервис):
   - модель, которой нет в списке моделей адаптера, отклоняется с 422 и понятной ошибкой;
   - список — тот, что адаптер отдаёт интерфейсу, включая список, заданный администратором
     инстанса;
   - пустое значение и специальные значения адаптера (например, «по умолчанию») — по правилам
     адаптера, без отказа.
3. Касается и новых полей M1.

**Готово, когда:** тесты зелёные, на коде вендора первые два красные:

- токен агента, `PATCH` своей карточки → 403;
- неизвестная модель → 422;
- администратор меняет карточку агента → 200;
- агент с правами управления меняет **другого** агента по правилам вендора — поведение не
  изменилось.

### Шаг 3. M1 — модели в карточке агента

1. **Поля карточки:** модель для текста, зрения, видео, слуха (распознавание речи), голоса
   (синтез), резервные модели (упорядоченный список), уровень рассуждений. Хранение — в
   `adapterConfig`, например `adapterConfig.models = {text, vision, video, stt, tts,
   fallbacks: [], reasoningEffort}`. Миграций нет. Имя и форму выбери сам, согласуй с
   существующим полем модели адаптера.
2. **Интерфейс** — форма адаптера Hermes (`packages/adapters/hermes/src/ui/build-config.ts`)
   и схема (`packages/adapters/hermes/src/server/config-schema.ts`). Модели выбираются из того
   же списка, что основная. Правила дизайн-системы вендора.
3. **Для `hermes_local`** — новый модуль
   `packages/adapters/hermes/src/server/myrmidon-profile-config.ts`. Он дописывает поля
   карточки в `config.yaml` **конкретного прогона**, во временную копию из P4:
   - текст → `model.default`;
   - зрение → `auxiliary.vision`;
   - слух → `stt`;
   - голос → `tts`;
   - резервные → `fallback_model`;
   - рассуждения → `agent.reasoning_effort`.
   
   Правила:
   - пустое поле не меняет значение профиля;
   - постоянный профиль агента не меняется;
   - если Hermes не поддерживает поле (например, отдельной модели видео может не быть) —
     предупреждение в журнал прогона, не ошибка.
   
   Точка вызова в `execute.ts` — после P4.
4. **Уровень рассуждений** — переключатель вендора «уровень мышления» должен доходить до
   Hermes. Если он уже есть в карточке, используй его, а не заводи второй.
5. Другие адаптеры: поля хранятся, применяются там, где адаптер это умеет. Где не умеет — в
   интерфейсе пометка «не поддерживается адаптером».
6. Ключи и адреса моделей в карточку не пишутся: только имена моделей.

**Готово, когда:** тесты зелёные.

- Карточка со всеми полями → сгенерированный `config.yaml` прогона содержит ожидаемые ключи.
- Пустые поля → ключи профиля не тронуты.
- Неподдерживаемое поле → предупреждение, прогон стартует.
- Неизвестная модель в любом поле → 422 (S4).
- Постоянный профиль после прогона не изменился.

### Шаг 4. S5 — маскирование секретов

1. Модуль `server/src/myrmidon/secret-masking.ts`. Он знает значения секретов, которые могут
   встретиться:
   - секреты компании, привязанные к прогону и агенту;
   - развёрнутые значения секретов из `adapterConfig.env`;
   - секреты сервера из списка S2;
   - пароль из строки подключения к БД.
   
   Маскирует их в тексте: `[secret:<имя>]` или `****`. Значения короче 8 символов не
   маскируются — иначе пострадают обычные слова. Строки подключения и адреса с учётными
   данными маскируются по шаблону: идеи #11311 и #13936.
2. Точки применения — там, где текст сохраняется или уходит наружу:
   - события и журнал прогона;
   - результат прогона (`result_json`) и транскрипт;
   - комментарий, созданный агентом;
   - исходящее сообщение в чат.
   
   Вендорские `redaction.ts` и `log-redaction.ts` расширить, а не дублировать. Точки вызова в
   чужих файлах — по одной строке, после слияния правок треков 2–5 в этих файлах.
3. Маскировать при записи, а не только при выдаче: в БД значения секретов оседать не должны.

**Готово, когда:** тесты зелёные, на коде вендора красные.

- Значение секрета агента в выводе прогона → в сохранённом событии и в результате — маска.
- Комментарий агента со значением секрета → сохранён с маской.
- Исходящее сообщение чата с секретом → уходит с маской.
- Строка `postgres://user:pass@host/db` в выводе → пароль замаскирован.
- Короткое значение (меньше 8 символов) не портит обычный текст.

## Чего не делать

- Не делать песочницу на агента (S3), хранилище паролей (S1), разрешения на инструменты (S6) —
  это V1.x.
- Не делать LiteLLM-интеграцию (M2): список моделей — тот, что уже есть у адаптера.
- Не писать ключи и адреса провайдеров в карточку и в конфиг прогона.
- Не ломать передачу секретов, привязанных к агенту: они должны доходить до прогона.
- Не трогать передачу промпта (H4, трек 4) и навыки (H1, трек 4) в тех же файлах.
- Не трогать `packages/adapter-utils/src/github-launcher.ts` (P6, трек 3). Он работает внутри
  процесса прогона и получает уже отфильтрованное окружение.
- Не делать миграций БД.
- Не класть в тесты настоящие значения секретов: только заведомо поддельные.
