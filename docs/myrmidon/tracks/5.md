# Трек 5 — эксплуатация

**Функции:** R3 (режим обслуживания), R2 (еженедельный перенос релиза вендора).

Перед началом прочитай [README](../README.md), [ROADMAP](../ROADMAP.md),
[CONVENTIONS](../CONVENTIONS.md). Этот файл самодостаточен для работы трека.

## Цель

- **R3.** Доску можно перевести в режим обслуживания и вернуть без потерь и без замков:
  - новые прогоны не стартуют;
  - идущие дожидаются или прерываются с повтором;
  - рутины и сторожа стоят;
  - побудки копятся и доставляются после выхода.
  
  Этим режимом пользуются выкат (R4, трек 1) и любое плановое окно.
- **R2.** Раз в неделю бот на нашей доске переносит последний стабильный релиз вендора
  отдельным PR с отчётом.

## Входы

- Заплаток у R3 и R2 нет: это новая работа.
- Что уже есть у вендора в 916.1 — строить поверх этого, а не параллельно:
  - дренаж при остановке: `heartbeat.drainRunningRunsForShutdown`,
    `drainActiveRunExecutions`, горячий перезапуск с «затишьем планировщика»
    (`prepareHotRestartShutdown`, `reconcileHotRestartAdoption`), всё в `server/src/index.ts`;
  - очередь побудок: `server/src/modules/wake-queue/**`;
  - сторож идущих прогонов: `server/src/modules/active-run-watchdog/**`;
  - рутины: `server/src/services/routines.ts`, `server/src/routes/routines.ts`;
  - настройки инстанса: таблица `instance_settings`, JSON-поле `general`, сервис
    `server/src/services/instance-settings.ts`;
  - пауза агента: `paused_at`.
- Что вендор влил после 916.1 в ту же зону — посмотри через `git fetch` репозитория вендора,
  чтобы не дублировать то, что придёт при переносе:
  - #14028 — побудки во время дренажа остаются в очереди, прерванные передачи повторяются;
  - #14046 — эскалация задачи, чей прерванный прогон исчерпал повторы;
  - #13761 — отмена устаревших продолжений перед запуском.
- Открытый PR вендора #3837 (пауза и продолжение сразу для всех агентов) — как идея, не как
  основа.
- Боевые требования к окну (наш протокол «пауза → ноль прогонов → пересоздание → проверка →
  снятие паузы») описаны в `myrmidon-deploy`, если такой документ там есть. Иначе хватает этого
  файла.

## Порядок и зависимости

- **Шаг 1 (проект R3) — первым и быстро.** Трек 1 возьмёт из него контракт API для скриптов
  выката.
- Точку вызова в `server/src/modules/run-dispatch/**` ставь после слияния P2 (трек 2).
- `server/src/services/heartbeat.ts` правят треки 2 и 3. Твои куски там — только вызовы
  функций из твоего модуля, по возможности после их слияния.
- `server/src/index.ts` и `server/src/routes/health.ts` правит и трек 2 (P11). Порядок любой,
  перебазируйся.
- R2 не зависит от R3, его можно делать параллельно.

## Шаги

### Шаг 1. Проект режима обслуживания (документ, маленький PR)

`docs/myrmidon/design/maintenance-mode.md`, коротко и конкретно:

1. **Состояния:** `off` → `entering` (дренаж) → `on` → `leaving` → `off`. Переходы, кто их
   делает, что при сбое на каждом шаге.
2. **Область:** инстанс, компания, отдел или агент. Отдел — агент-руководитель и все его
   подчинённые по цепочке `reportsTo` (у вендора отдельной сущности «отдел» нет). Как области
   пересекаются: например, режим инстанса при уже включённом режиме компании; агент, который
   перешёл в другой отдел во время режима.
3. **Новые прогоны:** не стартуют в области режима. Побудки не отбиваются, а стоят в очереди
   (вендорская очередь побудок) и уходят после выхода. Ни одна не теряется.
4. **Идущие прогоны:** ждём до таймаута (`drainTimeoutSec`). По таймауту действие на выбор:
   - `wait` — ждать дальше;
   - `interrupt_and_retry` — прервать и назначить повтор после выхода.
   
   Прерывание режимом обслуживания **не ставит замок** «требуется разбор, не повторять»
   (`legacy_execution_requires_reconciliation` и подобные). Гарантию «без повтора» при
   настоящих сбоях не ослаблять: замок не ставится только тем прерываниям, которые сделал
   режим, и это видно по причине.
5. **Рутины и сторожа:** тики рутин в области режима пропускаются и после выхода не
   выполняются задним числом — это решение, запиши его. Сторожа не будят и не эскалируют.
6. **Хранение:** `instance_settings.general.myrmidonMaintenance` для инстанса; для компании,
   отдела (на карточке руководителя) и агента — существующие JSON-поля. Миграций нет.
7. **API** (контракт для трека 1):
   - `GET /api/myrmidon/maintenance`;
   - `POST /api/myrmidon/maintenance` с телом
     `{action: "enter"|"exit", scope: {type, id?}, reason, drainTimeoutSec, onTimeout}`.
   
   В ответе: состояние, число идущих прогонов, число побудок в очереди, время начала. Права —
   только администратор инстанса. Каждое действие пишется в журнал активности.
8. **Плашка в интерфейсе:** что видит пользователь и что может сделать.
9. **Zabbix (встроенная интеграция, по умолчанию выключена):** при входе и выходе создаётся и
   снимается период обслуживания через API Zabbix. Адрес и токен — из настроек или ссылки на
   секрет. Сбой Zabbix никогда не мешает режиму.
10. **Связь с остановкой сервера:** как вендорский дренаж при `SIGTERM` сочетается с режимом.
    Как выкат (R4) пользуется режимом.

**Готово, когда:** документ влит, контракт API в нём зафиксирован.

### Шаг 2. Режим обслуживания — сервер

1. Модуль `server/src/myrmidon/maintenance/**`: сервис состояний, маршруты API, хуки.
2. Точки вызова с меткой `myrmidon(R3)`, каждая — одна строка вызова:
   - `run-dispatch` — старт прогона запрещён в режиме;
   - `wake-queue` — побудка остаётся в очереди;
   - планировщик рутин — пропуск тика;
   - сторожа (`active-run-watchdog`, сторож задач) — пропуск;
   - `heartbeat.ts` — прерывание с повтором без замка;
   - `server/src/index.ts` — регистрация маршрутов и восстановление состояния при старте;
   - `server/src/routes/health.ts` — поле `maintenance`.
3. После перезапуска сервера режим сохраняется: состояние лежит в БД.

**Готово, когда** тесты со встроенным postgres зелёные:

- вход → новый прогон не стартует, побудка в очереди;
- выход → побудка доставлена ровно один раз;
- идущий прогон дорабатывает;
- таймаут с `interrupt_and_retry` → прогон прерван, после выхода повторён, замка нет;
- настоящий сбой прогона вне режима по-прежнему ставит замок, как у вендора;
- рутина в режиме не срабатывает;
- режим агента не мешает другим агентам;
- режим отдела действует на руководителя и его подчинённых и не действует на соседний отдел;
- режим переживает перезапуск сервера;
- API отвечает 403 не-администратору.

### Шаг 3. Режим обслуживания — интерфейс

- Плашка: новый компонент в `ui/src/components/myrmidon/`, одна вставка в общий макет.
- Управление в настройках инстанса: войти, выйти, область, таймаут, действие по таймауту.
- Правила дизайн-системы вендора: только токены, `pnpm check:token-gates`.

**Готово, когда:** компонентные тесты зелёные (плашка видна в режиме и скрыта вне его), проверка
токенов проходит.

### Шаг 4. Окно в Zabbix (интеграция, по умолчанию выключена)

Модуль `server/src/myrmidon/maintenance/zabbix.ts`, настройки `MYRMIDON_ZABBIX_URL`,
`MYRMIDON_ZABBIX_TOKEN_REF` (ссылка на секрет, не значение), `MYRMIDON_ZABBIX_HOST_GROUPS`.
Без настроек выключен.

**Готово, когда** тесты с поддельным `fetch` зелёные:

- вход создаёт период, выход снимает;
- ошибка Zabbix записывается в журнал, но режим входит и выходит нормально;
- без настроек вызовов нет.

### Шаг 5. R2 — еженедельный перенос релиза вендора

Перенос выполняет бот на нашей доске: рутина Paperclip, раз в неделю. У бота fine-grained
токен **только на `itkadr-git/myrmidon`** (секрет доски; сессия его не видит и не нужен).
Вендора бот читает публично, без токена. Трек делает скрипт, инструкцию для бота и тесты.
Рутину на доске заводит сопровождающий.

1. `scripts/myrmidon/vendor-sync/` (bash или Node без зависимостей):
   - **поиск тега:** последний стабильный тег вендора — `vYYYY.MDD.N` без суффиксов
     (`-canary`, `-beta`, `-rc`). Текущая база — самый свежий тег вендора, достижимый из
     `main`. Нет нового — выход «нечего делать» с кодом 0;
   - **слияние:** ветка `sync/<тег>` от `main`, `git merge --no-ff <тег>`;
   - **при конфликте** слияние прерывается (`merge --abort`), в файл отчёта пишется список
     файлов с конфликтами и строки DIVERGENCE.md, которые их касаются. Код выхода 2. Дальше
     конфликты разрешает бот по инструкции;
   - **отчёт** `sync-report.md`:
     - диапазон коммитов вендора;
     - строки DIVERGENCE.md, у которых, возможно, выполнено условие «как снимать» —
       упоминаемый PR вендора вошёл в диапазон;
     - новые и изменённые workflow в `.github/workflows/` — сопровождающий решает, выключать ли;
     - новые миграции БД вендора;
     - изменения в файлах с нашими метками `myrmidon(`;
     - изменения `package.json`, `pnpm-lock.yaml`, `Dockerfile`.
2. `docs/myrmidon/vendor-sync.md` — инструкция для бота:
   - порядок: скрипт → при конфликтах разрешить, сохраняя наши куски с меткой `myrmidon(` и
     смысл вендора → `pnpm install --frozen-lockfile`, typecheck, тесты → push ветки → PR с
     отчётом;
   - PR вливается **только merge commit**, не squash;
   - PR сливает сопровождающий после проверки. Автослияние ботом — только по отдельному решению сопровождающего;
   - что делать, если тесты красные: не сливать, описать в PR;
   - как снять нашу правку, которую закрыл вендор: отдельный PR после переноса, по колонке
     «Как снимать»;
   - учесть особенность первой базы: `v2026.916.1` — хотфикс-тег на боковой ветке вендора.
     При слиянии следующего стабильного тега из `master` возможен конфликт на том же
     исправлении (#13562). Разрешать в пользу вендора.
3. Тесты скрипта — `node:test`, файлы `scripts/myrmidon/vendor-sync/*.test.mjs`: их подхватывает
   проверка CI трека 1. В корневой `package.json` не добавлять. Во временном каталоге
   создаются поддельный «вендор» с тегами и наш «форк». Случаи:
   - нового тега нет → ничего не делается;
   - есть новый стабильный → ветка и слияние;
   - есть только canary/beta → ничего не делается;
   - конфликт → код 2 и список файлов;
   - в отчёте найдены затронутые файлы с меткой `myrmidon(` и новые workflow.

**Готово, когда:** скрипт, инструкция и тесты в `main`, тесты зелёные в CI. В описании PR —
пример отчёта на поддельных данных.

## Чего не делать

- Не делать миграций БД: состояние — в существующих JSON-полях.
- Не ослаблять вендорские гарантии «без повтора» для настоящих сбоев.
- Не заводить рутину на доске и не создавать токены: это делает сопровождающий.
- Не делать синхронизацию через GitHub Actions по расписанию: решение — рутина на доске.
- Не отправлять ничего вендору.
- Не класть в код, тесты и документы наши адреса Zabbix, имена групп хостов и агентов.
- Не трогать P1/P2/P9 в `heartbeat.ts` и `run-dispatch`: только свои точки вызова.
