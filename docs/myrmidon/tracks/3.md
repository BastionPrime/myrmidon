## Шаги

### Шаг 1. P10 — 405 на GET-поток MCP-шлюза

По спецификации MCP Streamable HTTP сервер, который не отдаёт поток по GET, обязан ответить 405.
Вендор на GET отвечает 200 с JSON-описанием шлюза.

Что сделать: в `server/src/routes/tool-gateway.ts`, в обоих GET-обработчиках
(`/mcp/gateways/:gatewayPublicId` и `/tool-gateway/gateways/:gatewayId/mcp`):

- если `Accept` содержит `text/event-stream` → 405, заголовок `Allow: POST`, JSON-ошибка;
- иначе — ответ вендора без изменений.

**Весь остальной файл — вендорский.** Старую нашу версию этого маршрута (срез 2026.831.1)
не брать ни целиком, ни кусками: она откатывает около 300 строк вендора.

**Готово, когда:**

- тест: GET с `Accept: text/event-stream` на оба пути → 405 и `Allow: POST`;
- тест: обычный GET → как у вендора;
- на коде вендора первый тест красный.

### Шаг 3. P6 — `gh` в прогоне получает учётку через брокер

Проблема: сервер даёт прогону один адрес брокера учёток GitHub — публичный адрес сервера.
Бывает, что из прогона он недоступен: например, за ним вход с клиентским сертификатом. Тогда
`gh` остаётся без учётки. Ошибка вендора: производные адреса-кандидаты наследуют протокол
публичного адреса, а не протокол, который слушает сервер.

Что сделать:

1. `packages/adapter-utils/src/github-launcher.ts`:
   - список кандидатов до 6, без дублей, в порядке `PAPERCLIP_GITHUB_BROKER_URL` →
     `PAPERCLIP_API_URL` → `PAPERCLIP_RUNTIME_API_URL` → элементы
     `PAPERCLIP_RUNTIME_API_CANDIDATES_JSON`;
   - запрос учётки по очереди: 10 с на адрес, 60 с всего, повтор на 409 сохраняется;
   - диагностика без токенов.
   
   Логику переносить **поверх текущего файла вендора**, а не копировать наш файл, иначе
   откатится вендорская правка `user.useConfigOnly`.
2. `packages/paperclip-runner/src/github-credential-environment.ts`: через границу раннера
   передаются `PAPERCLIP_RUNTIME_API_URL` и `PAPERCLIP_RUNTIME_API_CANDIDATES_JSON`.
3. `server/src/runtime-api.ts` — переписать в TS по черновику:
   - производные кандидаты строятся протоколом слушателя (`listenProtocol`, по умолчанию
     `http:`);
   - loopback-кандидат есть в списке всегда.
   
   Поправить ожидания вендорского `server/src/__tests__/runtime-api.test.ts`.
4. Зеркало в Rust-раннере — **не делаем**. Запиши в DIVERGENCE.md, раздел «Известные
   пробелы».

**Готово, когда:** новые тесты зелёные, на коде вендора красные (ориентир — около 20 проверок):

- порядок кандидатов, лимит 6, бюджеты 10/60 с, повтор на 409;
- сбой одного кандидата не останавливает перебор;
- производные кандидаты по протоколу слушателя, loopback всегда есть;
- обе переменные переносятся через границу раннера.

В тестах нет наших адресов.

### Шаг 4. P4 — инструменты MCP доски в прогоне `hermes_local`

Проблема: сервер строит для прогона MCP-шлюз подключений агента и отдаёт его адаптеру
(`ctx.runtimeMcp`). Адаптер Hermes это поле не читает, и инструменты подключений до агента не
доходят.

Что сделать: перенести `ope2469-src.patch` в `packages/adapters/hermes/src/server/execute.ts`.
В нём вместе:

1. **Серверы в прогон.** Hermes читает MCP-серверы только из `<HERMES_HOME>/config.yaml`.
   Профиль агента общий между прогонами, а токен шлюза живёт ограниченное время. Поэтому на
   прогон создаётся временный `HERMES_HOME`:
   - ссылки на все элементы профиля (включая `skills`);
   - своя копия `config.yaml` с правами 0600 и добавленным сервером прогона;
   - каталог удаляется после выхода процесса.
2. **`-t/--toolsets`** — ещё и список разрешённых MCP-серверов. Адаптер дописывает туда имена
   серверов прогона и серверов из профиля. Отключается полем `includeConfiguredMcpServers:
   false`.
3. **Внутренний адрес шлюза.** Адрес шлюза, который пришёл публичным origin, подменяется на
   внутренний: путь и query сохраняются, в лог пишется только пара origin без токена.
   - Умолчание в форке — **как у вендора, без подмены**.
   - Подмена включается настройкой уровня инстанса `MYRMIDON_HERMES_RUNTIME_MCP_URL_BASE`.
   - Поля `adapterConfig.runtimeMcpUrlBase` и `runtimeMcpUrlRewrite` из заплатки сохранить как
     переопределение на агента.
4. **Промпт через stdin** вместо аргумента командной строки.
5. **Проверка размера конверта** до запуска: понятная ошибка вместо `E2BIG`.

Сверь с `main` после вендорского #13891: он убрал дублирование контекста побудки в окружении.
Не возвращай его.

**Готово, когда:** 22 теста из `tests/` каталога P4 перенесены на нейтральные данные и
зелёные, на коде вендора красные. Тест «defaults to the in-container listener» из заплатки
проверяет подмену адреса по умолчанию — перепиши его под умолчание форка (без подмены, пока не
задана настройка). Плюс тесты:

- промпт не попадает в аргументы процесса;
- слишком большой конверт → понятная ошибка до запуска;
- без настройки адрес шлюза не меняется.

### Шаг 5. P9 — сбой инструмента не отключает подключение

**Итерация 1 — шлюз** (`server/src/services/tool-gateway.ts`). Основа — `v2/ope2732-v2-src.patch`
и `v2/ope2732-v2-tests.patch`, на тег ложатся чисто.

- Здоровье подключения — только для информации:
  - оно не скрывает каталог в discovery;
  - сбой `tools/call` не записывает `error`;
  - успешный вызов возвращает `ok`.
- Сбой сообщается по одному инструменту: текст называет инструмент, его имя у сервера,
  подключение и причину и говорит, что остальные инструменты доступны.
- Предохранитель на инструмент: после 3 транспортных сбоев одного инструмента подряд его вызовы
  60 с отвечают быстро (`503 tool_temporarily_unavailable`). Затем идёт один пробный вызов.
  Остальные инструменты подключения это не затрагивает. Состояние — в памяти процесса.
- Таймауты:
  - потолок 180 с;
  - 45 с по умолчанию для навигационных инструментов;
  - `toolTimeouts` на подключении.
- Причина сбоя транспорта показывается безопасно. Ошибка сервера цитируется до 300 знаков, без
  управляющих символов.
- Пороги — настройки `MYRMIDON_TOOL_BREAKER_FAILURES` (3), `MYRMIDON_TOOL_BREAKER_COOLDOWN_MS`
  (60000), `MYRMIDON_TOOL_TIMEOUT_MAX_MS` (180000), `MYRMIDON_TOOL_TIMEOUT_SLOW_MS` (45000).
  Имена можно уточнить, тогда запиши их в SETTINGS.md.
- Убери из кода номера наших задач (в патче их десятки) и русские тексты.

**Итерация 2 — отбор подключений для прогона.** Сейчас `server/src/services/heartbeat.ts`
(сборка MCP прогона) и `server/src/services/native-runtime/runtime-context.ts` отбрасывают
подключения со статусом здоровья «требует внимания» (`isToolConnectionAttentionHealth`). Так
одно «больное» подключение целиком исчезает из прогона.

1. Если в каталоге P9 есть итерация 2 (итог или снимок `v2.1-wip/`) — перенеси её. Снимок не
   финальный: проверь его по правилу ниже и своими тестами.
2. Если нет — сделай по этому правилу: подключение, назначенное агенту, остаётся в наборе
   прогона независимо от здоровья. Выключенное подключение (`disabled`) по-прежнему не
   попадает.
3. Проверь `server/src/services/tool-access.ts` и
   `server/src/services/tool-runtime-supervisor.ts`: не отключает ли сбой одного вызова
   локального stdio-сервера подключение целиком. Если отключает — то же правило.

**Готово, когда:**

- все тесты `server/src/__tests__/tool-gateway.test.ts` зелёные (74 на основе `v2/`, 81 на основе
  `v2.1-wip/`). Новые случаи:
  - каталог виден после сбоя;
  - здоровье не переключается;
  - на паузе только сбойный инструмент;
  - навигационный бюджет;
- на исходнике вендора и на первой нашей редакции новые случаи красные;
- тесты итерации 2 зелёные: подключение с «плохим» здоровьем остаётся в наборе прогона,
  выключенное не попадает.
