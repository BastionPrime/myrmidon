# Приём записей в план обновлений Myrmidon

Процедура описывает, как запись попадает в план обновлений, кто её проверяет и что делать
с секретами. Документ внутренний по духу, но репозиторий публичный: в нём и в записях —
плейсхолдеры (`example.com`, `192.0.2.0/24`), никаких имён, номеров задач нашей доски и
внутренних адресов. Общие правила — [CONVENTIONS.md](CONVENTIONS.md), раздел 9.

## 1. Что такое запись плана и правила плана

Запись — минимальный элемент плана обновлений: один баг, один долг, одна хотелка или один
пункт про процесс. План ведётся выпусками. Стандарт записи задаёт этот документ (поля — в
разделе 2), он же служит чек-листом приёма.

Правила плана:

1. Любой баг, долг или хотелка сначала попадает в план, а не сразу в работу.
2. Оператор раскладывает записи по выпускам и предлагает порядок.
3. Очередь выпуска утверждает владелец. Менять порядок можно только его словом.
4. Исполнителям задачи ставятся только из утверждённой очереди.
5. Авария идёт вне очереди: чинится сразу, а запись вносится в план задним числом, по тем
   же полям и с тем же сканером (раздел 5).

## 2. Поля записи

| Поле | Что содержит | Обязательное |
|---|---|---|
| Тип | `баг` / `долг` / `хотелка` / `процесс` | да |
| Что | Одно-два предложения: что именно меняется | да |
| Зачем | Проблема, которую решает; кого касается | да |
| Размер | Оценка: `S` (<1 дня) / `M` (несколько дней) / `L` (неделя и больше) | да |
| Зависимости | От каких записей зависит, что блокирует сама; «нет», если пусто | да |
| Риски | Что может сломаться, как проверим (тест в репозитории) | нет |

Заголовок записи — нейтральный, на русском или английском, без номеров задач, имён
агентов и серверов.

## 3. Роли

Роли названы обезличенно; кто именно их занимает, в публичном репозитории не указывается.

- **Участник** — предлагает запись: заполняет поля, прогоняет сканер, приносит текст
  на приём.
- **Оператор** — раскладывает принятые записи по выпускам и предлагает порядок, помечает
  дубликаты, следит за отсутствием пересечений с чужими файлами (карта файлов в
  CONVENTIONS.md, раздел 12).
- **Владелец** — утверждает очередь выпуска, решает споры, отклоняет запись с формулировкой
  причины. Порядок в утверждённой очереди меняется только его словом.

Участник и оператор могут совпадать в одном лице; очередь выпуска утверждает всегда
владелец.

## 4. Процедура приёма

1. **Черновик.** Участник пишет запись по полям из раздела 2.
2. **Самопроверка.** Участник прогоняет сканер текста (раздел 5) на полном тексте
   записи — включая поля «зачем», «зависимости», «риски». Сканер чист (exit 0) —
   запись готова к приёму. Есть находки — исправить текст и прогнать заново.
3. **Приём.** Участник передаёт текст записи оператору только задачей на внутренней
   доске. PR не подходит: он лежит в публичном репозитории, а план ведётся на доске.
4. **Раскладка.** Оператор проверяет запись по полям и карте файлов, помечает дубликаты и
   пересечения, раскладывает запись по выпускам и предлагает порядок внутри выпуска.
5. **Утверждение.** Владелец утверждает очередь выпуска или отклоняет запись. Порядок
   меняется только его словом. В работу исполнителям идут только записи из утверждённой
   очереди; авария — исключение по правилу 5 из раздела 1.

Запись без пройденного шага 2 к приёму не принимается.

## 5. Сканер текста

`scripts/myrmidon/scan-text.mjs` (Node, встроенные модули) сканирует произвольный текст
записи: тело, комментарии, описания задач. gitleaks остаётся стражем коммитов; этот
сканер — страж текста записей плана.

```sh
# из файла:
node scripts/myrmidon/scan-text.mjs --file entry.md
# из stdin:
cat entry.md | node scripts/myrmidon/scan-text.mjs
```

- Выход: `0` — текст чист, `1` — есть находки, `2` — ошибка использования или чтения. Текст,
  который не удалось прочитать (файл, stdin), чистым не считается.
- Находка печатается как тип паттерна и номер строки, **без** совпавшего текста:
  значение секрета не должно попадать в логи.
- Что ищется: присваивания `password/passwd/secret/token/api_key` (в том числе ключ JSON в
  кавычках; имя переменной подозрительно, значения не должно быть вовсе), заголовки
  приватных ключей, префиксы токенов (`github_pat_`, `ghp_`, `gho_`, `ghs_`, `ghu_`,
  `ghr_`, `pcp_`, `sk-`), токены Telegram-ботов, учётные данные внутри адреса (имя и пароль
  перед именем хоста), частные адреса (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`),
  пути к файлам секретов в системном каталоге настроек и к каталогу ssh-ключей, в том
  числе в обратных кавычках Markdown и в скобках.
- Наши адреса, домены и имена хостов сканер знает из переменной окружения
  `MYRMIDON_FORBIDDEN_PATTERNS` — того же списка, что и проверка диффов в CI: по одному
  регулярному выражению в строке, `#` начинает комментарий. Находка печатается как
  `forbidden pattern #N` (номер строки списка), сам шаблон и совпавший текст не печатаются.
  Список хранится вне публичного репозитория (секрет репозитория, см. [ci.md](ci.md)).
  Если переменная не задана, сканер печатает предупреждение и проверяет только встроенные
  правила: тогда наши адреса ловит только глаз владельца (раздел 7).
- Тесты: `node --test scripts/myrmidon/scan-text.test.mjs`.

## 6. Секреты в записях

В записи плана секретов не бывает: ни значений, ни «маскированных» фрагментов, ни
ссылок на файлы секретов с реальными путями.

Если в записи нужно описать сбой, связанный с секретом:

- **имя переменной без значения**: `API_TOKEN` (без `= …`);
- **номер строки или путь без содержимого**: «секрет передан в строке 42 конфига»;
- **краткое описание сбоя**: «токен истёк, продлён; журнал маскировки показал
  замаскированное значение».

Если секрет уже попал в текст записи или публичный репозиторий — не исправлять тихо:
из истории он не исчезнет. Немедленно поднять тревогу по внутренним каналам и
отметить в отчёте с пометкой «срочно» (правило раздела 9 CONVENTIONS.md).

## 7. Что проверяет владелец при утверждении очереди

1. Поля заполнены, размер адекватен описанию.
2. Шаг самопроверки пройден: сканер возвращал `0` на итоговом тексте записи.
3. Нет секретов и внутренних адресов (в том числе глазами: сканер — помощь, не замена
   чтению).
4. Зависимости реальны, пересечения с другими записями и чужими файлами разобраны.
