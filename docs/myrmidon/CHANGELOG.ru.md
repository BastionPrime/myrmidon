# Журнал изменений Myrmidon

> English version: [CHANGELOG.md](CHANGELOG.md)

Заметки о выпусках Myrmidon, новее сверху. Версия берётся из git-тега
`myr-v<major>.<minor>.<patch>` (CI вшивает её в образ и в `/api/health`); файла версии,
который надо править, нет. Версия Paperclip в основе — в метке образа
`io.github.itkadr-git.myrmidon.base.paperclip-version`. Подробности процедуры выпуска:
[ci.md](ci.md) и [deploy.md](deploy.md).

## Без выпуска

### Интерфейс настроек Telegram-уведомлений (TG-NOTIFY-SETTINGS, часть F)

- Панель «Уведомления Telegram» на экране «Система» нового UI: все пять секций
  настроек telegramNotify видны и редактируемы (дайджест, ошибки, сообщения
  владельца, эскалации, проактивность головного бота), каждая секция по
  умолчанию выключена, журнал изменений настроек рисуется из документа,
  который отдаёт ядро настроек. Сохранение отправляет один PATCH только с
  изменёнными полями. Зависит от ядра настроек (часть A); пока оно не влито,
  UI покрыт тестами по замоканному JSON-контракту.
## 1.6.1

### Свои касты, потребители (CUSTOM-CASTES B)

- Серверные потребители справочника каст компании (сам справочник — часть A):
  валидатор роли агента принимает любой корректный ключ касты (латиница,
  цифры, дефис, 1–60), а create/update агента отказывают ключом, которого нет
  в справочнике компании, — 400 с именем ключа; гейт роя читает касту
  клеймящего агента — `swarmEligible=false` возвращает новый reason `caste_excluded`
  (надзорная каста вообще не попадает в пул claim), кастовый `maxActiveTasks`
  перекрывает глобальный лимит роя для агентов этой касты. Роль без записи в
  справочнике и сборка без подключённого справочника работают как раньше.
  Матрица автономии и логика authorization не менялись: ключ касты — это
  строка роли, проверки ceo остались байт-в-байт, кастовые роли работают через
  явные гранты. Регрессионные тесты закрепляют всё выше, включая «перевод
  агента на касту не меняет ни одного вердикта автономии».

### Сторож мёртвых блоков (STALE-BLOCK, часть B)

- Периодический модуль `myrmidon/stale-block`: раз в
  `MYRMIDON_STALE_BLOCK_INTERVAL_SEC` (умолчание 300 с) проверяет
  blocked-задачи и снимает блок, у которого мертвы все причины — блокер
  закрыт (done) или отменён (cancelled; отменённые блокеры не будят путь
  blockers-resolved), дата `reasonRef.dueAt` прошла, гейт/событие снято.
  Мёртвые blocked-by-рёбра удаляются обычным путём обновления issue,
  задача возвращается в `in_progress`, система оставляет один комментарий
  с причиной. Задачу с живой причиной sweep не трогает. Опционально, через
  `MYRMIDON_STALE_BLOCK_ENABLED` (умолчание 0).
- Один новый sourceKind `stale_block`: снятый блок поднимает одну карточку
  лиду и оператору, фид вычисляется на лету из процесса-локального реестра
  сигналов (нового хранилища нет); карточки гаснут через
  `MYRMIDON_STALE_BLOCK_SIGNAL_TTL_MS` (умолчание 24 ч).
### Расход прогонов через шлюз (HERMES-USAGE-COST)

- Прогоны hermes_gateway больше не пишутся в журнал расходов как unpriced
  с нулевой суммой: после каждого прохода сбора трат LLM-шлюза сверка
  заполняет строку `cost_events` каждого прогона фактическим расходом
  шлюза (cost_status=reported) и пересчитывает месячные счётчики
  агента/компании. Трогаются только unpriced-строки hermes_gateway —
  оценённые адаптером строки и чужие провайдеры не перезаписываются, а
  прогон без собранного расхода остаётся unpriced, цена не выдумывается.
  Первый проход может смотреть назад до 90 дней
  (`MYRMIDON_LITELLM_FIRST_LOOKBACK_DAYS`), а
  `POST /api/myrmidon/companies/:id/litellm/sweep` принимает `from` в теле
  для разового бэкфилла месяца. Чип forecast в UI-2.0 без заданного
  бюджета показывает только расход — плашка «$0 of $0» исчезает.

### Агенты-администраторы доски (ADMIN-AGENT, часть C)

- Интерфейсная половина назначения агента администратором доски. На вкладке
  **Permissions / Trust** карточки агента появился четвёртый флаг — **Board
  administrator**: переключение идёт тем же PATCH прав, что и три соседних
  флага, состояние приходит из API карточки агента (`access.boardAdmin` с
  откатом на `permissions.boardAdmin`), и оба читателя fail-closed — всё, что
  не явное `true`, читается как «не администратор». Переключатель видят
  только операторы с правом управления правами (роль owner или admin,
  администратор инстанса, локальная неявная доска); 403 от API превращается
  в человеческое пояснение под переключателем. Страница **Members** настроек
  компании называет каждого агента-администратора: по строке таблицы на
  не-terminated агента с флагом, с бейджем **Board administrator** и ссылкой
  на вкладку Permissions карточки. Семантика грантов (ключи прав, снимок
  грантов, запрет само-включения) — серверная половина функции, мержится
  отдельно. Руководство оператора:
  [guides/agent-board-admin.ru.md](guides/agent-board-admin.ru.md).

### Параллельные помощники без жёсткого потолка (HELPERS-NO-CAP)

- Число параллельных помощников — настраиваемый параметр **без встроенного
  верхнего предела**; умолчание остаётся 2 (решение владельца, повторено
  03.10). Жёсткий потолок 50, который зажимал даже значение из самих
  настроек владельца, убран: потолок компании (`maxPerAgent`) и лимит на
  агента берутся ровно как сохранены — из интерфейса, и компилятор профиля
  разрешает карточку против числа владельца как записано. Защита от
  опечатки — предупреждение, а не зажим: страница настроек показывает
  предупреждение о нагрузке на хост для сохранённого потолка выше 50 («столь
  высокие значения создают реальную нагрузку на хост — убедитесь, что это
  намеренно, а не опечатка»), сохранение никогда не блокируется. Поле лимита
  в карточке агента так же принимает любое целое число ≥ 1 и отклоняет
  только не-числа. Документация настроек:
  [SETTINGS.ru.md](SETTINGS.ru.md) § PARALLEL-HELPERS.

## 1.6.0

### Планировщик чата с доской (CTO-CHAT B)

- Планировщик чата с доской: одно сообщение владельца в свободной форме
  (`POST /api/myrmidon/cto-chat/plan`, или тот же шаг планирования из
  Telegram-диалога владельца) превращается в предложенный эпик с дочерними
  задачами и критериями приёмки каждой. Предложение показывается
  существующей карточкой доски `suggest_tasks` на стоящей задаче разговора, и
  именно приёмка карточки создаёт задачи — до приёмки не существует ничего,
  исполнитель не выводится из прозы, отклонённая или истёкшая карточка не
  создаёт ничего. Планировщик выключен, пока не заданы
  `MYRMIDON_CTO_CHAT_BASE_URL` и `MYRMIDON_CTO_CHAT_KEY_SECRET`; ключ шлюза —
  секрет компании, читаемый на каждый вызов и никогда не логируется. Модель
  по умолчанию — бесплатная `dashscope-qwen-flash`; одно предложение
  ограничено 8 дочерними задачами (жёсткий потолок 20), а один
  планировочный вызов никогда не повторяется. Руководство оператора:
  [guides/cto-chat-planner.ru.md](guides/cto-chat-planner.ru.md). Экран чата
  портала (часть A) — ниже.

### Чат CTO (CTO-CHAT)

- Экран «Чат с Полководцем» оболочки 2.0 (маршрут `commander-chat`, входы —
  рейка, нижняя панель телефона и палитра «Сказать Полководцу» с `Ctrl K`,
  переносящая набранный черновик): владелец пишет один запрос свободным
  текстом, экран вызывает планировщик чата с доской
  (`POST /api/myrmidon/companies/:companyId/cto-chat/plan`) и показывает
  предложенный эпик в режиме чтения — эпик, каждую дочернюю задачу, критерии
  приёмки построчно. Ожидающая карточка согласования `suggest_tasks` на
  стоящей задаче чата агента показывается существующим карточным компонентом;
  приёмка карточки создаёт задачи, отклонение не создаёт ничего. Тот же поток
  доступен из Telegram-лички владельца. Гайд оператора:
  [guides/commander-chat.ru.md](guides/commander-chat.ru.md).

### Эталоны и судья (EVALS-A часть A)

- Путь оценки: сеяный корпус нейтральных эталонных задач пилотной роли
  `engineer`, LLM-судья за LLM-шлюзом компании (по умолчанию бесплатная
  модель DashScope, один вызов chat/completions на задачу, строгий парсинг
  JSON — непарсируемый ответ даёт ноль с флагом `parseError`, а не
  выдуманные баллы), скоринг по рубрикам с CI pass rate для задач `code`,
  и вердикт «продвигать/подтвердить/регресс», где падение за порогом — не
  приговор, пока подтверждающий прогон не повторил его. Судья сам код не
  исполняет. Скоры живут в `myrmidon_eval_runs`; необязательный экспорт в
  Langfuse по умолчанию выключен и никогда не блокирует локальный скоринг.
  Чтение ограничено компанией, мутации прогона требуют board-актора,
  ненастроенный контур отвечает `503` с именами недостающих настроек. Шейм
  вердикта для жизненного цикла навыков (`candidate → verified → deprecated`
  с откатом) открыт как `POST …/evals/verdict`; смерженный модуль цикла пока
  не подключил его к доске. Руководство:
  [guides/reference-task-evals.ru.md](guides/reference-task-evals.ru.md).

### Экран обновлений стека (STACK-UPDATES часть C)

- Экран «Стек» в панели (Company → Stack, маршрут `/stack`): все компоненты
  реестра стека с нашей версией/коммитом/дайджестом (или честным `unknown` с
  причиной), где запущено, последним релизом автора, отставанием, заметными
  security/breaking-строками заметок релиза сворачиваемой выжимкой и вердиктом
  «патч закрыт» по каждой переносимой дельте; отстающие компоненты сверху,
  есть фильтр по имени. Кнопки «Обновить данные» и «Проверить релизы» запускают
  instance-admin-маршруты `POST /api/myrmidon/stack/refresh` /
  `POST /api/myrmidon/stack/check` прямо с экрана — сбой, включая 503
  сломанной пробы, показывается на месте без потери таблицы. Кнопка
  «Запланировать обновление» на отстающей строке открывает диалог с планом по
  умолчанию (версии, наши патчи, заметные строки, канарейка затем бой, откат) и
  создаёт черновик задачи в backlog без назначения через существующий маршрут
  создания задач — с экрана ничего не выкатывается. Сама сверка релизов
  (часть B: расписание, правила выжимки и вердикт «патч закрыт») и API реестра
  документированы в том же руководстве. Руководство:
  [guides/stack-registry.ru.md](guides/stack-registry.ru.md).

### Документация цикла обновлений стека (STACK-UPDATES часть D)

- Обзорный документ «Обновления стека» (EN + RU) обо всём цикле слежения за
  релизами: откуда берётся «наше» по каждой пробе (health-commit, docker-image,
  container-labels, env, manual, none) и откуда «у автора» (анонимное чтение
  GitHub releases/tags), как считается отставание и почему не совпавшая
  локальная версия читается как `unknown`, правила выжимки заметных строк,
  вердикт «патч закрыт» (closed/open/unknown по каждой переносимой дельте через
  compare API, с агрегатом), плановая сверка за
  `MYRMIDON_STACK_CHECK_INTERVAL_SEC` и ручная проверка, карточка внимания
  `stack_update` с ключом дедупликации, черновик задачи в backlog без
  назначения, который создаёт планировщик, обе настройки и поведение без сети
  (транспортный сбой → 503 с целым прежним кэшем; HTTP-ошибка источника →
  «неизвестно» по компоненту). Поещёчное руководство экрана — по ссылке, без
  дублирования. Документ: [stack-updates.ru.md](stack-updates.ru.md).

### Регламенты компании в вики (WIKI-CORTEX)

- Страницы-регламенты с жизненным циклом «черновик → одобрено», ревизиями и
  откатом: правка черновика или одобренного регламента добавляет новую
  ревизию DRAFT, а резолвер продолжает отдавать последнюю APPROVED, поэтому
  написание текста никогда не меняет то, что читает флот, без явного
  одобрения board; откат — ещё одна ревизия, копирующая более раннюю (история
  append-only, сам откат откатываем). Запись черновика открыта любому
  действующему лицу с доступом к компании — ревизии-черновики пишет
  агент-википедист, — а одобрение и откат доступны только board. Одобренные
  регламенты, применимые к роли, доходят до агентов через компиляцию профиля
  бота: один детерминированный workspace-файл `REGULATIONS.md` рядом с
  собственными файлами инструкций агента, где хэш профиля решает,
  перезапускается ли бот (те же одобренные ревизии — те же байты — без
  перезапуска; файл никогда не затирает `REGULATIONS.md` из собственного
  бандла агента). Роли — обычные ключи ролей, `*` означает все роли.
  Руководство оператора — API, механика доставки и инструкция по
  википедисту: [guides/wiki-regulations.ru.md](guides/wiki-regulations.ru.md).

### Матрица автономии

- Вердикты «роль × класс действия»: что агент роли может делать сам, а что
  требует доски. Матрица хранится как регламенты компании с ревизиями и
  отдаётся через REST API. Экран настроек «Матрица автономии» показывает и
  правит матрицу; каждая правка — новая ревизия, прежние вердикты остаются
  читаемыми и восстановимыми.

### Заявки роя (SWARM-CLAIM)

- Часть A, очереди задач по ролям с арендованными заявками: агент берёт
  верхнюю задачу очереди своей роли под лизом (TTL плюс heartbeat), который
  записан в новой таблице `issue_claims`. Checkout прогона пишет заявку,
  завершающийся прогон её освобождает; свип возвращает в очередь истёкшие
  лизы и лизы задач, покинувших очередь, и будит следующего агента роли.
  Лимит активных задач на агента не даёт одному забрать всю очередь, а задача
  P0 (critical) обходит обычный порядок очереди. Путь заявок выключен, пока не
  включён `MYRMIDON_SWARM_CLAIM_ENABLED`; TTL лиза, потолок активных задач и
  интервал свипа — `MYRMIDON_SWARM_LEASE_TTL_SEC`,
  `MYRMIDON_SWARM_MAX_ACTIVE_TASKS` и
  `MYRMIDON_SWARM_CLAIM_SWEEP_INTERVAL_SEC`.
- Часть B, вид супервизора и отчёт пилота по заявкам и лизам: состояние
  очередей и лизов по ролям и сравнение окна с замороженным срезом baseline.
  Запасное освобождение теперь тоже пишет причину освобождения. Настройки
  супервизора (`MYRMIDON_SWARM_SUPERVISOR_TASK_MAX`,
  `MYRMIDON_SWARM_PILOT_BASELINE_DOC`) описаны в [SETTINGS.md](SETTINGS.md).

### Жизненный цикл навыков (SKILL-LIFECYCLE)

- Жизненный цикл навыка компании `candidate → verified → deprecated` с
  промоушеном через согласование и откатом. Навык `candidate` доходит только
  до агентов из `MYRMIDON_SKILL_PILOT_AGENTS`, `verified` — до всех. Пока
  переменная не задана, набор пилота пуст и кандидат не получает никто.

### Поиск источников (FORAGING)

- Реестр источников компании, сравнение снимков источников, кандидаты в навыки
  по изменившемуся, бюджет стоимости на проход и экран. Foraging поставляется
  ВЫКЛЮЧЕННЫМ: без `MYRMIDON_FORAGING_ENABLED=1` таймер не взводится и ни один
  источник не читается; любое другое значение оставляет его выключенным, так
  что опечатка не включит его.

### Базовые метрики (BASELINE часть A)

- Шесть метрик доски по истории задач за произвольное окно, в разрезе проекта
  и роли исполнителя: цикл (todo → done, среднее, медиана, p90), время в
  ревью, доля возвратов (in review → in progress), время в блокировке с топом
  причин, прогоны на задачу и стоимость LLM на задачу. Отдаются через
  `GET /api/myrmidon/companies/:companyId/baseline/metrics?from&to`.
  Периодическая джоба, выключенная без `MYRMIDON_BASELINE_INTERVAL_SEC`,
  пересчитывает последние 14 дней по каждой компании и замораживает по одному
  срезу за проход в аддитивной таблице `baseline_metric_snapshots`, чтобы
  пилот можно было сравнить с измеренным «до». Падение одной компании не
  останавливает остальных.

### Параллельные помощники (PARALLEL-HELPERS)

- Агенты могут запускать параллельных субагентов-помощников. В карточке
  агента появляется блок «Параллельные помощники»: вкл/выкл, максимум
  одновременных помощников в пределах потолка компании и модель помощника из
  списка допустимых; рядом — значение по умолчанию для компании и подсказка о
  ёмкости. Компилятор профиля пишет соответствующую секцию делегирования для
  контейнеров ботов. Если ни карточка, ни сохранённые настройки не называют
  модель, помощники работают на `MYRMIDON_BOT_HELPER_MODEL`, а если и она не
  задана — на модели родительского агента.

### Качество и стек

### Доступ к GitHub из контейнера (CONTAINER-GITHUB-WRITE)

- Агент в контейнере бота может пушить в GitHub через управляемые доской
  учётные данные (#363): когда GitHub-личность прогона управляется доской
  (по умолчанию, см. `MYRMIDON_HOST_GITHUB_CREDENTIALS` в
  [SETTINGS.ru.md](SETTINGS.ru.md)), heartbeat выпускает capability
  `github_credentials`, привязанную к прогону, и адаптер `hermes_gateway`
  теперь доставляет её в контейнер — пара едет телом запроса `/v1/runs`
  (`github_broker`), привязывается только к этому прогону (contextvars,
  никогда не через общий для одновременных прогонов шлюза process env) и
  попадает в каждый дочерний процесс терминала и `execute_code` этого
  прогона как `PAPERCLIP_GITHUB_BROKER_URL`/
  `PAPERCLIP_GITHUB_BROKER_TOKEN`. Внутри контейнера credential-хелпер
  `git` dev-образа (URL-скоуп на `github.com` по https, ремоуты
  `ssh://git@github.com/…` переписываются на https) и врапер `gh` на каждом
  вызове резолвят учётные данные через брокера доски
  `POST /runtime-tools/github/credentials` и запускают настоящий
  `git`/`gh`; враперы перебирают до 6 адресов брокера
  (`PAPERCLIP_GITHUB_BROKER_URL` → `PAPERCLIP_API_URL` →
  `PAPERCLIP_RUNTIME_API_URL` → элементы
  `PAPERCLIP_RUNTIME_API_CANDIDATES_JSON`) и никогда не печатают токен.
  Прогон без capability — или карточка, чья GitHub-личность не управляется
  доской, — получает оба имени вырезанными, а враперы честно пропускают
  вызов дальше, ровно как до этой правки. Статический
  `GH_TOKEN`/`GITHUB_TOKEN`, унаследованный из профиля образа, больше не
  затеняет учётные данные: пока capability привязана, эти имена
  очищаются в дочерних процессах прогона. Это закрывает дыру, ради которой
  вводился `MYRMIDON_BOT_CONTAINER_GITHUB_ENV_ALLOWLIST` (см.
  SETTINGS.ru.md): allowlist остаётся запасным путём для ботов разработки
  на машинах, где адрес брокера доски действительно недостижим.

### Выкат и надёжность

- Автоматический откат по здоровью для доски и парка ботов (R5-C). Неуспешная
  проверка здоровья после выката больше не оставляет доску и затронутых ботов на
  сломанном образе. Доска: работа переходит в `rolling_back`, хостовой исполнитель
  запускает `rollback.sh` на образ, который выкат запомнил перед переключением;
  работа заканчивается `auto_rolled_back` (окно обслуживания закрыто) или
  `failed_rollback` (окно оставлено оператору). Боты: неуспешный канарейка или бот
  волны переводит раскат в `rolling_back`; каждый бот, получивший новый образ,
  получает обратно образ своей карточки по одному, и раскат заканчивается
  `rolled_back` с сохранённой исходной причиной. Переключатели (оба по умолчанию
  включены): `MYRMIDON_DEPLOY_AUTO_ROLLBACK` для доски,
  `MYRMIDON_BOT_CANARY_AUTO_ROLLBACK` для парка; хостовая сторона переключателя
  доски — `AUTO_ROLLBACK` в `deploy.env`, обе стороны должны совпадать.
  Автообновление без подтверждения остаётся выключенным (`MYRMIDON_DEPLOY_AUTO_UPDATE=0`);
  см. [SETTINGS.md](SETTINGS.ru.md) (#261).
- Прогоны: запуск из очереди, повторно входящий в start-lock агента, больше не
  ждёт сам себя. Тело блокировки теперь выполняется в кадре async-контекста на
  агента, поэтому вложенный запуск из той же цепочки пропускает ожидание и больше
  не стоит по `AGENT_START_LOCK_STALE_MS` (30 с) на каждой отмене, продвигающей
  очередь (#174).

- RELEASE-GATE: доска и компоненты релиза выкатываются вместе, и это держит сам deploy.sh.
  Он резолвит дайджесты dockergate и fleetd того же релиза (тег `myr-vX.Y.Z` из version-метки
  образа доски, иначе тег `sha-<короткий>` коммита) и отказывает релизу без компонентов в
  реестре ДО каких-либо изменений — инцидент 01.10 выкатил одну доску, а производственный
  dockergate отвергал новый ключ `maxConcurrentRuns` маркера, и все apply ботов падали ~40
  минут. Каждый компонент теперь катится тем же прогоном со своей health-пробой
  (`MYR_<COMPONENT>_HEALTH_URL`), а постдеплойный smoke (`bot-apply-smoke.sh`) ждёт
  повторного применения хотя бы одного ботового контейнера, иначе выкат сообщает DEGRADED с
  командами отката (`rollback-component.sh` на компонент). CI получил контракт applied-маркера:
  маркеры `serializeAppliedMarker()` эмитятся из серверного кода каждого коммита и прогоняются
  через валидатор dockergate — маркер, который валидатор отверг бы, краснит CI до сборки образов (#276).
- AUTO-RESUME: доска сама возобновляет агента, оставшегося в `error` после
  неудачного прогона, — проход на тике планировщика с бэкоффом 1, 5 и 15 минут,
  переиспользующий цепочку побудки выхода из паузы, поэтому поднятый агент
  заодно будит работу, на которой застрял. После `MYRMIDON_AUTO_RESUME_MAX_ATTEMPTS`
  (по умолчанию 3) неудачных возобновлений доска останавливается и эскалирует
  карточку агента `agent_error_alert` на столе внимания до severity `critical`;
  возобновление оператором взводит счётчик заново. Состояние живёт в
  `agents.metadata.myrmidon_auto_resume` (миграций нет), каждое действие пишет
  строку журнала активности (`agent.auto_resume_issued` /
  `agent.auto_resume_exhausted`). Настройки: `MYRMIDON_AUTO_RESUME_*` в
  [SETTINGS.ru.md](SETTINGS.ru.md); руководство:
  [guides/auto-resume.ru.md](guides/auto-resume.ru.md) (#272).

### Telegram

- Статус прогона в Telegram-личке и инлайн-деление (U1). В мостовой
  Telegram-личке (`MYRMIDON_TELEGRAM_DM_CONVERSATIONS`) прогон теперь может
  показывать статус «сейчас делаю» одним редактируемым сообщением вместо
  молчания по вехам: статус публикуется один раз, когда прогон встаёт в
  очередь, то же сообщение провайдера редактируется на месте при смене фазы,
  а финальный ответ прогона его заменяет — вехи сбоя, ожидания
  администратора и завершения по-прежнему публикуются, терминальная веха
  `/stop` остаётся подавленной. Отдельно: длинный структурированный
  Markdown-ответ, который вендор шлёт одним `.md`-вложением, теперь может
  делиться прямо в чате на упорядоченные части по границам абзацев/строк/слов.
  Оба поведения опциональны и по умолчанию выключены:
  `MYRMIDON_TELEGRAM_DM_STATUS` и `MYRMIDON_TELEGRAM_SPLIT_MAX_PARTS`
  (документ, требующий больше частей, чем порог, остаётся вложением); см.
  [SETTINGS.ru.md](SETTINGS.ru.md) и руководство
  [guides/telegram-dm-status.ru.md](guides/telegram-dm-status.ru.md) (#267, #313).

### Контейнеры ботов

- dockergate принимает маркер применённого профиля с необязательным ключом
  `maxConcurrentRuns` (целое 1–50), который доска записывает со времён CONCURRENCY-SYNC.
  dockergate версии 1.3.0 требовал ровно три ключа и отклонял каждое применение профиля

  весь парк. Выкатывайте образ dockergate этого выпуска вместе с доской; подменённый
  вручную образ dockergate больше не нужен. См. [dockergate.md](dockergate.ru.md#маркер-применённого-профиля)

  против шлюза канарейки, и только затем идут волны по
  `MYRMIDON_BOT_CANARY_WAVE_SIZE` (по умолчанию 4) ботов, по одному за раз. Провал
  канарейки останавливает выкат, не трогая остальной парк; выкат можно прервать.
  Маршруты: `GET/POST /api/myrmidon/bot-canary[/preview|/:id/abort]` (чтение — доска;
  запись — администратор инстанса). По умолчанию всё выключено (`MYRMIDON_BOT_CANARY`).

- Настройки бота разрешаются по хосту парка: запись `MYRMIDON_FLEET_HOSTS` может
  переопределить адрес hindsight, базовый адрес LLM-шлюза, дополнительное имя хоста
  доски, корень томов, сеть ботов и список разрешённых образов для ботов, размещённых на
  этом хосте; поле, отсутствующее в записи, берёт значение инстанса. См.
  [SETTINGS.md](SETTINGS.ru.md) (#225).
- Новое руководство: [guides/bot-container-card.md](guides/bot-container-card.ru.md) —
