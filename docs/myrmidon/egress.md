# egress: выход ботов наружу через прокси — журнал и белые списки

Пункты 4 и 5 выпуска 1.3: контейнер бота не выходит наружу напрямую, весь его исходящий трафик
проходит через прокси флота. Сначала — **«только журнал»** (EGRESS-A): прокси ничего не блокирует,
он записывает, куда бот ходил; по журналу собирается опись реальных направлений каждого проекта.
Затем — **белые списки и блокировка по проектам** (EGRESS-B): списки правятся в карточке проекта и
в карточке бота, а проект, чей список сверен с журналом, прокси начинает **отказывать** всему, чего
в списках нет; отказ виден и боту (403), и в интерфейсе.

Две половины делают это вместе:

```
бот ──▶ egress-proxy:3128 ──▶ наружу
        (журнал направлений)     сеть `egress` (обычный bridge)
   ▲
   │ сеть `myrmidon-bots` (docker internal: наружу маршрута нет)
```

- **Сеть.** Сеть ботов создаётся без маршрута наружу (`internal: true`) — это делает развёртывание
  на хосте, репозиторий сеть не создаёт. Контейнер, который проигнорировал прокси, не «блокируется»:
  ему просто некуда идти.
- **Профиль.** Правка шаблона контейнера бота
  (`server/src/myrmidon/bot-containers/egress.ts`): при включённом режиме драйвер дописывает в
  `hermes/.env` бота `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` и `NODE_USE_ENV_PROXY=1`.
  Пользователем прокси в адресе стоит ключ самого бота (`http://<botKey>:egress@egress-proxy:3128`) —
  по нему прокси и называет бота в журнале. Пароль не проверяется: «только журнал» не пускает по
  учётным данным, значение там только для того, чтобы адрес понимали все клиенты.

Служба — `tools/egress-proxy/`, образ собирает workflow службы
(`tools/egress-proxy/ci/myrmidon-egress-proxy.yml`; его кладут в `.github/workflows/` —
пуш файлов туда требует у токена отдельного права `workflow`, которого у инженерного нет),
`ghcr.io/itkadr-git/myrmidon-egress-proxy`, на бою только по digest из CI. Реестр переменных — ниже,
образец развёртывания — `tools/egress-proxy/compose.example.yml`.

## Что делает прокси

- **HTTP** — запрос в абсолютной форме (`GET http://хост/путь`), как его отправляет клиент,
  прочитавший `HTTP_PROXY`; прокси передаёт его дальше и возвращает ответ.
- **HTTPS** — `CONNECT хост:порт`, дальше туннель. TLS прокси не расшифровывает: он видит **назначение**
  (хост и порт), а не содержимое. Нашего сертификата внутри бота нет.
- **Отказ — только по списку проекта.** В режиме службы `log` не отказывается никому (EGRESS-A).
  В режиме `enforce` проект, чья политика говорит `block`, получает 403 на направление, которого нет
  ни в списке проекта, ни в списке самого бота; отказ записывается в журнал с исходом `blocked`.
  Недоступное, но разрешённое назначение попадает в журнал с исходом и отдаётся клиенту как 502.
- **Журнал** — по строке JSON на назначение в `docker logs`:

```json
{"ts":"2026-09-30T12:00:00Z","bot":"example-bot","project":"example-project","method":"CONNECT","scheme":"https","destination":"api.example.com","port":443,"result":"ok"}
```

Учётных данных в строке нет: пользователь прокси берётся из заголовка, сам заголовок отбрасывается
и дальше не передаётся. Запросы к самому прокси (относительный путь) — это проверка здоровья
(`GET /healthz`), в журнал они не пишутся.

Опись направлений за период наблюдения (какой проект куда реально ходит) читается из журнала:

```sh
docker compose logs egress-proxy | grep -o '^{.*}$' \
  | jq -r '[.bot, .project, .destination, (.port|tostring)] | @tsv' | sort -u
```

## Как включить

1. Собрать образ из CI (`myrmidon-egress-proxy`), взять digest из итога job.
2. На хосте: `./config/bots.json` — ключ бота → проект (образец `config.example.json`). Бот, которого
   в файле нет, всё равно обслуживается: его направления пишутся без проекта. Это и есть тот пробел,
   который закрывает период наблюдения.
3. Сеть ботов — без маршрута наружу (`internal: true`), сеть прокси — обычный bridge.
4. `docker compose -f tools/egress-proxy/compose.example.yml up -d`.
5. На инстансе: `MYRMIDON_BOT_EGRESS_MODE=log` и `MYRMIDON_BOT_EGRESS_PROXY=http://egress-proxy:3128`.
   Настройки читаются при каждой сборке профиля, перезапуск доски не нужен: боты перезапускаются
   сами, потому что `.env` — это изменение класса «restart».
6. Выключить: `MYRMIDON_BOT_EGRESS_MODE=off` (или снять переменную) и снова собрать профили.

## Белые списки и блокировка по проектам (EGRESS-B)

Журнал отвечает на вопрос «куда боты ходят»; списки — на вопрос «куда им можно». Правятся они в двух
местах доски:

- **страница проекта → раздел «Egress»**: список направлений проекта, отметка «сверено с журналом»
  и переключатель «блокировка»;
- **карточка бота → раздел «Egress»**: проект, к которому бот относится в журнале, и свои
  направления бота (они **добавляются** к списку проекта, а не заменяют его).

Правила, за которыми следит сервер:

- направление — это `host` или `host:port` (у URL схема отбрасывается); `host` без порта означает
  «любой порт на этом хосте». Шаблонов (`*`) нет: ни один клиент флота их не понимает;
- проект может быть переведён в `block` только когда список **сверен с описью** наблюдения и
  непустой. Это риск плана, ставший правилом: блокировка без описи ломает работу. Строка, у которой
  отметку сняли после сохранения, публикуется как `log` — прокси не начинает отказывать
  задним числом.

Документ, который читает прокси, отдаёт доска:

```
GET /api/myrmidon/bot-egress/policy   Authorization: Bearer $MYRMIDON_BOT_EGRESS_TOKEN
```

Прокси забирает его по `EGRESS_PROXY_POLICY_URL` раз в `EGRESS_PROXY_POLICY_REFRESH_SEC` секунд и
держит **последний удачный** документ: падение доски или сети ботов не должно превращать блокирующие
проекты в «политики нет». Документ, который нельзя прочитать, при старте останавливает службу, а не
подменяется пустым.

Отказы. Прокси пишет каждое отклонённое направление в журнал строкой с `result: "blocked"` и держит
последние 200 в памяти (`GET /refusals`); доска читает их по `MYRMIDON_BOT_EGRESS_REFUSALS_URL` и
показывает в разделе «Egress» проекта. Долговременная запись — журнал (`docker logs`), лента — лишь
хвост для интерфейса.

Откат. Три способа, от узкого к широкому: вернуть проект в `log` (переключатель), снять отметку
«сверено» (то же самое), или перевести службу целиком в `log` (`EGRESS_PROXY_MODE`) — тогда ничего не
отказывает никому, и всё снова только записывается.

**Начальные списки.** Первый выпуск пункта едет **без списков**: опись направлений собирается за
период наблюдения на стенде (её механику даёт EGRESS-A), и до неё ни один проект не сверен. Поэтому
блокировка нигде не включена, а направление вписывается в проект, только когда его видно в журнале.

## Переменные

Переменные инстанса (реестр — `SETTINGS.md`, раздел «Контейнеры ботов»):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `MYRMIDON_BOT_EGRESS_MODE` | `off` | `off` — как раньше, бот не получает переменных прокси; `log` — бот получает адрес прокси, прокси пишет журнал. Всё, кроме `off` и `log`, — ошибка, профиль не собирается (опечатка не должна выглядеть как «оставили как было») |
| `MYRMIDON_BOT_EGRESS_PROXY` | — | Адрес прокси, как его видит контейнер (`http://egress-proxy:3128`). Обязателен при `log`, только `http://` и только URL: с `log` без адреса профиль не собирается |
| `MYRMIDON_BOT_EGRESS_NO_PROXY` | — | Дополнительные хосты через запятую, которые идут напрямую. К ним всегда добавляются `localhost`, `127.0.0.1`, `::1` и хост `MYRMIDON_BOT_BOARD_URL`: доска — тот адрес, куда бот ходит постоянно, и она на его же сети |
| `MYRMIDON_BOT_EGRESS_TOKEN` | — | Общий токен между доской и прокси (EGRESS-B): прокси предъявляет его, забирая список, а доска — читая ленту отказов. Не задан — доска списки никому не отдаёт (503) |
| `MYRMIDON_BOT_EGRESS_REFUSALS_URL` | — | Адрес прокси, как его видит доска (например `http://egress-proxy:3128`); доска читает по нему `/refusals` для раздела «Egress» проекта. Не задан — лента отвечает 503, списки работают |

Переменные службы (образ `tools/egress-proxy`):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `EGRESS_PROXY_MODE` | `log` | `log` — записывает всё и никому не отказывает; `enforce` — к решению добавляется политика проекта: проект в режиме `block` отказывает всему, чего нет в списках. Другое значение — отказ старта |
| `EGRESS_PROXY_PORT` | `3128` | Порт прослушивания |
| `EGRESS_PROXY_BIND` | `0.0.0.0` | Адрес прослушивания |
| `EGRESS_PROXY_BOTS_FILE` | — | JSON `{"bots": {"<ключ>": {"project": "<проект>"}}}`: чем прокси называет проект в журнале, если доска имени не дала |
| `EGRESS_PROXY_POLICY_URL` | — | Адрес документа политики на доске. Обязателен при `EGRESS_PROXY_MODE=enforce`, если не задан файл. Документ, который не читается при старте, останавливает службу; неудачный опрос потом оставляет последний удачный документ |
| `EGRESS_PROXY_POLICY_TOKEN` | — | Токен к `EGRESS_PROXY_POLICY_URL` (тот же, что `MYRMIDON_BOT_EGRESS_TOKEN` на доске) |
| `EGRESS_PROXY_POLICY_FILE` | — | Локальный файл политики вместо адреса: годится стенду без доски и тестам |
| `EGRESS_PROXY_POLICY_REFRESH_SEC` | `30` | Как часто перечитывается документ политики (1–3600) |
| `EGRESS_PROXY_CONNECT_TIMEOUT_SEC` | `30` | Таймаут соединения с назначением |

## Что проверить на стенде

Критерии приёмки пункта — живые, изнутри контейнера:

1. **Прямого выхода нет.** Изнутри контейнера бота запрос наружу мимо прокси должен не пройти
   (`curl --noproxy '*' -sS -m 5 https://example.com` → нет соединения), а через прокси — пройти.
   Смотреть надо именно изнутри: сеть ботов — часть развёртывания, и её флаг на хосте ни о чём не
   говорит.
2. **Весь исходящий трафик в журнале.** Прогон бота одного проекта целиком (побудка, обращение к
   модели, к доске, к общим MCP-серверам) и сверка: в журнале есть все внешние направления, а
   внутренние (доска, медиа, соседние боты) — либо в `NO_PROXY`, либо тоже видны.
3. **Работа ботов не нарушена.** Смоук-прогон по одному боту каждого проекта.
4. **Опись направлений** собирается из журнала за период наблюдения; без неё блокировку (EGRESS-B)
   не включать: план прямо отмечает риск «иначе блокировка сломает работу».
5. **Списки и блокировка (EGRESS-B).** В разделе «Egress» проекта вписать направления из описи,
   поставить отметку «сверено» и только потом включить блокировку. Проверить живьём: разрешённое
   направление проходит, запрещённое отклоняется (`curl` изнутри бота получает 403 от прокси), отказ
   появился в журнале строкой `result: "blocked"` и виден в разделе «Egress» проекта. Затем откат:
   выключить блокировку переключателем и убедиться, что то же направление снова проходит, а служба
   при `EGRESS_PROXY_MODE=log` не отказывает никому.

## Риски и известные пробелы

- **Клиент, не читающий переменные прокси, в журнал не попадёт.** В режиме «только журнал» это
  пробел в описи, а не отказ: он будет виден как «бот есть — направлений нет».
- **Node-инструменты бота** по умолчанию игнорируют `HTTP_PROXY`/`HTTPS_PROXY`; для них драйвер
  дописывает `NODE_USE_ENV_PROXY=1` (поддерживается Node 24, в образе бота он есть).
- **`NO_PROXY` не понимает шаблонов** у большинства клиентов: хост доски добавляется буквально,
  список дополнительных хостов — точный.
- **Прокси — единая точка отказа для всего флота ботов.** В режиме «только журнал» его падение
  означает «нет выхода»; поэтому запасной путь и доступность прокси — предмет проверки на стенде,
  а не то, что этот пункт уже решил.
