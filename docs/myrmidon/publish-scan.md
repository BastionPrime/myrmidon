# Публикация PR и задач через обёртку со сканером

Боты публикуют тексты PR и задач только через обёртку `scripts/myrmidon/publish-scan.mjs`.
gitleaks смотрит коммиты; текст описаний PR и задач остаётся без проверки — обёртка
закрывает этот пробел. Текст проходит те же два списка правил, что и диффы
(`scripts/myrmidon/scan-diff.mjs`):

- встроенные правила `scan-text.mjs`: секреты, частные адреса, пути к секретам;
- запрещённые шаблоны из `MYRMIDON_FORBIDDEN_PATTERNS` — наши хосты, имена, номера задач
  (формат и секрет — в [ci.md](ci.md), раздел «Внутренние адреса»).

См. также [plan-intake.md](plan-intake.md) и CONVENTIONS.md, раздел 9.

## Когда использовать

- бот публикует или обновляет описание PR (тело PR, комментарии);
- бот создаёт или обновляет текст задачи;
- бот постит отчёт, содержащий выдержки из логов или конфигов.

Прямая публикация текста без обёртки запрещена для ботов. Человек перед PR проходит
самопроверку по CONVENTIONS.md (раздел 9) — обёртка не отменяет её.

## Как использовать

```sh
# текст в файле:
node scripts/myrmidon/publish-scan.mjs --file pr-body.md
# или через stdin:
cat pr-body.md | node scripts/myrmidon/publish-scan.mjs
```

Запрещённые шаблоны берутся из переменной окружения `MYRMIDON_FORBIDDEN_PATTERNS` (по одному
регулярному выражению на строку, `#` — комментарий, без учёта регистра). Если переменная не
задана, обёртка печатает предупреждение (`::warning`), пропускает эту проверку и применяет
только встроенные правила.

- `exit 0` — публикация разрешена;
- `exit 1` — публикация запрещена: в тексте секрет, внутренний адрес или запрещённый шаблон;
- `exit 2` — ошибка чтения или аргументов (текст не прочитан, `--file` без пути, нет файла).
  Это тоже отказ: при ошибке чтения обёртка никогда не считает текст чистым.

В stdout печатается краткий отчёт: сколько строк отсканировано, сколько находок и
каких типов (`rule xN`). Значения находок и сами шаблоны не печатаются: запрещённый шаблон
называется по номеру строки в списке (`forbidden pattern #N`).

## Схема работы бота

1. Подготовить текст (тело PR или задачи) во временный файл.
2. Прогнать обёртку. `exit 0` — публиковать. `exit 1` — не публиковать: переписать
   текст, убрав секреты, внутренние адреса и имена (имя переменной без значения, номер
   строки, описание сбоя — см. [plan-intake.md](plan-intake.md), раздел 6), и
   прогнать снова. Повторный отказ — эскалация человеку.
3. После публикации текст считается проверенным; при редактировании — прогон заново.

## Что ищет сканер

Присваивания `password/passwd/secret/token/api_key`, заголовки приватных ключей,
префиксы токенов (`github_pat_`, `ghp_`/`gho_`/`ghs_`/`ghu_`/`ghr_`, `pcp_`, `sk-`; префикс `pcp_`
и `sk-` ищется только в начале слова, поэтому `task-assignment` не считается токеном), токены
Telegram-ботов, учётные данные в URL (`://user:password@`), частные адреса (`10/8`,
`172.16/12`, `192.168/16`, `100.64/10`), пути к секретам (`/etc/.../secret`, `~/.ssh/`;
в том числе в обратных кавычках и круглых скобках, как их пишут в markdown).
Список встроенных правил — в `scripts/myrmidon/scan-text.mjs`; запрещённые шаблоны — из
секрета репозитория, в открытом репозитории их нет.

## Автоматическая проверка в CI

Обёртка сама по себе работает, только если её вызвали. Чтобы описание PR не оставалось
непроверенным, у любого PR (от человека или бота) заголовок и тело проверяет workflow
[`myrmidon-pr-text.yml`](../../.github/workflows/myrmidon-pr-text.yml): job `PR text scan`,
события `opened`, `edited`, `reopened`, `synchronize`. Событие `edited` есть только здесь: правка
описания перезапускает этот лёгкий job, а не весь `myrmidon-ci`.

- заголовок и тело попадают в шаг только через переменные окружения, не через подстановку
  выражений в текст скрипта — иначе текст PR мог бы выполнить команду;
- секрет `MYRMIDON_FORBIDDEN_PATTERNS` передаётся в шаг так же, как в проверке диффов; в PR
  из чужого форка секретов нет, и проверка идёт по встроенным правилам с предупреждением;
- красный job означает отказ: поправить описание PR — правка сама запустит проверку заново.

Job отдельный, в обязательные проверки ruleset он не входит: если нужно сделать его
обязательным, это решение сопровождающего.

## Тесты

```sh
node --test scripts/myrmidon/publish-scan.test.mjs scripts/myrmidon/scan-text.test.mjs
```

Обёртка использует правила `scan-text.mjs`; тот же файл (и его тесты) использует проверка
текста плана (PLAN-INTAKE), поэтому в этой ветке они совпадают с веткой PLAN-INTAKE побайтно.
Правки правил вносятся в обе ветки одинаково.
