# Ротация и отзыв ключей по ролям (ROLE-SCOPED-TOKENS)

Runbook для оператора доски. Применим после выката релиза с скоупами ключей доски
(миграция 0282, enforcement в middleware). Правило выпуска: ротация ключей выполняется
только по явному слову оператора доски; доска запускается только из образа, собранного CI.

## 0. Что есть после выката

- У `board_api_keys` появилась колонка `scope_config` (jsonb). Виды скоупов:
  `full` / `read_only` / `ops` / `agents_manage` / `secrets_manage` / `release`.
- Ключи без скоупа (созданные до выката) и скоуп `full` сохраняют полный доступ —
  существующие CLI- и операторские потоки не ломаются.
- Enforcement действует только на ключи (источник аутентификации `board_key`):
  сессия UI, local-trusted и cloud-акторы не ограничиваются.
- Управление — UI: Settings → Instance settings → Board API keys (создание с выбором
  скоупа — токен показывается один раз; листинг со скоупом и последним использованием;
  отзыв), либо API: `GET/POST /api/board-api-keys`, `DELETE /api/board-api-keys/{keyId}`.

## 1. Ротация ключа доски одной роли (без остановки остальных)

Порядок («двойной ключ», нулевой простой):

1. Создать НОВЫЙ ключ роли с её скоупом (UI или `POST /api/board-api-keys` с
   `scope: {kind: ...}`). Токен сохраняется сразу — показывается один раз.
2. Положить новый токен держателю роли по существующему каналу доставки (карточка
   секрета на доске → профиль агента → рестарт шлюза — как при прошлых выдачах).
3. Проверить живым использованием, что новый ключ работает и скоуп держится:
   ожидаемое действие роли проходит, действие чужой области — 403
   `Board API key scope '<kind>' does not allow this action`.
4. Убедиться, что остальные роли работают (их ключи не менялись).
5. Отозвать СТАРЫЙ ключ роли (UI → Revoke, или `DELETE /api/board-api-keys/{keyId}`).
6. Проверить фактом: старый токен даёт 401, остальные роли работают.

Отзыв НЕ ломает остальные роли: ключи независимы, скоуп каждого проверяется отдельно,
`revokedAt` касается только своей строки `board_api_keys`.

## 2. Ротация GitHub PAT роли

1. Владелец аккаунта (itkadr-git / BastionPrime) минтит новый fine-grained PAT
   исключительно с правами матрицы этой роли (см. worklog задачи пункта 16: матрица
   «роль → права PAT → скоуп ключа доски»).
2. Обновить значение секрета в карточке на доске; доставить в профиль агента
   (канал тот же, что в п.1.2).
3. Проверить фактом: push/PR проходит от новой роли; у остальных ролей доступ прежний.
4. Отозвать старый PAT в настройках GitHub (Developer settings → Fine-grained tokens).
5. Проба независимости: после отзыва PAT роли X её профиль теряет доступ к GitHub,
   остальные профили продолжают работать.

## 3. Отзыв при компрометации (только одной роли)

- Ключ доски: немедленный Revoke в UI (шаг 1.5–1.6). Скоуп ограничивает ущерб до
  области роли (у `read_only` вообще нет мутаций).
- GitHub PAT: отзыв в GitHub + при необходимости force-push protection на ветки.
- Остальные роли НЕ трогаем: их токены и ключи не связаны с отозванным.

## 4. Связь с существующим окном ротации

Ключ `adm/paperclip-board-admin-key` (keyId fc8faab5) уже стоит в окне ротации ранбука
ключей доски (см. работу окна ротации 27.09). Ротация по ролям НЕ отменяет то окно, а
закрывает его предметно: вместо одного админ-ключа на всех — по ключу со скоупом на роль;
общий ключ отзывается последним, после пересадки всех держателей (см. п.1).

## 5. Признаки проблем

- 403 `Board API key scope ... does not allow this action` на легитимном действии роли —
  скоуп уже, чем её фактические потребности: проверить матрицу, перевыпустить ключ с
  нужным видом (ротация по п.1), сообщить команде для правки таксономии.
- После отзыва старого ключа роль молчит — проверить, что доставка нового токена дошла
  (env профиля) и шлюз перезапущен.
- GET-запросы идут от любого скоупа — это штатно (read-доступ не ограничивается).
