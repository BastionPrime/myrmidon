# Здоровье LLM-трейсинга: карточка статуса и сигнал оператору (TRACING-HEALTH)

> English version: [tracing-health.md](tracing-health.md)

LLM-трейсинг (LiteLLM → Langfuse v4 через OTLP) умеет ломаться молча: инцидент
02.10 тянулся днями — таблицы `traces` пусты по самой схеме v4, легаси-колбэк
жёг ~12 тыс. ошибок в час, а доска не показывала ничего. Проверка здоровья
(часть C, эндпоинт `GET /api/myrmidon/tracing/health`) делает состояние
конвейера вычислимым; это руководство — про две его поверхности на доске
(часть D): где каждая живёт и что значат её состояния.

Проверка выключена, пока не заданы настройки трейсинга
(`MYRMIDON_TRACING_CLICKHOUSE_*` + две настройки шлюза `MYRMIDON_LITELLM_*`);
переменные и семантика здоровья — в [../SETTINGS.ru.md](../SETTINGS.ru.md).
Обе поверхности ниже читают один и тот же закешированный отчёт, поэтому
всегда согласны между собой.

## Карточка статуса в настройках компании

**Настройки компании** (маршрут `/company/settings`) несут карточку
«LLM tracing» под секцией Server console. Она только читает: конвейер чинит
оператор (хранилище ClickHouse `events_core` инстанса Langfuse v4, колбэки
шлюза), доска лишь сообщает. Карточка берёт отчёт через react-query и
обновляется раз в минуту; ошибка запроса заменяет тело текстом ошибки.

Карточка показывает цветную точку с состоянием, строку причины, по одной
приглушённой строке на пробу и окно проверки:

| Состояние | Надпись на карточке | Что значит |
|---|---|---|
| `ok` | зелёная точка, `ok` | Шлюз обслуживал трафик в окне, события легли в ClickHouse, частота ошибок колбэка ~0 |
| `idle` | зелёная точка, `ok (idle)` | Шлюз не обслуживал трафика в окне — тихий период, не тревога |
| `degraded` | красная точка, `red` | Трейсинг потерян при живом трафике, коэффициент доставки ниже 0,5, в окне есть отказ легаси-инжестии или частота ошибок колбэка ≥ 0,02 |
| `unknown` | красная точка, `unknown` | Отказала проба: сама проверка не видит конвейер |
| не включено | серая точка, `not enabled` | Настройки трейсинга не заданы; эндпоинт отвечает 503 с `enabled: false` |

Строка причины — человеческое пояснение из отчёта (например «the gateway
served traffic but no tracing events landed in the window»). Строки улик —
`gateway requests in window`, `events in window`, `delivery ratio`,
`callback error rate`, `legacy rejections`; отказавшая проба показывает
`unknown` вместо числа. Нижняя строка — окно (например `window 15 min`) и
время `checked` последнего реального измерения.

## Сигнал оператору

Карточка помогает, только когда кто-то открыл страницу. Периодический проход
(`MYRMIDON_TRACING_SIGNAL_INTERVAL_SEC`, по умолчанию 300 с; выключен вместе
с самой проверкой) вычисляет тот же отчёт в процессе для каждой компании и
поднимает ОДНУ карточку внимания на столе оператора:

- `degraded` → важность `high`: трейсинг потерян при живом трафике;
- `unknown` → важность `medium`: сама проверка не видит;
- `ok` / `idle` → карточки нет. Тихое окно — не поломка.

Сигнал идёт роли оператора, никогда владельцу задачи: чинить конвейер
трейсинга — работа оператора, и инцидент 02.10 горел ровно потому, что у
того, чья это работа, не было поверхности, которая смотрит. Строка «почему
сейчас» называет, что проверять (ClickHouse `events_core` Langfuse и колбэки
шлюза при `degraded`; конфигурацию проб `MYRMIDON_TRACING_*` /
`MYRMIDON_LITELLM_*` при `unknown`).

Дедуп по состоянию: одна карточка (дедуп-ключ `tracing_health:llm-tracing`),
пока сбой держится, и она исчезает сама, как только отчёт становится `ok` или
`idle` — без бухгалтерии закрытий. Ручное закрытие тоже работает, пока
состояние держится.

## Журнал активности

Проход пишет одну строку журнала только на ПЕРЕХОД состояния (действие
`myrmidon.tracing.health_signal`, исполнитель `tracing_health_sweep`):
состояние, важность и причина — в деталях. Устойчивенно красный конвейер
журнал не засоряет — одна строка, когда покраснел, одна, когда восстановился.
