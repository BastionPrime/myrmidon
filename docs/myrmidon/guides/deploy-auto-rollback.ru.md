# Автооткат по здоровью после выката

> English version: [deploy-auto-rollback.md](deploy-auto-rollback.md)

Эта страница — руководство оператора по автооткату, который защищает каждый
выкат доски (релиз 1.4, трек R5-C). Когда проверка здоровья после смены образа
проваливается, доска не ждёт человека: хостовый исполнитель возвращает образ на
тот, что выкат запомнил до смены, проверяет, что прежний образ снова здоров, и
закрывает работу — всё без участия человека.

О самом выкате (digest, окно обслуживания, хостовый исполнитель) —
[../deploy.ru.md](../deploy.ru.md). Заметки об обновлении каждого релиза
повторяют короткую версию того же контракта.

## Когда срабатывает

Откат запускает ровно одно: **проверка здоровья после смены образа**. Выкат
сверяет версию и коммит из `/api/health` с метками образа; несовпадение,
недоступный health-эндпоинт или ошибка хостового исполнителя на этом шаге —
провал здоровья.

- при включённом откате (по умолчанию) провал здоровья переводит работу в
  `rolling_back` — сбой ещё не терминальный;
- при выключенном (`MYRMIDON_DEPLOY_AUTO_ROLLBACK=0` на доске И
  `AUTO_ROLLBACK=0` в `deploy.env` — обе стороны должны совпадать) провал
  здоровья завершает работу `failed_health`, окно обслуживания остаётся:
  откат — инструмент оператора, ручной контракт 1.3.x.

Всё до смены образа не затрагивается: отказанный digest (проверка CI-образа),
окно, которое не открылось, или таймаут шага завершают работу без отката —
ничего не переключали, восстанавливать нечего.

## Что делает работа

Сама доска docker не запускает. Она ведёт работу по статусам, а переключает
хостовый исполнитель (`scripts/myrmidon/deploy/deploy-from-job.sh`), записывая
фазы в `$STATE_DIR/job-<id>.json`:

| Шаг | Статус работы | Фаза отчёта | Что происходит |
| --- | --- | --- | --- |
| Здоровье провалено | `rolling_back` | `health-failed` (или исполнитель сразу переходит к `rolling-back`) | Причина записана в работу; окно остаётся — оно покрывает и переключение отката |
| Откат идёт | `rolling_back` | `rolling-back` | `rollback.sh` заново подтягивает и пересоздаёт сервис на запомненном прежнем образе (аварийный путь: CI-проверка цели отката только предупреждает) |
| Откат здоров | `auto_rolled_back` | `rolled-back` | Прежний образ прошёл собственную проверку здоровья; окно обслуживания снимается; доска снова работает — человек не участвовал |
| Откат провалился | `failed_rollback` | `rollback-failed` | Окно ОСТАЁТСЯ для оператора; работа хранит и причину выката, и причину отката |

Доска не доверяет одному отчёту исполнителя: работа закрывается успехом (или
откат закрывается) только когда собственный `/api/health` доски подтверждает
версию и коммит.

Весь путь идемпотентен и ведётся тиком сверки (`MYRMIDON_DEPLOY_TICK_SEC`,
по умолчанию 5 с). Тик, пропустивший промежуточные фазы (откат занимает секунды,
тик — 5 с), всё равно приходит к верному терминальному статусу по финальной фазе
отчёта.

## Куда записывается причина

- **Работа** — `failureReason` работы и журнал шагов хранят причину сбоя
  (например `host executor failed: health-failed — health did not match`);
  неудачный откат добавляет свою строку сверху. Видно в панели «Board update»
  настроек инстанса и в `GET /api/myrmidon/deploy-jobs` (история).
- **Журнал активности** — каждый переход пишет строку в `activity_log`
  (`myrmidon.deploy_jobs.rolling_back`, `...auto_rolled_back`,
  `...failed_rollback`) с digest, статусом и причиной в деталях.
- **Лог исполнителя** — `$STATE_DIR/job-<id>.log` на хосте содержит вывод
  `deploy.sh` и `rollback.sh`; детали `rollback-failed` ссылаются на него.

## Карточка владельцу

Работа `failed_rollback` держит окно обслуживания: инстанс на паузе, и оператор
— единственный, кто может действовать. Сама доска задачу владельцу не создаёт:
доска в обслуживании, её агенты на паузе, и задача с доски на паузе не будет
взята в работу. Что срабатывает вместо этого:

- баннер обслуживания наверху доски называет окно и его причину
  (`deploy <префикс digest>`), так что каждый участник доски видит, почему она
  на паузе;
- панель «Board update» показывает работу `failed_rollback`, её причину и
  терминальное состояние без кнопки abort;
- дневной дайджест в Telegram (если владелец его включил, см.
  [owner-telegram-cards.ru.md](owner-telegram-cards.ru.md)) перечисляет открытые
  элементы внимания, включая состояние обслуживания.

Если доска не встала даже на прежнем образе, порядок действий — скриптовый:
[../deploy.ru.md](../deploy.ru.md) («Откат», «Что проверить после выката») с
хоста.

## Настройки

| Настройка | По умолчанию | Смысл |
| --- | --- | --- |
| `MYRMIDON_DEPLOY_AUTO_ROLLBACK` (доска) | `1` (вкл) | Половина выключателя на доске; `0` возвращает ручной контракт |
| `AUTO_ROLLBACK` (deploy.env, хост) | `1` (вкл) | Половина на хосте; исполнитель запускает `rollback.sh` при провале здоровья, только когда обе стороны согласны |
| `MYRMIDON_DEPLOY_HEALTH_POLL_SEC` / `MYRMIDON_DEPLOY_HEALTH_TIMEOUT_SEC` | 5 с / 300 с | Окно проверки здоровья после смены |
| `MYRMIDON_DEPLOY_STEP_TIMEOUT_SEC` | 1800 с | Шаг, застрявший дольше, завершает работу — включая застрявший откат |

Обе половины выключателя читаются из окружения; это настройки старта доски и
хоста, а не меняемые в интерфейсе без перезапуска: стороны должны совпадать, и
доска не может записать `deploy.env` хоста. Полные строки:
[../SETTINGS.md](../SETTINGS.md).

Та же защита для парка ботов (канарейка и волны) — отдельный выключатель
`MYRMIDON_BOT_CANARY_AUTO_ROLLBACK`, см. заметки о канарейке ботов в
[../deploy.ru.md](../deploy.ru.md).
