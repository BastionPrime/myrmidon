# Эталоны и судья: путь оценки качества (1.6 EVALS-A)

> English version: [reference-task-evals.md](reference-task-evals.md)

Менять навык, модель или инструкции роли раньше было вслепую: нечем было
измерить, стала роль лучше или хуже, продвижение решали на глаз. Путь оценки
делает вопрос вычислимым: сеяный корпус нейтральных эталонных задач пилотной
роли, LLM-судья за LLM-шлюзом компании, скоры каждого прогона в базе и вердикт
«продвигать / подтвердить / регресс», где падение за порогом — не приговор,
пока подтверждающий прогон не повторил его.

Модуль живёт в `server/src/myrmidon/evals/` (путь 1.6 EVALS-A). Судья — один
вызов chat/completions на задачу, по умолчанию бесплатная модель DashScope
(правило волны 1.6: платные модели — забота deploy-репозитория). Судья сам
код не исполняет: для задач вида `code` CI pass rate приходит параметром
запроса и сворачивается в скор отдельной строкой, а не измеряется здесь.

Контур судья зеркалит [путь OCR](ocr.ru.md): адрес OpenAI-совместимого шлюза
плюс **имя** секрета компании с ключом — значение не появляется ни в
настройке, ни в логах, ни в журнале. Все настройки (`MYRMIDON_EVALS_*`) — в
[../SETTINGS.ru.md](../SETTINGS.ru.md). Пока контур не настроен, чтение
работает, а мутации отвечают `503` с именами недостающих настроек.

## API

API доски под `/api/myrmidon/companies/:companyId/evals`:

| Маршрут | Кто | Что делает |
|---|---|---|
| `GET /tasks?role` | чтение компании | Список эталонных задач роли (по умолчанию `engineer`): `slug`, `title`, `prompt`, `kind`, `weight`, `rubric` |
| `POST /seed` | только board | Сеет нейтральный корпус роли (по умолчанию `engineer`); идемпотентен по `(companyId, role, slug)` — повторный запуск обновляет prompt/rubric/weight на месте и никогда не дублирует строки. Ответ: `{role, inserted, updated}` |
| `POST /runs` | только board | Оценивает один прогон одного субъекта (ниже) |
| `POST /runs/:runId/confirm` | только board | Подтверждающий прогон для прогона, перешедшего порог |
| `POST /verdict` | только board | Ответ жизненному циклу: «продвигать ли кандидата» против его базлайна |
| `GET /runs?role&limit` | чтение компании | Список прогонов, новые сверху (`limit` по умолчанию 50) |
| `GET /runs/:runId` | чтение компании | Один прогон со всеми скорами |

Чтение требует доступа к компании; три мутации прогона требуют board-актора
(они тратят реальные вызовы шлюза — актор-агент получает `403`).

## Что такое прогон

Прогон оценивает один **субъект** — версию навыка, конфиг агента, черновик —
по каждой эталонной задаче роли:

1. **Сначала посейте корпус.** `POST /seed` пишет 24 нейтральные эталонные
   задачи пилотной роли `engineer` (задачи general и code, у каждой рубрика
   из двух критериев; веса 1 = рутина, 2 = значимая). Без посеянных задач
   прогон отвечает `502` с `no reference tasks for role "<role>"`.
2. **Соберите ответы.** Текст ответа субъекта на каждый slug приходит в
   объекте `answers` запроса `POST /runs`. Отсутствующий slug даёт ноль
   баллов — порог это поймает. Для задач вида `code` передайте `ciPassRate`
   (0–100): CI pass rate сворачивается в агрегат одной дополнительной строкой
   скора размером `ciPassRate`% баллов рубрики задачи, а не баллами судьи.
3. **Судья.** Один вызов chat/completions на задачу, температура 0, ответ —
   строгий JSON `{"criteria": {"<name>": <points>}}`. Судья выставляет от 0 до
   полного балла критерия за критерий. Непарсируемый ответ даёт ноль за
   задачу и флаг `parseError` — ненадёжный судья заметно портит прогон, а не
   выдумывает баллы.
4. **Агрегат.** На задачу: `rawScore` (начисленные баллы) × `weight`;
   `scorePercent` прогона — `totalScore / maxScore × 100` с одним знаком.
   Каждый прогон хранит полные скоры, ид модели судьи и CI pass rate в
   `myrmidon_eval_runs`.

Передайте `baselineRunId` в прогоне кандидата, чтобы сравнить его с
базлайн-прогоном той же роли (прогон без `baselineRunId` — базлайновый: без
сравнения, вердикт null).

## Вердикт: порог + повтор

Один плохой прогон — не вердикт. Порог по умолчанию — 5 процентных пунктов
(меняется на прогон через `thresholdDrop`, 0–100); `dropPercent` — базлайн
минус кандидат, округление до одного знака.

| Вердикт | Когда | Что значит |
|---|---|---|
| `promote` | нет базлайна или падение в пороге | кандидата можно продвигать |
| `confirm` | первый прогон перешёл порог | регрессия заподозрена — нужен подтверждающий прогон, прежде чем что-либо откатывать; ответ несёт `needsConfirm: true` |
| `regress` | подтверждающий прогон снова перешёл порог | регрессия подтверждена — не продвигать, откатить |
| `error` | у подтверждающего прогона пропал базлайн | сравнение невозможно |

Первый переход только *подозревает*: статус остаётся `confirm`, пока
`POST /runs/:runId/confirm` не повторит прогон того же субъекта. Вызов
подтверждения обязан снова нести ответы в теле (`answers`, slug задачи →
текст) — ответы с прогоном не хранятся, и без них маршрут отвечает `400`,
а не молча ставит нули. Если повтор уложился в порог — подозрение не
подтвердилось: сам подтверждающий прогон завершается `promote` с причиной
«подозренная регрессия не повторилась», и кандидата пробуют заново со свежим
прогоном.

Вердикт для жизненного цикла навыков возвращает `POST /verdict`
(`{role, subject, baselineRunId, thresholdDrop?}`): он берёт последний
завершённый *первый* прогон субъекта (подтверждающий прогон — повтор того же
кандидата, а не новый), его подтверждающий прогон, если был, и отвечает
`{promote, reason, scores}`. Это замороженный шейм, под который спроектирован
жизненный цикл навыков (`candidate → verified → deprecated` с откатом);
смерженный модуль цикла (1.6) пока не подключил его к доске, поэтому сегодня
шейм доступен через этот API.

## Журнал

Каждая мутация пишет одну строку активности от системного актора
`myrmidon-evals`: `evals.seeded` (роль, inserted/updated), `evals.run_completed`
(роль, субъект, вердикт, scorePercent, needsConfirm) и `evals.run_confirmed`
(роль, субъект, вердикт, scorePercent). Тексты ответов и сырые ответы судьи
не сохраняются вовсе — в `eval_runs.scores` лежат только начисленные баллы и агрегат; журнал их не видит.

## Экспорт в Langfuse (необязательный, по умолчанию выключен)

Скоры всегда пишутся локально в `myrmidon_eval_runs`. Задайте
`MYRMIDON_EVALS_LANGFUSE=true` плюс базовый URL ингестии Langfuse и публичный
ключ, чтобы дополнительно экспортировать агрегат каждого прогона: один POST
на прогон с событием `trace-create` (`eval-run:<role>`) и событием
`score-create` (`eval-score-percent`, вердикт в комментарии). Неудача экспорта
никогда не валит прогон — Langfuse это наблюдаемость, а не гейт.
