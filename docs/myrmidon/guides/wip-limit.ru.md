# Лимит WIP: лимит задач в работе на агента

> English version: [wip-limit.md](wip-limit.md)

**Лимит WIP** ограничивает, сколько задач один агент может держать в полёте
одновременно — `in_progress` плюс `in_review`. Фича едет двумя частями, обе
слиты: сервер (часть A) хранит настройки, считает живой статус и поднимает
сигнал о превышении; интерфейс (часть B, PR #415) — это экран настроек и
бейдж агента.

Экран настроек живёт в настройках компании → **WIP limit** (маршрут
`/company/settings/wip-limit`, пункт в сайдбаре после **Autonomy**). Живая
загрузка видна ещё в трёх местах: бейдж `wip/limit` на каждой строке
страницы агентов (список и орг-вид), карточка в ленте внимания на каждого
агента сверх лимита и system-notice-комментарий в задаче агента.

## Что входит в WIP и что делает лимит

`wip = inProgress + inReview` — видимые задачи агента в полёте, посчитанные
на лету из строк задач доски. Агент сверх лимита помечается для надзора;
прогон в полёте лимит никогда не прерывает, и ни один гейт не отказывает
задаче агенту сверх лимита — лимит это сигнал внимания, не блокировка.

Лимит `null` (отсутствует) означает **только подсчёт**: эндпоинт статуса
продолжает отвечать, бейдж всё ещё показывается, но ни карточки внимания,
ни комментария для этого агента никогда не создаётся. Компания вообще без
лимита гоняет всю фичу в режиме подсчёта — даже периодический sweep
останавливается до первого запроса.

## Лид-правило

Агент, на которого кто-то ссылается в `reportsTo`, — **лид**: его лимит
реализации 0 по определению, потому что лид надзирает и принимает работу,
а не доставляет. Лид с любой задачей в работе или на ревью сверх лимита по
определению — карточка внимания и system-notice говорят об этом лидской
формулировкой вместо цитирования числа. Поле `limit` всё равно показывает
значение настроек; только проверка превышения использует 0.

## Экран настроек

Читать настройки может любой участник компании; пишет instance-админ.

Два элемента управления:

- **Лимит по умолчанию на агента** — одно поле. Действует для всех агентов
  без собственного значения. **Пусто — только подсчёт** (плейсхолдер
  «Без лимита»).
- **Лимиты по агентам** — строка таблицы на каждого агента компании,
  отсортированы по имени: имя агента, его живая загрузка (только чтение) и
  поле **Лимит**. Пустая строка (плейсхолдер «по умолчанию») следует
  умолчанию; введённое число переопределяет лимит только для этого агента.

Допустимые значения: целое число от `1` до `100` в интерфейсе; сервер
принимает `0..100` (хранимый `0` считается жёстким нулём — агент хоть с
одной задачей в полёте уже сверх лимита). Всё остальное отклоняется с
сообщением под полем, а кнопка **Сохранить лимит WIP** остаётся
неактивной, пока все поля не станут корректны.

Колонка живой загрузки («Сейчас в работе») читает статус-энпоинт и на этом
экране не редактируется. Когда лимит задан, строка показывает полную
арифметику — `in progress + in review = wip/limit`,
например `2+1 = 3/4`; у
агента сверх лимита рядом с загрузкой появляется пометка «Сверх лимита», а
вся ячейка краснеет. Когда лимит выключен, колонка показывает голое число
`wip` приглушённым серым. Агент без записи в статусе (нет в ответе)
показывает прочерк.

**Сохранить лимит WIP** отправляет один PUT со всей строкой настроек.
Сохранение с очищенным полем агента удаляет переопределение этого агента из
хранимой строки — агент возвращается к умолчанию. Сохранение также
обновляет живую загрузку и на этом экране, и в списке агентов.

Обработка состояний: без выбранной компании экран сообщает об этом и не
делает запросов; пока настройки грузятся — «Загрузка настроек лимита
WIP...»; упавший GET или PUT настроек показывает сообщение об ошибке в
красной рамке на экране; компания без агентов показывает «В этой компании
пока нет агентов.» вместо таблицы.

## Бейдж в списке агентов

Каждая строка страницы агентов (и в списке, и в орг-виде) может нести
маленькую «пилюлю» рядом с индикатором живого прогона:

- при заданном лимите: `wip/limit` (например, `4/6`);
- сверх лимита: тот же текст красным с точкой, тултип «Over the WIP limit»;
- при выключенном лимите: только голое число `wip` (без знаменателя),
  тултип «Tasks in work (in progress + in review)»;
- бейджа нет вовсе, когда в ответе статуса нет записи для агента.

Бейдж только читает; сам лимит редактируется на экране лимита WIP.

## Сигнал о превышении

Две поверхности несут один и тот же факт превышения:

- **Лента внимания** (source kind `wip_limit`, важность `low`; `medium` для
  лид-правила) держит по карточке на каждого агента сверх лимита с
  заголовком «<agent> is over its WIP limit» (или «…is a lead holding
  implementation work») и двумя действиями: **Inspect** и **Dismiss**. Лента
  пересчитывается при каждом чтении — карточка существует ровно пока
  держится состояние и исчезает в момент, когда счётчик вернулся в лимит;
  ничего для неё не сохраняется.
- **System-notice-комментарий** в самую свежую задачу агента в работе, с
  заголовком «WIP limit exceeded», пишется не чаще раза на агента за
  UTC-день — дедуп-ключ `wip-limit:<agentId>:<utc-day>` лежит в метаданных
  комментария. Комментарий называет счётчик, лимит (или лид-правило) и
  выход: завершить или передать задачи, пока счётчик не вернётся в лимит;
  лиду сказано передать задачу реализации инженеру и оставить тикет на
  ревью и приёмку.

Периодическая проверка, пишущая эти комментарии, работает на планировщике
heartbeat с интервалом модуля **300 с** (проход при ещё идущем предыдущем
пропускается, а не ставится в очередь). Sweep сначала читает настройки:
нигде не заданный лимит означает, что проход останавливается до любого
запроса — в режиме подсчёта фича никогда не сигналит.

## Поверхность API

Маршруты — company-scoped под `/api/myrmidon`:

| Маршрут | Назначение | Доступ | Тело / ответ |
|---|---|---|---|
| `GET /myrmidon/companies/:companyId/wip-limit/settings` | прочитать строку настроек | любой участник компании | `{ defaultLimit: number \| null, perAgent: Record<agentId, number \| null> }` |
| `PUT /myrmidon/companies/:companyId/wip-limit/settings` | записать строку настроек | instance-админ | тот же вид |
| `GET /myrmidon/companies/:companyId/wip-limit/status` | живая загрузка на агента | любой участник компании | `[{ agentId, inProgress, inReview, wip, limit, overLimit, leadRule }]` |

Настройки хранятся на инстанс в `instance_settings.general.wipLimit` —
переменных окружения нет. Отсутствующая или нечитаемая строка
нормализуется в умолчание «только подсчёт» (`defaultLimit: null`), так что
ручная правка не может примениться наполовину. `null` означает «без
лимита»; отсутствие ключа в `perAgent` следует умолчанию, а явный `null` в
`perAgent` — «только подсчёт» для этого одного агента.

## Вопросы оператора

**Прерывает ли лимит прогон в полёте или блокирует новые задачи?** Нет.
Лимит — сигнал для надзора: бейдж, карточка внимания и дневной комментарий
показывают состояние превышения; ничто не гейтит следующую задачу и ничто
не останавливает идущий прогон.

**Как выключить фичу?** Очистите поле умолчания на экране лимита WIP (и
уберите заданные значения по агентам). Без заданного лимита статус
продолжает считать, бейдж продолжает показываться, а ни item внимания, ни
комментарий никогда не создаются.

**Почему агент с лимитом 4 помечен при трёх задачах?** Проверьте, не лид
ли он — у агента с прямыми подчинёнными лимит реализации 0, так что любая
задача в полёте его помечает. Формулировка карточки внимания называет
лид-правило, когда причина в нём.

**Комментарий повторяется каждый день — как остановить?** Комментарий
повторяется не чаще раза на агента за UTC-день, пока держится состояние.
Он останавливается в момент, когда счётчик агента вернулся в лимит (или
лимит убран), а **Dismiss** на карточке внимания прячет саму карточку, не
трогая счётчик.
