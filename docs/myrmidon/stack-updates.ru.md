# Обновления стека

> English version: [stack-updates.md](stack-updates.md)

Цикл обновлений стека — это то, как доска следит за релизами всех компонентов, из которых
состоит развёртывание: сама доска, её вендорский апстрим, общие сервисы вокруг, — и
превращает увиденное в план, с которым можно работать. Один закэшированный документ держит
всю картину: нашу сторону (что реально запущено у нас), сторону автора (что он выпустил),
сравнение между ними и вердикт по переносимым нами патчам. Операторские поверхности —
экран «Стек» (Company → Stack), плановая сверка релизов и черновик задачи, планирующий
обновление.

Поещёчное, покнопочное описание экрана «Стек» — в
[guides/stack-registry.ru.md](guides/stack-registry.ru.md); этот документ — про цикл
вокруг него: откуда берётся каждое число, как устроено сравнение, что значит вердикт
«патч закрыт» и что происходит, когда сети нет.

## Две стороны таблицы

### «Наше»: что реально запущено у нас

Локальная сторона каждого компонента заполняется refresh-ом
(`POST /api/myrmidon/stack/refresh` или кнопка *Refresh data*, instance admin). Что
записывает refresh, зависит от пробы компонента:

- `health-commit` (сама доска): коммит сборки из того же снимка информации о сервере,
  который отдаёт `/api/health`, — одна правда о версии доски. Если git-метаданные
  недоступны, компонент — честное `unknown`
  (`board build commit unavailable (<причина>)`).
- `docker-image`: инспекция образа через unix-сокет Docker (путь в
  [`MYRMIDON_STACK_DOCKER_SOCKET`](SETTINGS.ru.md)); первый repo-тег становится версией,
  первый digest — дайджестом, место запуска записывается. Отсутствующий на хосте образ —
  `unknown` (`image not present on the Docker host reachable from the board`), а не сбой.
- `container-labels`, `env`, `manual`, `none`: записываются как `unknown` с фикс-причиной
  (`no matching container labels found`, `no version override configured`,
  `managed by the operator; no automatic probe`, `not visible from the board server
  process`) — локальное значение такого компонента знает оператор.

### «У автора»: что выпустил автор

Сторона автора заполняется сверкой релизов (`POST /api/myrmidon/stack/check`, кнопка
*Check releases* или плановый проход). Она покрывает компоненты с источником релиза
`github-releases` или `github-tags`; источники `registry`, `package` и `manual` остаются
`unknown` — сверка их не читает. Сверка анонимно, без токенов читает публичный список
релизов или тегов GitHub (30 записей на страницу, таймаут 10 секунд) и записывает:

- последний релиз автора (самую свежую запись ленты);
- на сколько релизов мы отстаём — считается, только если наша версия встречается в ленте;
  неизвестная или не совпавшая локальная версия даёт честное `unknown`, а не догадку;
- заметные строки заметок релиза (ниже).

Refresh никогда не затирает сторону автора: состояние сверки переносится по имени
компонента, поэтому перечитывание локального состояния после выката сохраняет последнее
сравнение релизов.

## Сравнение: отставание и заметные строки

### Отставание

`Behind` — число релизов автора между нашим и последним. Оно считается, только если
рабочая версия совпала с записью ленты релизов; версия вне ленты (сборка форка,
компонент только с дайджестом, версия от оператора) читается как `unknown`. Компонент с
`Behind` ≥ 1 считается отстающим: он поднимается наверх экрана и получает кнопку
*Schedule update*.

### Заметные строки

Сверка релизов хранит строки заметок релиза, в которых упомянуты security, уязвимости,
CVE, breaking changes или deprecations: пять самых свежих, каждая обрезана, с пометкой,
когда выжимка была обрезана. Пропускаются строки, а не заметка целиком: обычный релиз с
одной security-строкой всё равно поднимет её. Выжимка с хоть одной security-строкой
помечается: на экране — иконкой щита, на карточке внимания — высокой критичностью.

## Вердикт «патч закрыт»

Поверх некоторых компонентов апстрима мы несём дельты. Каждая записанная дельта несёт
версию, на которой мы её держим, и коммиты автора, которые её закрывают (список
`fixCommits`, засеян в реестре). На каждой сверке каждая дельта оценивается по диапазону
между нашей версией и последним релизом автора через GitHub compare API:

- `closed` — диапазон сравнения уже содержит закрывающий коммит: дельту можно снять при
  следующем обновлении;
- `open` — закрывающего коммита в диапазоне ещё нет: дельту придётся нести дальше или
  перебазировать;
- `unknown` — вердикт не вычислен: релиз автора ещё неизвестен, наша версия неизвестна,
  закрывающий коммит не записан или диапазон сравнения недоступен (404 или HTTP-ошибка
  compare API).

Общий вердикт по компоненту — агрегат: все дельты закрыты → `closed`; есть неизвестная
дельта → `unknown`; иначе `open`. Вердикт, его причину и построчное состояние дельт видно
в колонке *Patches* экрана, и они копируются в план обновления по умолчанию — чтобы
планирующий обновление точно знал, какие дельты перепроверить.

## Плановая сверка и ручная проверка

У сверки релизов два триггера с одним и тем же кодом:

- **Плановый проход** за [`MYRMIDON_STACK_CHECK_INTERVAL_SEC`](SETTINGS.ru.md). По
  умолчанию выключен: не задано, пусто, `0`, отрицательное или не число — всё значит
  «выключено», доска ходит в сеть, только когда оператор задал интервал. Осмысленный
  интервал меньше 60 секунд поднимается до 60 (источники релизов не долбим). Проход
  запускает одну сверку сразу на старте, затем по интервалу; наложившийся проход
  пропускается, неудачный — пишется в журнал и повторится на следующем тике.
- **Ручная проверка** — `POST /api/myrmidon/stack/check` (instance admin) или кнопка
  *Check releases*: то же сравнение по требованию, свежий документ вернётся в ответе.

## Что поднимает отстающий компонент

Каждый компонент, который сверка посчитала отстающим (`Behind` ≥ 1) или у которого после
предыдущей сверки появился новый последний релиз, всплывает на столе оператора
(«Ждёт меня») карточкой `stack_update`: компонент, последний релиз, наша версия,
отставание, вердикт по патчам и выжимка заметок релиза (обрезана). Критичность высокая,
когда в выжимке есть security-строки, иначе средняя. Карточка дедуплицируется ключом
`stack:<компонент>:<последний релиз>` — сверка без смены последнего релиза новую
карточку не поднимает — и не ссылается на экран «Стек» (у субъекта карточки нет `href`);
экран и карточка читают один и тот же закэшированный документ.

## Планирование обновления

Отстающая строка экрана несёт кнопку *Schedule update*. Диалог открывается с планом по
умолчанию — версии (наша, последняя, отставание, источник релиза), вердикт по патчам с
состоянием каждой дельты, заметные строки автора, порядок «канарейка, затем бой» и шаг
отката, — и заголовок, и план редактируются. *Create draft task* создаёт **черновик
задачи в backlog без назначения** через обычный маршрут создания задач; с экрана ничего
не выкатывается и никого не назначается. Черновик становится обновлением, когда его
кто-то возьмёт, спланирует и прогонит обычный выкат ([deploy.ru.md](deploy.ru.md)).

## Настройки

Обе переменные, их значения по умолчанию и поведение при сбоях — в
[SETTINGS.ru.md](SETTINGS.ru.md):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `MYRMIDON_STACK_DOCKER_SOCKET` | `/var/run/docker.sock` | Unix-сокет Docker для локальных проб образов; читается при каждом refresh, перезапуск не нужен |
| `MYRMIDON_STACK_CHECK_INTERVAL_SEC` | не задана (выключено) | Интервал плановой сверки релизов; выключена, пока не задана, минимум 60 с |

## Когда сети нет

Оба пишущих маршрута сохраняют прежний кэш при сбое:

- **транспортный** сбой (нет сети, DNS, таймаут) во время сверки проваливает весь запрос
  с **503** — прежний кэш цел и читаем;
- **HTTP-ошибка** одного источника релизов (репозиторий удалён, rate limit) — обычные
  данные: компонент записывается `unknown` со статусом (`github 403`), остальная сверка
  проходит;
- сломанная проба Docker при refresh отвечает **503** так же — последний хороший документ
  выживает, экран показывает ошибку на месте, не теряя таблицу.

Сетевой сбой никогда не роняет доску: чтение продолжает отдавать последнее
закэшированное состояние, а следующая успешная сверка или refresh приведёт документ в
актуальное состояние.

## Где живёт код

- `server/src/myrmidon/stack-registry/` — реестр: сид и модель (`domain.ts`), локальные
  пробы (`collector.ts`), сверка релизов (`check.ts`, `releases.ts`), карточки внимания
  (`attention.ts`), настройки (`settings.ts`), маршруты (`routes.ts`), кэш (`store.ts`);
- `ui/src/components/myrmidon/stack/` — экран «Стек» и его presentation-хелперы;
- маршруты подключены в `server/src/app.ts` (маркер `myrmidon(SUA)`), плановый проход —
  в `server/src/index.ts` (маркер `myrmidon(SUB)`), экран — в `ui/src/App.tsx`
  (маркер `myrmidon(SUC)`, маршрут `/stack`);
- API и хранилище (ключ `myrmidonStack` в `instance_settings.general`) описаны в
  [guides/stack-registry.ru.md](guides/stack-registry.ru.md).
