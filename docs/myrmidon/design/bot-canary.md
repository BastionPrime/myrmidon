# Bot image canary (R5-B): design and API contract

Редакция 01.10.2026, трек 5, R5-B (пункт 9 выпуска 1.3). Продолжение R5-A
(`deploy-from-ui.md`): доска обновляется по digest из интерфейса, боты — волнами.

## 0. Коротко

- Новый образ ботов (`ghcr.io/itkadr-git/myrmidon-hermes`) раскатывается по
  digest: сначала канарейка — один контейнер, — затем волны по 4 бота.
- Канарейка живёт в драйвере контейнеров ботов (bot-containers), а не в fleetd:
  fleetd — исполнитель одного хоста и не знает флота. Драйвер уже умеет всё, что
  нужно (маршрутизация по хостам карточки, health-check образа, drain агента);
  канарейка — это порядок применения того же обновления.
- Волны идут только после успеха канарейки. Провал канарейки оставляет остальные
  контейнеры нетронутыми: доска просто не продолжает, бот канарейки остаётся в
  новом образе для разбора (откат — R5-C).
- Дымовой прогон канарейки: `POST /v1/runs` с коротким входом и подтверждённым
  ответом — реальный вызов шлюза hermes в новом образе, не только HEALTHCHECK.
- Всё выключено по умолчанию: без `MYRMIDON_BOT_IMAGE_CANARY=1` поведение
  репозитория не меняется.

## 1. Работа (rollout) и её состояния

Одна работа — один digest. Не больше одной незавершённой работы (вторая — 409).

```
 pending → verifying → verified → canary_waiting → canary_running
                │                        │
                └→ failed_verification    └→ canary_health_wait → wave_draining
                                                │         │         │
                                                │         └→ canary_failed
                                                └→ canary_smoke_failed
 волны: wave_draining → wave_applying → wave_restoring → (следующая волна) → succeeded
 любой живой шаг → aborted (до canary_running включительно) / failed_timeout
```

| Статус | Что происходит | Кто двигает |
|---|---|---|
| `pending` → `verified` | Проверка CI-образа (та же, что R5-A) | сервис, в `create` и тике |
| `failed_verification` | Образ отказан, ничего не менялось | сервис |
| `canary_waiting` | Канарейка-бот выбран, ожидает окна обслуживания канарейки | тик |
| `canary_running` | Реконсиляция канарейки в новом образе (drain → recreate → start) | тик |
| `canary_health_wait` | Ждём health контейнера (Docker HEALTHCHECK) и стабильности | тик |
| `canary_smoke` | Дымовой прогон: POST /v1/runs на шлюз канарейки | тик |
| `canary_failed` / `canary_smoke_failed` | Канарейка не здорова / дым не прошёл; всё остановлено | тик |
| `wave_draining` | Волна ботов: для каждого — R3 окно агента | тик |
| `wave_applying` | Реконсиляция бота волны в новом образе (spec прохода собирается из свежепрочитанной карточки; образ канарейки подменяет образ карточки опцией `specImage`, а не фабрикацией карточки с образом раскатки) | тик |
| `wave_restoring` | Профиль и карточки бота волны восстановлены | тик |
| `succeeded` | Все волны прошли, все боты в новом образе | тик |
| `aborted` | Отмена оператором (до `canary_running`) или таймаут шага | маршрут/тик |

Таймаут шага: `MYRMIDON_BOT_CANARY_STEP_TIMEOUT_SEC` (по умолчанию 1800) в одном
статусе — работа отменяется.

## 2. Проверка образа — та же, что у R5-A

До выбора канарейки, в `create` и в `preview`:

1. Ссылка — `ghcr.io/itkadr-git/myrmidon-hermes@sha256:<64 hex>`.
2. Образ есть в реестре, метки CI (`org.opencontainers.image.revision`,
   `org.opencontainers.image.source`).
3. Коммит достижим из `origin/main` или несёт тег `myr-v*` — через GitHub API.

Флага обхода нет. Отказ пишется в работу и журнал активности
(`myrmidon.bot_canary.image_refused`).

## 3. Выбор канарейки

`MYRMIDON_BOT_CANARY_SELECTOR` задаёт botKey агента-канарейки. Пусто — работа не
создаётся: канарейка без явного выбора не угадывается (боты не равнозначны по
критичности). Канарейка должна быть `hermes_gateway` с включённым контейнером и
управляться тем же драйвером, что и флот (только один хост в этой редакции —
хост канарейки из карточки).

## 4. Здоровье канарейки

- `driver.status(botKey)`: `running` и не `unhealthy` — Docker HEALTHCHECK
  образа (30 с интервал, 3 повтора), тот же источник, что сверка.
- Стабильность: `MYRMIDON_BOT_CANARY_HEALTH_SETTLE_SEC` (по умолчанию 90) —
  статус остаётся `running` весь срок.
- Дым: `POST /v1/runs` с `{"input": "<строка>", "session_id": "canary-smoke"}` и
  `Idempotency-Key: canary-<rolloutId>` на шлюз канарейки. Прогон должен дойти до
  терминального статуса `completed` за `MYRMIDON_BOT_CANARY_SMOKE_TIMEOUT_SEC`
  (по умолчанию 300). Провал или таймаут — `canary_smoke_failed`.

## 5. Волны

`MYRMIDON_BOT_CANARY_WAVE_SIZE` (по умолчанию 4) ботов за волну — тот же предел
конкуренции, что у сверки (`RECONCILE_CONCURRENCY`), чтобы волна не занимала
больше памяти, чем штатный проход. Волна обрабатывает ботов по одному: окно
агента, реконсиляция (тот же `reconcileBot`), health по `driver.status`, потом
следующий. Провал любого бота в волне — `failed_health` работы: остановка,
остальные боты не трогаются.

## 6. API

Монтировано под `/api`, та же авторизация, что у deploy-jobs.

### `GET /api/myrmidon/bot-canary`
Права: любой пользователь доски с доступом к организации. Ответ — живая (или
последняя) работа и history (последние 20).

### `POST /api/myrmidon/bot-canary/preview`
Права: как GET. Тело `{ "reference": "sha256:…" }`. Ответ — вердикт проверки.

### `POST /api/myrmidon/bot-canary`
Права: только администратор инстанса. Тело `{ "reference": "sha256:…", "reason?" }`.
Создаёт работу, проверяет образ. Отказы: 400 (ссылка), 409 (работа уже идёт),
503 (функция не включена).

### `POST /api/myrmidon/bot-canary/:id/abort`
Права: администратор инстанса. Отменяет работу до `canary_running` (иначе 409 с
подсказкой про R5-C откат).

`MYRMIDON_BOT_CANARY` (вкл/выкл), `MYRMIDON_BOT_CANARY_SELECTOR` (botKey
канарейки), `MYRMIDON_BOT_CANARY_WAVE_SIZE`, `MYRMIDON_BOT_CANARY_STEP_TIMEOUT_SEC`,
`MYRMIDON_BOT_CANARY_HEALTH_SETTLE_SEC`, `MYRMIDON_BOT_CANARY_SMOKE_TIMEOUT_SEC`,
`MYRMIDON_BOT_CANARY_TICK_SEC` (частота тика), `MYRMIDON_BOT_CANARY_VERIFY_TIMEOUT_SEC`
(таймаут сетевых проверок). См. `docs/myrmidon/SETTINGS.md`, раздел «Трек 5».

## 9. Откат по здоровью (R5-C, п. 10)

Провал канарейки (health или дым) или бота в волне при включённом
`MYRMIDON_BOT_CANARY_AUTO_ROLLBACK` (по умолчанию включён) больше не оставляет
ботов в новом образе:

- работа переходит в `rolling_back` (не терминальный статус), причина провала
  сохраняется на ней;
- тик возвращает каждому боту, получившему новый образ, ОБРАЗ ЕГО КАРТОЧКИ —
  тот самый «локальный» образ, что карточка пинила до выката, — тем же
  `applyBotContainerNow`, по одному боту за раз (как волны: один drain за
  раз). Цели отката: канарейка с момента `canary_running` и применённые боты
  волн (`doneBotKeys`), см. `botCanaryRollbackTargets`;
- когда восстановлены все — `rolled_back` (терминальный, причина провала на
  работе);
- ошибка применения при откате завершает работу `aborted` с громкой причиной
  (имя бота): свип на следующем проходе сам вернёт карточечный образ, машина
  состояний не wedge-ится.

`MYRMIDON_BOT_CANARY_AUTO_ROLLBACK=0` возвращает прежнее поведение: провал —
терминальный `canary_failed` / `canary_smoke_failed` / `failed_health`,
канарейка остаётся в новом образе для разбора.

## 10. Чего сознательно нет

- Раскатки по нескольким fleet-хостам: канарейка и волны идут через драйвер
  контейнеров, хост бота — из карточки; отдельная волна на каждый хост —
  после FLEETD-VMEXEC выката.
- Автовыбора канарейки: селектор задаётся оператором.
- Отката ботов, которых выкат не трогал: цели отката — только те, кто получил
  новый образ; прочие контейнеры не пересоздаются.
