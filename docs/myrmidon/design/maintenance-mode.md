# Режим обслуживания (R3): проект и контракт API

Редакция 27.09.2026, трек 5, шаг 1. Контракт API из раздела 7 — для скриптов выката (R4,
трек 1). Меняется только обратно совместимо: новые поля можно добавлять, старые не
переименовываются и не меняют смысл.

## 0. Коротко

- Режим — это **окно обслуживания** на область: инстанс, компания, отдел или агент. Окон может
  быть несколько, на одну область — не больше одного.
- Пока окно открыто, прогоны агентов из области **не стартуют**. Побудки не отбиваются: они
  ложатся в вендорскую очередь (`agent_wakeup_requests` и `heartbeat_runs` в статусе `queued`)
  и стартуют после выхода.
- Идущие прогоны дорабатывают. По таймауту дренажа — либо ждём дальше (`wait`), либо прерываем
  с повтором после выхода (`interrupt_and_retry`) без замка «требуется разбор».
- Тики рутин в области пропускаются без догона. Сторожа область не будят и не эскалируют.
- Состояние хранится в БД (`instance_settings.general.myrmidonMaintenance`) и переживает
  перезапуск. Миграций нет.
- API: `GET` и `POST /api/myrmidon/maintenance`. Менять режим может только администратор
  инстанса.

## 1. Состояния окна

```
        enter                  идущих прогонов 0            exit                  допуск снят
 off ──────────► entering ─────────────────────────► on ──────────► leaving ────────────────► off
                   │  ▲  по таймауту: wait — остаётся entering (drainTimedOut=true),
                   │  │  interrupt_and_retry — прерывает оставшиеся и переходит в on
                   │  └───────────────────────────────────────────────────────────────
                   └── exit из entering: сразу leaving (дренаж отменён)
```

| Состояние | Допуск новых прогонов в области | Что происходит |
|---|---|---|
| `off` | обычный | Окна нет. В хранилище его нет (последние 20 закрытых окон лежат в `history`) |
| `entering` | закрыт | Дренаж: ждём, пока идущие прогоны области закончатся. Раз в `MYRMIDON_MAINTENANCE_TICK_SEC` сервис пересчитывает число идущих прогонов |
| `on` | закрыт | Идущих прогонов в области нет. Можно выкатывать, чинить, пересоздавать контейнер |
| `leaving` | открыт | Окно закрывается: будим очередь области (`startNextQueuedRunForAgent` по агентам области), затем окно удаляется |

**Кто делает переходы.**

- `off → entering` и `on|entering → leaving` — запрос `POST` администратора (или скрипта
  выката).
- `entering → on` и `leaving → off` — сервис режима, по своему тику и сразу после `POST`.

**Порядок записи.** Каждый переход сначала записывается в БД, потом выполняются его действия.
Все действия идемпотентны, поэтому после сбоя их можно повторить.

**Что при сбое на каждом шаге:**

| Шаг | Сбой | Итог |
|---|---|---|
| `POST enter` | запись в БД не прошла | 500, окна нет, допуск не менялся |
| `entering` | тик упал или сервер перезапустился | При старте окно читается из БД до первого прохода планировщика, допуск закрыт с первой секунды. Дренаж продолжается, срок `drainDeadlineAt` не сдвигается |
| `entering`, прерывание по таймауту | прерывание одного прогона не удалось | Ошибка — в журнал активности (`myrmidon.maintenance.interrupt_failed`), на следующем тике попытка повторяется. В `on` окно переходит, только когда идущих прогонов 0 |
| `leaving` | сбой при побудке очереди или перезапуск | Окно остаётся `leaving` в БД. При старте или на следующем тике шаг повторяется. Даже если его не повторить, очередь поднимет вендорский периодический `resumeQueuedRuns` |
| Интеграция Zabbix | любой сбой | Запись в журнал сервера и журнал активности. На переходы не влияет (раздел 9) |

Вход в уже открытое окно той же области ничего не меняет: ответ 200, `changed: false`, в
ответе — текущее окно с его исходными параметрами. Выход из области без окна — тоже 200,
`changed: false`, `state: "off"`. Скрипты могут повторять запросы без проверок.

## 2. Область

| `scope.type` | `scope.id` | Кого закрывает |
|---|---|---|
| `instance` | нет | Всех агентов всех компаний |
| `company` | id компании | Всех агентов компании |
| `department` | id агента-руководителя | Руководителя и всех его подчинённых по цепочке `reportsTo`, на любую глубину |
| `agent` | id агента | Одного агента |

- Отдельной сущности «отдел» у вендора нет. Отдел — поддерево оргструктуры от руководителя.
- **Членство в отделе вычисляется в момент проверки**, а не запоминается при входе. Агент,
  которого во время окна перевели в другой отдел, выходит из-под окна, и его очередь стартует
  на ближайшем тике. Новый подчинённый руководителя попадает под окно. Кэш членства живёт
  `MYRMIDON_MAINTENANCE_CACHE_TTL_SEC` (по умолчанию 5 с).
- **Области складываются.** Агент закрыт, если его покрывает хотя бы одно окно в состоянии
  `entering` или `on`. Пример: при открытом окне компании администратор открывает окно
  инстанса, потом закрывает окно компании. Агенты компании остаются закрыты, пока открыто окно
  инстанса. Каждое окно живёт и закрывается независимо.
- **Число идущих прогонов окна** считается по его собственной области. Поэтому окно агента
  может перейти в `on`, даже если в компании идут другие прогоны.
- Удалённая компания или агент с открытым окном: окно остаётся, его можно закрыть. Тик
  переводит его в `on`: прогонов в пустой области нет.

## 3. Новые прогоны и побудки

**Шлюз допуска** — одна функция модуля `isAgentUnderMaintenance(agentId, companyId)`, результат
кэшируется. Вызывается там, где вендор уже проверяет допуск:

- `heartbeat.startNextQueuedRunForAgent` — перед захватом очереди. Прогоны остаются `queued`,
  как при занятом слоте конкурентности;
- `heartbeat.executeRun` — повторная проверка. Если окно открылось между захватом и стартом,
  прогон возвращается в `queued` вендорским `releaseRunClaimedJustBeforeSuppression`.

**Побудки.** `enqueueWakeup` вендора в режиме не меняется. Побудка проходит обычный путь:
склейка с уже стоящими в очереди, `deferred_issue_execution` за замком задачи, запись
`queued`. Застревает она только на шлюзе допуска. После выхода каждая побудка стартует **ровно
один раз**: запись в очереди одна, склейку делает вендор.

**Почему не вендорский task drain** (`POST /api/instance/task-drain`):

- в 916.1 побудка во время дренажа пишется как `skipped` и больше не поднимается. Вендор
  исправил это в #14028 уже после 916.1;
- дренаж живёт только в памяти процесса и не переживает перезапуск;
- дренаж действует только на весь инстанс.

Вендорский дренаж остаётся как есть, режим с ним не связан. После переноса #14028 (R2) можно
будет подумать о том, чтобы окно инстанса дополнительно ставило task drain.

**Пауза агента не используется.** Вендорская пауза (`POST /agents/:id/pause`) отменяет
идущие и стоящие в очереди прогоны и побудки. Отмена прогона, в котором уже работал
провайдер, ставит замок `legacy_execution_requires_reconciliation`. Режим обслуживания
`paused_at` не трогает. Агент, стоящий на паузе, после выхода остаётся на паузе.

**`run-dispatch`.** Модуль `server/src/modules/run-dispatch/**` переводит `scheduled_retry` в
`queued`. Шлюз стоит после него, поэтому отдельная точка вызова там не нужна. Если после
слияния P2 (трек 2) найдётся путь старта в обход `startNextQueuedRunForAgent`, точка вызова
появится там.

## 4. Идущие прогоны

- При входе окно получает срок `drainDeadlineAt = enteredAt + drainTimeoutSec`.
- Идущий прогон дорабатывает. Когда в области 0 прогонов в статусе `running`, окно переходит в
  `on`.
- При истечении срока действует `onTimeout`:
  - **`wait`** (по умолчанию) — окно остаётся `entering`, в ответе `drainTimedOut: true`,
    в журнал пишется `myrmidon.maintenance.drain_timed_out` (один раз). Решает человек или
    скрипт: ждать дальше, выйти или повторить вход с другим окном после выхода;
  - **`interrupt_and_retry`** — каждый оставшийся прогон области прерывается вендорской
    отменой (`heartbeat.cancelRun`: сигнал процессу, грейс, освобождение аренд). Прогон
    получает статус `interrupted` и код ошибки **`myrmidon_maintenance_interrupted`**. Для
    него сразу создаётся повтор — вендорский ограниченный повтор (`scheduled_retry` с
    `retryOfRunId`). Повтор проходит `run-dispatch` в `queued` и держится шлюзом до выхода.
- **Замок.** Прерывание режимом не ставит замок «требуется разбор, не повторять»
  (`legacy_execution_requires_reconciliation`). Проверка сделана в точке вызова в
  `heartbeat.ts` и срабатывает **только** на код `myrmidon_maintenance_interrupted`. Настоящие
  сбои — таймаут, падение процесса, отмена человеком, `server_shutdown_interrupted` — ставят
  замок, как у вендора. Прерывания видны в карточке прогона по коду ошибки и в журнале
  активности (`myrmidon.maintenance.run_interrupted`, с `runId`).
- Повтор расходует вендорский бюджет ограниченных повторов. Если бюджет исчерпан, повтора нет,
  и это пишется в журнал (`myrmidon.maintenance.retry_not_scheduled`) — как у вендора при
  исчерпанных повторах.
- **Нативные прогоны** (`paperclip_runner`, отсоединяемые) считаются идущими, пока не
  завершены. Прерываются тем же путём.

## 5. Рутины и сторожа

**Рутины.** Тик рутины, чей исполнитель (агент) в области открытого окна, **пропускается**:

- `nextRunAt` сдвигается на следующий тик расписания;
- пропуск пишется вендорским `recordSuppressedAutomaticRun` с причиной `maintenance`;
- после выхода пропущенные тики **не выполняются задним числом**, даже с политикой
  `enqueue_missed_with_cap`.

Почему решено именно так: после обслуживания не должна прийти лавина накопленных запусков.
Рутина, которой важен каждый тик, увидит пропуски в своей истории. Ручной запуск рутины
(`POST /routines/:id/run`) в режиме создаёт задачу, её побудка ждёт в очереди.

Точка вызова — `server/src/services/routines.ts`, в условии вендорского подавления
(`projectPaused || worktreeSuppressed`) и в условии догона.

**Сторожа** не будят и не эскалируют агентов и задачи в области открытого окна:

- таймерные побудки (`tickTimers`) — пропуск тика. После выхода таймер сработает один раз:
  вендор считает от `lastHeartbeatAt`;
- `reconcileStrandedAssignedIssues` — не переназначает и не эскалирует задачи исполнителей из
  области: их прогоны законно стоят в очереди;
- `reconcileTaskWatchdogs` — не будит сторожевого агента по поддереву в области и не будит
  агента из области;
- `active-run-watchdog` (`scanSilentActiveRuns`) — не считает «молчащими» прогоны области,
  пока окно открыто;
- `sweepStaleIssueLocks` — работает как у вендора: он снимает только замки завершённых
  прогонов.

Для окна инстанса эти обходы пропускаются целиком. Для узких областей агенты из области
отфильтровываются внутри обхода, одной строкой вызова с меткой `myrmidon(R3)`.

## 6. Хранение

Одно место для всех окон: ключ `myrmidonMaintenance` в JSON-поле `instance_settings.general`.

```json
{
  "version": 1,
  "windows": [
    {
      "id": "9f0c…",
      "scope": { "type": "department", "id": "<id руководителя>" },
      "companyId": "<id компании области или null для instance>",
      "state": "entering",
      "reason": "deploy",
      "drainTimeoutSec": 900,
      "onTimeout": "wait",
      "enteredAt": "2026-09-27T10:00:00.000Z",
      "drainDeadlineAt": "2026-09-27T10:15:00.000Z",
      "onAt": null,
      "drainTimedOut": false,
      "exitRequestedAt": null,
      "startedBy": { "actorType": "user", "actorId": "…" },
      "interruptedRunIds": [],
      "zabbix": { "maintenanceId": null, "lastError": null }
    }
  ],
  "history": []
}
```

**Почему не на карточках компании и агента**, как предлагал трек:

- у таблицы `companies` нет свободного JSON-поля. Единственное, `interactionResolverGovernance`,
  валидируется строго;
- `agents.metadata` вендорский `PATCH` агента заменяет целиком: правка карточки в интерфейсе
  стёрла бы окно;
- проверка допуска на горячем пути читает одно место. Переходы атомарны: одна запись одной
  строки.

**Защита ключа.** Вендорский `instanceSettingsService` нормализует `general` через схему со
`strip()`: при чтении неизвестные ключи отбрасываются, при `updateGeneral` — стираются. Поэтому:

- модуль режима читает и пишет ключ сам: сырая строка `instance_settings`,
  `jsonb_set(general, '{myrmidonMaintenance}', …)` в транзакции с `SELECT … FOR UPDATE`;
- в `updateGeneral` вендора — одна точка вызова `myrmidon(R3)`: ключ `myrmidonMaintenance`
  переносится из сохранённой строки в новую. Без неё любое сохранение общих настроек в
  интерфейсе стирало бы режим;
- вендорский `GET /api/instance/settings` ключ не показывает: вендорская схема его
  отбрасывает. Наш API — отдельный.

Истина — в БД. В памяти процесса лежит кэш с TTL. Каждый переход перечитывает строку под
блокировкой.

## 7. API (контракт для скриптов выката)

Оба маршрута смонтированы под `/api`. Авторизация — как у остального API доски: сессия
пользователя или ключ доски (`Authorization: Bearer <board API key>`) пользователя —
администратора инстанса. В режиме `local_trusted` действует неявный локальный администратор,
как у вендора.

### `GET /api/myrmidon/maintenance`

Права: любой пользователь доски с доступом к организации (`assertBoardOrgAccess`) — чтобы
показывать плашку. Токен агента → 403.

Параметры запроса, необязательные: `scopeType`, `scopeId` — вернуть только окно этой области.

Ответ 200:

```json
{
  "active": true,
  "instance": {
    "scope": { "type": "instance" },
    "state": "on",
    "reason": "deploy 2026.927.0-myr.1",
    "drainTimeoutSec": 1800,
    "onTimeout": "wait",
    "startedAt": "2026-09-27T10:00:00.000Z",
    "onAt": "2026-09-27T10:04:12.000Z",
    "drainDeadlineAt": "2026-09-27T10:30:00.000Z",
    "drainTimedOut": false,
    "exitRequestedAt": null,
    "runningRuns": 0,
    "queuedRuns": 7,
    "queuedWakeups": 9,
    "interruptedRuns": 0,
    "startedBy": { "actorType": "user", "actorId": "…" }
  },
  "windows": [ { "...": "то же для каждого открытого окна, включая instance" } ]
}
```

- `active` — есть ли хотя бы одно окно в любом состоянии, кроме `off`.
- `instance` — окно инстанса или `null`. Скрипты выката смотрят сюда.
- `state` — `entering` | `on` | `leaving`. Если окна нет, окно в ответе отсутствует: `instance`
  равен `null`, в `windows` его нет.
- Счётчики берутся из БД по агентам области в момент запроса:
  - `runningRuns` — `heartbeat_runs.status = 'running'`;
  - `queuedRuns` — `queued` и `scheduled_retry`;
  - `queuedWakeups` — `agent_wakeup_requests.status in ('queued', 'deferred_issue_execution')`;
  - `interruptedRuns` — прогоны, прерванные этим окном.
- `startedAt` — время входа (`enteredAt` в хранилище).

### `POST /api/myrmidon/maintenance`

Права: только администратор инстанса (`assertInstanceAdmin`). Иначе 403
`{"error": "Instance admin access required"}`.

Тело:

```json
{
  "action": "enter",
  "scope": { "type": "instance" },
  "reason": "deploy 2026.927.0-myr.1",
  "drainTimeoutSec": 1800,
  "onTimeout": "wait"
}
```

| Поле | Тип | Обязательно | Смысл |
|---|---|---|---|
| `action` | `"enter"` \| `"exit"` | да | |
| `scope.type` | `"instance"` \| `"company"` \| `"department"` \| `"agent"` | да | |
| `scope.id` | uuid | для всех, кроме `instance` | id компании или агента (для `department` — руководителя) |
| `reason` | строка 1–500 | для `enter` | Попадает в плашку и журнал |
| `drainTimeoutSec` | целое 0–86400 | нет | По умолчанию `MYRMIDON_MAINTENANCE_DRAIN_TIMEOUT_SEC` (900). `0` — таймаут сразу |
| `onTimeout` | `"wait"` \| `"interrupt_and_retry"` | нет | По умолчанию `wait` |

Для `exit` учитываются только `action` и `scope`, `reason` необязателен и пишется в журнал.

Ответ 200 — окно области после действия, в формате элемента `windows`, плюс
`"changed": true|false`. После `exit` окно обычно уже в `leaving` или `off`:
`{"scope": …, "state": "off", "changed": true}`.

Ошибки:

| Код | Когда |
|---|---|
| 400 | Тело не проходит схему; `scope.id` у `instance` или его нет у других |
| 403 | Не администратор инстанса или токен агента |
| 404 | Компания или агент `scope.id` не найдены (только для `enter`) |
| 409 | `enter` в область, чьё окно сейчас в `leaving`. Повторить через секунду |

**Журнал активности** — каждое действие и переход, `entityType: "myrmidon_maintenance"`,
`entityId` — id окна:

- `myrmidon.maintenance.enter_requested`, `.on`, `.drain_timed_out`, `.run_interrupted`,
  `.interrupt_failed`, `.retry_not_scheduled`, `.exit_requested`, `.exited`,
  `.zabbix_failed`;
- в `details` — область, причина, параметры, счётчики;
- компании для записи: для окна инстанса — каждая компания (как у вендорского task drain), для
  остальных — компания области.

### `GET /api/health`

Добавляется поле `maintenance`. Оно видно и анонимному вызову, чтобы скрипт выката проверял
его без ключа:

```json
"maintenance": { "active": true, "instanceState": "on", "windows": 1 }
```

- Поле есть, **только пока открыто хотя бы одно окно**. Нет поля — окон нет. Вне режима ответ
  совпадает с вендорским, как у полей `cloud` и `hiddenSettings`.
- `instanceState` — состояние окна инстанса: `entering` | `on` | `leaving`, или `off`, если
  открыты только окна узких областей.
- Статус health режим не меняет: `status` остаётся `ok`.

### Как выкат (R4) пользуется режимом

1. `POST {"action":"enter","scope":{"type":"instance"},"reason":"deploy <tag>","drainTimeoutSec":<N>,"onTimeout":"wait"}`.
2. Опрашивать `GET /api/myrmidon/maintenance` раз в 5–10 с, пока `instance.state == "on"`.
   Если к своему сроку скрипта окно всё ещё `entering` — решить по политике выката: ждать,
   или `exit` и отменить выкат, или повторить окно с `interrupt_and_retry`.
3. Дамп БД, выкат по digest, пересоздание контейнера. Окно в БД, новый процесс поднимает его
   при старте до первого прохода планировщика, прогоны не стартуют.
4. Проверить `/api/health`: версия, коммит и `maintenance.instanceState == "on"`.
5. `POST {"action":"exit","scope":{"type":"instance"}}`, затем опрашивать, пока
   `instance == null` (или пока в `/api/health` не пропадёт поле `maintenance` либо
   `maintenance.instanceState` не станет `off`).
6. Откат выполняется так же: окно не закрывают, пока старый digest не поднят и не проверен.

## 8. Плашка в интерфейсе

- **Где:** полоса над содержимым в общем макете (`ui/src/components/myrmidon/MaintenanceBanner`,
  одна вставка в макет). Видна на всех страницах компании, которую затрагивает окно.
- **Что видит любой пользователь доски:**
  - окно инстанса или своей компании: «Maintenance mode: new agent runs are paused. Wakes are
    queued and will be delivered after maintenance ends.» Плюс причина, с какого времени,
    состояние (`draining: N runs still running` / `on`);
  - окна отделов и агентов своей компании — одна строка «Maintenance: N agents (department X,
    agent Y)» со ссылками на карточки.
- **Что может администратор инстанса:** кнопка «End maintenance» у каждого окна (с
  подтверждением в самой плашке) и ссылка на настройки инстанса. Там раздел «Maintenance»:
  войти (область, причина, таймаут, действие по таймауту), список открытых окон, выход.
- Остальные пользователи ничего менять не могут: плашка только информирует.
- Данные — `GET /api/myrmidon/maintenance`, опрос раз в 30 с и живые события доски, если
  подходящее есть. Тексты — на английском, как весь интерфейс вендора (языки — U5).
- Цвета и отступы — только токены дизайн-системы (`pnpm check:token-gates`).

## 9. Zabbix (встроенная интеграция, по умолчанию выключена)

- Включается, только если заданы `MYRMIDON_ZABBIX_URL`, `MYRMIDON_ZABBIX_TOKEN_REF` и
  `MYRMIDON_ZABBIX_HOST_GROUPS`. Без них — ни одного сетевого вызова.
- `MYRMIDON_ZABBIX_TOKEN_REF` — **ссылка** на токен API Zabbix, не значение:
  - `env:<ИМЯ>` — взять из переменной окружения;
  - `file:<путь>` — взять из файла, например секрета Docker.
  
  Токен не пишется в журналы и ответы.
- **Только окно инстанса.** Окна компаний, отделов и агентов хосты не выключают.
- Вход (`off → entering`): вызов `maintenance.create` API Zabbix (JSON-RPC,
  `Authorization: Bearer`). Параметры:
  - имя `myrmidon: <reason>`;
  - группы хостов из `MYRMIDON_ZABBIX_HOST_GROUPS` (имена через запятую, id ищутся через
    `hostgroup.get`);
  - сбор данных продолжается (`maintenance_type = 0`);
  - период — с момента входа на `MYRMIDON_ZABBIX_MAX_WINDOW_SEC` (по умолчанию 14400).
    Если выход не случится, окно Zabbix закроется само.
  
  Полученный id пишется в окно (`zabbix.maintenanceId`).
- Выход (`leaving`): `maintenance.delete` по сохранённому id.
- Таймаут вызова 10 с. **Любой сбой** — ошибка сети, ответ с `error`, отсутствие групп —
  пишется в журнал сервера и в журнал активности (`myrmidon.maintenance.zabbix_failed`). Режим
  входит и выходит как обычно. Повтора нет: окно Zabbix ограничено сроком.
- Адреса Zabbix, имена групп и токены — только в `myrmidon-deploy`, не в этом репозитории.

## 10. Связь с остановкой сервера

- **Вендорская остановка по `SIGTERM` не меняется.** Она останавливает планировщик и прерывает
  идущие прогоны (`server_shutdown_interrupted`), у них вендорский повтор или замок.
- **Режим делает остановку безопасной.** Выкат сначала открывает окно инстанса и ждёт `on`. К
  моменту `SIGTERM` идущих прогонов нет, прерывать нечего. Окно при остановке не закрывается:
  оно в БД.
- **Старт.** В `server/src/index.ts` — точка вызова `restoreMaintenanceOnStartup()` **до**
  стартового `resumeQueuedRuns` и первого тика планировщика. Она поднимает окна в кэш, и
  стартовое восстановление не запускает очередь области. Окна в `entering` продолжают дренаж.
  Прогоны, прерванные остановкой, вендор обрабатывает как обычно. Окна в `leaving`
  дозавершаются.
- **Горячий перезапуск вендора** (`prepareHotRestartShutdown` / `reconcileHotRestartAdoption`)
  не меняется. Усыновлённые процессы — это идущие прогоны, окно ждёт их как обычно.

## 11. Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `MYRMIDON_MAINTENANCE_DRAIN_TIMEOUT_SEC` | `900` | Таймаут дренажа, если в запросе нет `drainTimeoutSec` |
| `MYRMIDON_MAINTENANCE_TICK_SEC` | `5` | Как часто сервис пересчитывает окна (переходы `entering → on`, таймауты, `leaving → off`) |
| `MYRMIDON_MAINTENANCE_CACHE_TTL_SEC` | `5` | Кэш проверки допуска и членства в отделе |
| `MYRMIDON_ZABBIX_URL` | не задан | Адрес API Zabbix (`…/api_jsonrpc.php`). Не задан — интеграция выключена |
| `MYRMIDON_ZABBIX_TOKEN_REF` | не задан | `env:<ИМЯ>` или `file:<путь>` |
| `MYRMIDON_ZABBIX_HOST_GROUPS` | не задан | Имена групп хостов через запятую |
| `MYRMIDON_ZABBIX_MAX_WINDOW_SEC` | `14400` | Длина периода обслуживания в Zabbix |

Строки в [SETTINGS.md](../SETTINGS.md) добавляются в PR, где появляется настройка.

## 12. Точки вызова в файлах вендора

Каждая — одна строка вызова функции модуля `server/src/myrmidon/maintenance/` с меткой
`// myrmidon(R3): …`:

|---|---|

| `server/src/services/routines.ts` | пропуск тика и догона |
| `server/src/services/recovery/service.ts` | фильтр в `reconcileStrandedAssignedIssues` |

| `server/src/modules/active-run-watchdog/**` | фильтр в `scanSilentActiveRuns` |

## 13. Тесты (шаг 2)

Встроенный postgres, файлы `*.myrmidon.test.ts`:

- вход → новый прогон не стартует, побудка в очереди;
- выход → побудка доставлена ровно один раз;
- идущий прогон дорабатывает, окно переходит в `on`;
- таймаут с `interrupt_and_retry` → прогон прерван, после выхода повторён, замка нет;
- настоящий сбой прогона вне режима по-прежнему ставит замок;
- рутина в режиме не срабатывает и не догоняется после выхода;
- режим агента не мешает другим агентам;
- режим отдела действует на руководителя и подчинённых, не действует на соседний отдел;
- режим переживает перезапуск сервера и сохранение общих настроек;
- `POST` → 403 не-администратору и токену агента.
