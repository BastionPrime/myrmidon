# Выкат и откат Myrmidon

> English version: [deploy.md](deploy.md)

Выкат идёт по отпечатку (digest) образа `ghcr.io/itkadr-git/myrmidon`, а не по тегу: тег можно
передвинуть, digest — нет. На бой идёт только образ, собранный CI (решение владельца): скрипт
выката сам проверяет это до любых действий, см. [«Только образы из CI»](#только-образы-из-ci).
Скрипты лежат в [`scripts/myrmidon/deploy/`](../../scripts/myrmidon/deploy/)
и не знают ничего о конкретной установке: всё берётся из файла настроек. Пример —
[`deploy.env.example`](../../scripts/myrmidon/deploy/deploy.env.example); настоящий файл
установки лежит в закрытом репозитории развёртывания и в открытый не попадает.

## Что нужно на хосте

- bash 4+, `docker` с плагинами `compose` и `buildx`, `curl`, `jq`, `git`;
- скрипты запускаются из клона репозитория `itkadr-git/myrmidon`, у которого `origin` смотрит на
  `github.com/itkadr-git/myrmidon`: по этому клону проверяется, что коммит образа есть в `main`
  (см. ниже). Из каталога без git или из клона другого репозитория выкат отказывает;
- сервер Myrmidon запущен через docker compose, образ сервиса задаётся в отдельном файле
  override (`COMPOSE_OVERRIDE_FILE`). Скрипт меняет в нём только строку `image:`;
- команда дампа БД (`DUMP_COMMAND`) и, для отката с восстановлением, команда восстановления
  (`RESTORE_COMMAND`). Обе получают путь в переменной `DUMP_FILE`;
- в режиме `authenticated` анонимный `/api/health` показывает коммит, но не версию. Ключ доски
  в файле с правами `0600` в `HEALTH_TOKEN_FILE` **обязателен**: без него проверка версии на
  шаге 7 не проходит и выкат считается неудачным (так задумано — версия проверяется всегда);
- как считать идущие прогоны: `RUNNING_RUNS_COMMAND` или `MAINTENANCE_MODE=api`. Если счётчик
  не сработал (ошибка или пустой вывод), выкат останавливается до смены образа. Пропустить
  ожидание можно только явно: `ALLOW_UNKNOWN_RUNS=1`.

## Где взять digest

В сводке job `image` workflow **Myrmidon image** (Actions → запуск на нужном коммите или теге):
строка `Digest`. Или:

```sh
docker buildx imagetools inspect ghcr.io/itkadr-git/myrmidon:1.0.0 --format '{{json .Manifest.Digest}}'
```

`--digest` принимает `sha256:<64 hex>` или полную ссылку `ghcr.io/itkadr-git/myrmidon@sha256:<64 hex>`.
Тег (`1.0.0`, `main`, `ghcr.io/itkadr-git/myrmidon:1.0.0`) скрипт не берёт: по тегу нельзя
доказать, что это тот образ, который прошёл CI.

Версию и коммит, которые должен показать `/api/health`, скрипт берёт из меток образа
(`org.opencontainers.image.version`, `org.opencontainers.image.revision`). Их можно задать
явно: `--expect-version`, `--expect-commit`.

## Только образы из CI

Решение владельца: на бой идёт только образ, собранный CI (workflow **Myrmidon image**) из `main`
или из тега `myr-v*`. Срочное исправление тоже идёт через PR, пусть и ускоренный, а не образом,
собранным на месте. Образ, собранный руками, попадает на бой мимо репозитория и ревью, а при
следующем выкате его содержимое молча пропадает: в репозитории его нет.

`deploy.sh` проверяет это **до любых действий** (до `docker pull`, дампа и режима обслуживания) и
при любом «нет» завершается с причиной, ничего не меняя:

1. **Ссылка** строго `ghcr.io/itkadr-git/myrmidon@sha256:<64 hex>`: ни тега без digest, ни другого
   репозитория или реестра, ни заглавных букв в digest. `MYRMIDON_IMAGE` в файле настроек
   должен быть равен `ghcr.io/itkadr-git/myrmidon`, другое значение — отказ.
2. **Образ есть в реестре.** Его манифест и конфиг читаются из реестра
   (`docker buildx imagetools inspect`) без скачивания слоёв. Локально собранный образ туда не
   попадает; реестр недоступен — тоже отказ.
3. **Метки CI.** У образа есть `org.opencontainers.image.revision` (полный sha коммита) и
   `org.opencontainers.image.source` равна `https://github.com/itkadr-git/myrmidon`. Эти метки
   CI ставит при сборке.
4. **Коммит проверен.** Скрипт делает `git fetch origin main` в клоне, где лежит сам скрипт, и
   требует, чтобы коммит из метки был достижим из `origin/main` либо на нём стоял тег
   `myr-v<x>.<y>.<z>` в `origin` (`git ls-remote --tags`). Образ, собранный из ветки или из
   непроверенного кода, не проходит. Нет git, скрипт лежит вне клона, `origin` не наш, fetch не
   прошёл — отказ с понятной причиной.

Обхода нет: ни флага, ни настройки. `--force` (повторный выкат того же образа) и
`--expect-*` проверку не пропускают. Чтобы выкатить образ, который не проходит, нужно, чтобы он
прошёл CI: PR в `main`, слияние, сборка.

### Выкат доски и компонентов релиза вместе

С 1.4.0 (RELEASE-GATE, после инцидента 01.10) `deploy.sh` выкатывает образы компонентов
релиза (dockergate, fleetd) **в том же прогоне**, что и образ доски, и отказывает релизу,
чьи компоненты отсутствуют в реестре, **до каких-либо изменений**. Digest'ы резолвятся из
того же релиза: тег `myr-vX.Y.Z` из version-метки образа доски, иначе тег `sha-<короткий>`
его коммита (`scripts/myrmidon/dockergate/check-release-support.sh`). Вручную искать ничего
не нужно: оператор передаёт digest доски, а подходящие digest'ы компонентов скрипт находит
сам.

Компоненты перечислены в `MYRMIDON_RELEASE_COMPONENTS` (по умолчанию `dockergate,fleetd`).
Каждый компонент катится своим pull по digest, своим override-файлом
(`docker-compose.myrmidon-<компонент>.yml`), пересозданием сервиса и **обязательной**
health-пробой (`MYR_<КОМПОНЕНТ>_HEALTH_URL`; не задана — раскат компонента отказывает после
переключения, fail-closed). Неуспешный раскат компонента или неуспешный постдеплойный smoke
завершает выкат как DEGRADED с напечатанными командами отката; доска к этому моменту уже
здорова, поэтому откат — решение оператора. `MYRMIDON_RELEASE_COMPONENTS=none` возвращает
поведение «только доска» (не для релиза: инцидент 01.10 — ровно такой разрыв). Настройки —
в [SETTINGS.md](SETTINGS.ru.md); пример — в
[`deploy.env.example`](../../scripts/myrmidon/deploy/deploy.env.example).

### Обновление с 1.3.2 до 1.4.0

Выкатывайте образы доски, dockergate и fleetd из одного тега 1.4.0 вместе — с 1.4.0 скрипт
делает это одним прогоном (раздел выше): передайте digest доски, а digest'ы dockergate и
fleetd того же тега резолвятся и выкатятся автоматически. Новых миграций, которые надо
запускать вручную, нет: обновление на стороне хоста сводится к смене образа. Чтобы пробы
компонентов прошли, задайте `MYR_DOCKERGATE_HEALTH_URL` и `MYR_FLEETD_HEALTH_URL` в
`deploy.env` до выката (см. [SETTINGS.md](SETTINGS.ru.md)).

Что меняется для операторов:

- **Автоматический откат по здоровью включён по умолчанию** (R5-C). Неуспешная проверка
  здоровья после выката больше не оставляет доску на сломанном образе: хостовой исполнитель
  немедленно запускает `rollback.sh` на образ, который выкат запомнил перед переключением,
  и работа закрывается `auto_rolled_back` со снятым окном обслуживания. Неуспешный сам по
  себе откат заканчивается `failed_rollback` с оставленным оператору окном. Чтобы вернуть
  ручной контракт 1.3.x, поставьте `AUTO_ROLLBACK=0` в `deploy.env` И
  `MYRMIDON_DEPLOY_AUTO_ROLLBACK=0` на стороне доски — обе стороны должны совпадать.
  См. [SETTINGS.md](SETTINGS.ru.md).
- **Парк ботов получил ту же защиту**: неуспешный канарейка или бот волны переводит раскат
  в `rolling_back`, каждый затронутый бот возвращается на образ своей карточки по одному,
  и раскат заканчивается `rolled_back` с сохранённой исходной причиной. Отключить —
  `MYRMIDON_BOT_CANARY_AUTO_ROLLBACK=0`, чтобы оставить канарейку на новом образе для
  осмотра.
- **Автообновление без подтверждения остаётся выключенным**: `MYRMIDON_DEPLOY_AUTO_UPDATE`
  по умолчанию `0` — каждый выкат по-прежнему ждёт явного подтверждения человека в
  интерфейсе. Включайте его только после того, как сценарий выпуска прогнан на стенде.
- **Новая опциональная секция в карточке агента**: вкладка «Memory» (просмотр, выгрузка,
  удаление записей банка памяти) выключена, пока на инстансе не заданы
  `MYRMIDON_HINDSIGHT_API_URL` и `MYRMIDON_HINDSIGHT_KEY_SECRET`. Без этой пары в карточке
  ничего не меняется.
- **Облачное хранилище (часть B)**: владелец теперь может подключать облачного провайдера
  из панели по OAuth; набор токенов живёт в секрете компании в хранилище секретов инстанса
  и никогда не доходит до ботов. На момент обновления ничего делать не нужно —
  существующие выдачи продолжают работать.

`--dry-run` выполняет ту же проверку (она только читает реестр и обновляет `origin/main` в клоне),
поэтому пробный прогон заранее показывает отказ.

Границы. Это защита от ошибки, а не от злого умысла: тот, у кого есть право записи в пакет
`ghcr.io/itkadr-git/myrmidon`, может запушить образ с чужими метками. Поэтому право записи в пакет
должно быть только у workflow сборки (настройка пакета на GitHub, скрипт её не проверяет).

## Выкат

```sh
scripts/myrmidon/deploy/deploy.sh --config /path/to/deploy.env --digest sha256:<64 hex> --dry-run
scripts/myrmidon/deploy/deploy.sh --config /path/to/deploy.env --digest sha256:<64 hex>
```

Порядок:

0. Проверка образа (раздел выше). Не прошла — выкат не начинается, ничего не тронуто. Сразу
   после неё резолвятся digest'ы компонентов того же релиза (`check-release-support.sh`);
   релиз, чьи компоненты отсутствуют в реестре, отказывается здесь же — до pull и дампа.
1. `docker pull` образа по digest. Не тянется — выкат не начинается.
2. Текущий образ из файла override запоминается как предыдущий: полная ссылка — в
   `$STATE_DIR/previous-image` (так работает и первый переход с вендорского образа), digest
   форка — ещё и в `$STATE_DIR/previous-digest`.
3. Дамп БД командой `DUMP_COMMAND` в `DUMP_DIR`. Файла нет или он меньше `DUMP_MIN_BYTES` —
   отказ, образ не меняется.
4. Вход в режим обслуживания (`MAINTENANCE_MODE`):
   - `api` — `POST /api/myrmidon/maintenance` по контракту из
     [design/maintenance-mode.md](design/maintenance-mode.md), раздел 7 (трек 5, R3).
     Окно открывается с `onTimeout: interrupt_and_retry` и
     `drainTimeoutSec: MAINTENANCE_DRAIN_GRACE_SEC` (по умолчанию 300 с), чтобы плановый
     выкат не ждал длинных прогонов. `MAINTENANCE_ON_TIMEOUT=wait` возвращает прежнее
     поведение: окно открывается с `onTimeout: wait` и
     `drainTimeoutSec: MAINTENANCE_DRAIN_TIMEOUT_SEC` (1800 с);
   - `hook` — свои команды `MAINTENANCE_ENTER_COMMAND` / `MAINTENANCE_EXIT_COMMAND`;
   - `pause` — пока API режима нет: пауза `MAINTENANCE_PAUSE_SEC` секунд.
5. Ожидание, пока идущих прогонов не станет 0: `RUNNING_RUNS_COMMAND` или, в режиме `api`,
   `instance.runningRuns` из API. С умолчанием `onTimeout: interrupt_and_retry` окно
   дренирует grace (`MAINTENANCE_DRAIN_GRACE_SEC`, 300 с) и затем прерывает оставшиеся
   прогоны: каждый помечается прерванным режимом обслуживания (не сбой), задача сохраняет
   своё место, а прогон автоматически повторяется при закрытии окна. Именно это заставляет
   ожидание сходиться быстро, а не упираться в длинный прогон. Таймаут `RUNS_WAIT_TIMEOUT_SEC`
   (или сломанный счётчик) — выкат
   прерывается до смены образа, **режим обслуживания снимается перед аварийным выходом**: доска не
   остаётся в обслуживании до ручного снятия. Не сработавшее снятие (обслуживание уже выключено)
   — предупреждение, не двойной отказ; причина выхода остаётся «слив не завершился». Счётчик не
   сработал — тоже прерывается (кроме `ALLOW_UNKNOWN_RUNS=1`).
6. Новая строка `image:` в override и `docker compose up -d --no-deps <сервис>`: пересоздаётся
   только сервис сервера.
7. Проверка `/api/health` (`verify-health.sh`): `status` = `ok`, версия и коммит совпадают.
8. Выход из режима обслуживания. Вызов `exit` возвращает ответ, как только сервер помечает окно
   `leaving` (хвост выхода — возобновление очереди, хук выхода, закрытие окна — выполняется на тике
   режима), после чего скрипт ждёт закрытия окна: опрашивает `GET /api/myrmidon/maintenance`, пока
   состояние инстанса не станет `off` (окна инстанса нет), в пределах `MAINTENANCE_EXIT_WAIT_SEC`
   (по умолчанию 120 с). Таймаут печатается громко и **не** валит уже переключённый и здоровый
   выкат: окно остаётся `leaving`, а это состояние уже открывает допуск. Не сработавший сам вызов
   `exit` по-прежнему прерывает выкат — окно осталось бы `on`. Тот же шаг выполняет пост-деплойную
   проверку парка (`myrmidon(POST-DEPLOY-CHECK)`): при заданных `BOARD_API_URL` и `BOARD_COMPANY_ID`
   скрипт спрашивает у доски задачи `blocked` с обновлением после начала выката и перечитывает
   состояние режима. Заблокированная задача в окне, нечитаемая доска или не закрывшееся окно
   печатают `degraded: ...`, и прогон заканчивается строкой `DEPLOY DEGRADED`; уже переключённый и
   здоровый выкат это не валит. Без этих двух настроек проверка пропускается со строкой в логе.
9. Компоненты релиза катятся в том же прогоне (см.
   [Выкат доски и компонентов релиза вместе](#выкат-доски-и-компонентов-релиза-вместе)):
   по одному `rollout-component.sh` на компонент — pull по digest, override-файл компонента,
   пересоздание сервиса, обязательная health-проба. Неуспешный компонент помечает выкат
   DEGRADED и печатает команды отката.
10. Постдеплойный smoke (`bot-apply-smoke.sh`): за `MYRMIDON_DEPLOY_SMOKE_TIMEOUT_SEC`
    (по умолчанию 300 с) хотя бы один контейнер бота компании `MYRMIDON_DEPLOY_SMOKE_COMPANY`
    должен повторно примениться (его статус — `running`). При провале выкат отвечает
    DEGRADED с командами отката. Без заданной компании smoke пропускается с
    предупреждением; `MYRMIDON_DEPLOY_SMOKE=0` отключает его целиком (не для релиза).

Если шаг 7 не прошёл, скрипт завершается с ошибкой, **режим обслуживания остаётся включённым**,
в выводе — команда отката и путь к дампу. Сбой на шагах 9–10 случается, когда доска уже
здорова и обслуживание снято: скрипт завершается с ошибкой и строкой DEGRADED, а откат доски
и каждого компонента — решение оператора.

`--dry-run` ничего не меняет (не тянет образ, не делает дамп, не трогает файлы) и печатает
план. Проверка образа (шаг 0) в нём выполняется: она только читает.

## Откат

```sh
scripts/myrmidon/deploy/rollback.sh --config /path/to/deploy.env            # на предыдущий образ
scripts/myrmidon/deploy/rollback.sh --config /path/to/deploy.env --to sha256:<64 hex>
scripts/myrmidon/deploy/rollback.sh --config /path/to/deploy.env --to-image ghcr.io/paperclipai/paperclip:2026.916.1
```

Без `--to`/`--to-image` откат берёт образ, запомненный при последнем выкате, — в том числе
вендорский при первом переходе на форк. Откат возвращает образ и проверяет health по меткам
старого образа. **БД не восстанавливается.**

Откат — аварийный путь, и он **не блокируется** проверкой «только из CI»: образ, записанный
`deploy.sh` как предыдущий, возвращается, откуда бы он ни был. Но цель откат проверяет так же,
как `deploy.sh` новый образ (ссылка, реестр, метки, коммит) и, если она не проходит, печатает
`WARNING: rollback target is not a verified CI image: <причина>` и продолжает. Предупреждение
ожидаемо при первом откате на вендорский образ или на образ, собранный руками до введения этого
правила: его нет в реестре. Так преемник видит, что откат идёт на непроверенный образ.
Миграции вендора односторонние: старый образ обычно работает на новой схеме, а восстановление
дампа стирает всё, что записано после него. Если старый образ на новой схеме не стартует,
восстановление — отдельным явным шагом:

```sh
scripts/myrmidon/deploy/rollback.sh --config /path/to/deploy.env --to sha256:<old> \
  --restore-dump /path/to/myrmidon-<время>-<digest>.dump
```

Скрипт попросит ввести `RESTORE` (или флаг `--yes-restore-database`), остановит сервис сервера,
выполнит `RESTORE_COMMAND`, затем поднимет старый образ.

Компонент релиза откатывается отдельно, без троганья доски:

```sh
scripts/myrmidon/deploy/rollback-component.sh --config /path/to/deploy.env --component dockergate
```

Он возвращает образ, запомненный раскатом компонента как прежний
(`$STATE_DIR/previous-<компонент>-image`, либо явный `--to-image <ссылка>`), пересоздаёт
сервис и повторяет health-пробу этого компонента (при незаданной пробе — пропуск с
предупреждением). Как и `rollback.sh`, это аварийный путь: непроверенная цель предупреждает,
но не блокирует. Откат доски не откатывает компоненты, откат компонента не трогает доску:
после DEGRADED-выката вывод называет, какая сторона упала и какую команду запустить.

## Выкат из интерфейса

Доска может запустить свой выкат: настройки инстанса («Board update») проверяют digest,
открывают окно обслуживания, передают переключение хостовому исполнителю и следят за
здоровьем. Правила — те же, что у скрипта, а не вторая политика:

- та же проверка CI-образа (ссылка, реестр, метки, коммит на main или тег myr-v*) выполняется
  ДО открытия окна обслуживания — отказанный образ ничего не меняет, даже допуск прогонов;
  флага обхода нет;
- один выкат за раз: пока работа открыта, вторая — 409;
- окно обслуживания — на весь инстанс, причина `deploy <префикс digest>`, и оно закрывается
  при завершении работы; при провале здоровья окно ОСТАЁТСЯ для отката (тот же контракт,
  что у шага 7 скрипта);
- доска сама docker не запускает. Хостовая половина —
  `scripts/myrmidon/deploy/deploy-from-job.sh`: опрашивает API доски, ждёт окно `on`,
  запускает тот же `deploy.sh` (дамп, дренаж, здоровье) и пишет маленький JSON-отчёт на
  каждую работу (`$STATE_DIR/job-<id>.json`). Этот каталог монтируется в контейнер доски
  только для чтения как `MYRMIDON_DEPLOY_REPORTS_DIR`: доска его читает и никогда не пишет.
  Поскольку исполнитель запускает тот же `deploy.sh`, гейт релиза действует и здесь:
  компоненты релиза катятся в той же работе, а неуспешный раскат компонента или smoke валит
  работу со строкой DEGRADED в её журнале (`$STATE_DIR/job-<id>.log`);
- работа закрывается как успешная, только когда собственный `/api/health` доски согласен с
  отчётными версией и коммитом — лживый отчёт не закроет провалившийся выкат;
- работа, застрявшая в одном шаге дольше `MYRMIDON_DEPLOY_STEP_TIMEOUT_SEC`, отменяет себя
  и закрывает окно;
- **при провале проверки здоровья доска откатывается автоматически (R5-C).** Исполнитель
  немедленно запускает `rollback.sh` на образ, который `deploy.sh` запомнил перед
  переключением — локально известный прежний образ (откат — аварийный путь, его
  CI-проверка только предупреждает) — и пишет фазы `rolling-back`, затем `rolled-back`
  (прежний образ снова здоров; работа закрывается `auto_rolled_back`, окно обслуживания
  закрывается — человек не участвовал) или `rollback-failed` (работа закрывается
  `failed_rollback`, окно ОСТАЁТСЯ для оператора). `MYRMIDON_DEPLOY_AUTO_ROLLBACK=0`
  возвращает прежний контракт: работа закрывается `failed_health` с открытым окном, откат
  делает оператор. Хостовая половина того же выключателя — `AUTO_ROLLBACK` в `deploy.env`
  (по умолчанию 1); обе стороны должны совпадать;
- **автообновление без подтверждения остаётся выключенным
  (`MYRMIDON_DEPLOY_AUTO_UPDATE`, R5-C).** Каждый выкат из интерфейса ждёт явного
  подтверждения; включение необслуживаемых выкатов — решение на время после прогона
  сценария выпуска на стенде (STAND). Флаг существует, задокументирован и по умолчанию
  выключен.

### Включение

По умолчанию всё выключено (`MYRMIDON_DEPLOY_ENABLED` не задан). Чтобы включить:

1. `MYRMIDON_DEPLOY_ENABLED=1` в окружении доски;
2. `MYRMIDON_DEPLOY_HEALTH_URL` — собственный health-эндпоинт доски, как его видит
   контейнер доски (например `http://127.0.0.1:3100/api/health`);
3. `MYRMIDON_DEPLOY_REPORTS_DIR` — смонтированный каталог отчётов (хостовое `$STATE_DIR`);
4. на хосте — исполнитель (`deploy-from-job.sh --config <deploy.env>`), таймером или в
   терминале. Ему нужны `BOARD_API_URL` и (в режиме `authenticated`) `BOARD_TOKEN_FILE` —
   файл ключа доски, режим 0600, тот же, что у `HEALTH_TOKEN_FILE`.

Digest доска проверяет сама — реестр и GitHub. Если контейнер доски их не видит,
`MYRMIDON_DEPLOY_REGISTRY_INSPECT_URL` указывает на read-only inspect-эндпоинт, отвечающий
на `?ref=<ссылка>` тем же JSON, что `imagetools inspect`, а
`MYRMIDON_DEPLOY_GITHUB_HEADERS_JSON` добавляет заголовки к вызовам GitHub (но не значение
токена в окружении публичного файла развёртывания).

### Когда кнопка, когда скрипт

Интерфейс — для штатных выкатов: digest из зелёного прогона CI на `main` или теге `myr-v*`,
доска доступна, исполнитель запущен. Скриптом остаются первый выкат установки, сломанная
доска (себя она не выкатит) и все случаи, когда интерфейс отказывает — ровно те, когда
отказал бы и скрипт.

## Что проверить после выката

- `/api/health`: `status: ok`, версия и коммит — как в сводке образа; `maintenance` — выключен.
- Пробы компонентов гейта релиза: вывод выката заканчивается строкой
  `release gate passed: board and <компоненты> rolled out together, bots re-apply`. Каждый
  компонент отвечает на свою пробу (точная цель — ваш `MYR_<КОМПОНЕНТ>_HEALTH_URL`).
- Журнал сервера: миграции применились, ошибок старта нет:
  `docker compose logs --since 10m <сервис>`.
- Самодельные операторские индексы: миграция выпуска может удалять индексы, созданные
  вручную вне истории миграций (миграция этого выпуска удаляет выраженческие индексы
  `myr_hotfix_*` после перевода горячих сравнений на uuid-типизированные формы). Если в
  базу вмешивались вручную, после выката сверьте её со схемой: `pnpm db:generate` в
  выгрузке выкаченного тега не должно показать расхождения.
- Интерфейс открывается, список агентов на месте, задача открывается.
- Прогоны снова стартуют: побудки из очереди доставлены, новый прогон проходит.
- Контейнеры ботов после выпуска, который трогает сверку или dockergate: в течение 30 минут
  после выката в журнале доски не должно быть ни `bot container recreated for a template change`,
  ни `bot container template drift detected` по карточке, которую никто не менял (в том числе
  после перезагрузки хоста). Настоящая правка карточки (например `memoryMb`) по-прежнему
  пересоздаёт бота ровно один раз. Если строка всё же появилась, она называет поле и оба значения.
- Плагины (hindsight и остальные) в статусе `ready` в настройках плагинов.
- В `$STATE_DIR/history.log` — строка выката.

## Стенд проверки выпуска

Перед выкатом на боевую установку выпуск проверяется на отдельной ВМ на копии боевой базы.

**Ресурсы.** Не меньше боевой установки по памяти и диску под БД; по CPU можно меньше. Диск —
под образ (несколько ГБ), копию базы и её дамп.

**Разворачивание.**

1. Отдельная ВМ без доступа к боевым сервисам: свои сети, свои секреты, другой адрес.
2. Тот же compose, что на боевой установке, с файлом override на проверяемый digest.
3. Последний боевой дамп восстановлен в БД стенда.
4. Внешние интеграции выключены до старта сервера:
   - чаты (Telegram и другие) — токены ботов не заданы или заменены тестовыми;
   - почта — отправка выключена;
   - телеметрия и лента объявлений — выключены (по умолчанию так и есть);
   - все агенты на паузе, рутины выключены — прогоны не должны идти от боевых задач;
   - ключи моделей — тестовые или пустые.

**Smoke-проверки.**

1. `verify-health.sh --url <адрес стенда>/api/health --expect-version … --expect-commit …`.
2. Журнал: все миграции применились, повторного применения нет.
3. Список агентов открывается и совпадает с боевым.
4. Открывается задача с длинной историей.
5. Короткий прогон тестовым адаптером (`process` или `http` на заглушку) доходит до
   `succeeded`.
6. Плагины поднимаются (hindsight — обязательно).
7. Выкат с предыдущего digest на новый и откат обратно скриптами из этого каталога проходят на
   стенде.

**Можно выкатывать, когда:**

- все проверки выше прошли;
- CI на коммите выпуска зелёный, образ собран workflow **Myrmidon image**, digest записан
  (`deploy.sh` без этого всё равно не выкатит: проверка образа обязательна);
- на стенде нет новых ошибок в журнале сервера за время проверки;
- откат на стенде прошёл и сервер после него здоров.
