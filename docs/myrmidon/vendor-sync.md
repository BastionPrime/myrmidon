# Еженедельный перенос релиза вендора (R2)

Инструкция для бота на нашей доске. Бот выполняет её раз в неделю по рутине Paperclip. Рутину и
токен заводит сопровождающий.

## Доступы

- Вендор `https://github.com/paperclipai/paperclip.git` читается публично, без токена.
- В `itkadr-git/myrmidon` бот ходит fine-grained токеном, выданным **только на этот
  репозиторий**: содержимое (чтение и запись веток) и pull requests. Токен — секрет доски, в
  промпт и журналы не выводится.
- Бот не пушит в `main`, не создаёт теги в `myrmidon`, ничего не отправляет вендору: ни PR, ни
  issue, ни комментариев.

## Скрипт

`scripts/myrmidon/vendor-sync/vendor-sync.mjs` — Node 24 без зависимостей.

```sh
node scripts/myrmidon/vendor-sync/vendor-sync.mjs            # из корня свежего клона myrmidon, ветка main
node scripts/myrmidon/vendor-sync/vendor-sync.mjs --help     # параметры
```

Что делает:

1. Проверяет, что в рабочем дереве нет незакоммиченных изменений.
2. Забирает стабильные теги вендора (`refs/tags/v*`). Стабильный тег — `vYYYY.MDD.N` без
   суффиксов. Теги `-canary`, `-beta`, `-rc`, `canary/…`, `nightly/…` не рассматриваются.
3. Текущая база — самый свежий стабильный тег, достижимый из `main`. Если нового тега нет,
   печатает `nothing to do` и выходит с кодом 0.
4. Создаёт ветку `sync/<тег>` от `main` и делает `git merge --no-ff <тег>` с сообщением
   `Merge vendor release <тег>`.
5. Пишет отчёт в `.git/sync-report.md` (путь меняется `--report`). Отчёт не коммитится.

Коды выхода:

| Код | Значение |
|---|---|
| 0 | Слияние сделано или нечего делать (смотри первую строку вывода: `merged …` / `nothing to do …`) |
| 2 | Конфликт. Слияние прервано (`merge --abort`), ветка `sync/<тег>` стоит на `main`. В отчёте — файлы с конфликтами и строки DIVERGENCE.md, которые их касаются |
| 1 | Иная ошибка: грязное дерево, ветка `sync/<тег>` уже есть, нет сети. Ничего не сливать, сообщить сопровождающему |

Отчёт содержит:

- диапазон коммитов вендора (`main..<тег>`, без merge-коммитов);
- строки DIVERGENCE.md, у которых, возможно, выполнено условие «Как снимать»: упомянутый в
  строке PR вендора (`#N`) или коммит `vendor:<sha>` вошёл в диапазон;
- новые, изменённые и удалённые workflow в `.github/workflows/`;
- новые миграции БД (`packages/db/src/migrations/*.sql`);
- изменения вендора в файлах, где у нас есть метки `myrmidon(`;
- изменения `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `Dockerfile*`.

Изменения workflow, миграций и файлов зависимостей считаются от предыдущего тега вендора до
нового, то есть это то, что вендор поменял между релизами.

## Порядок работы бота

1. Свежий клон `myrmidon`, ветка `main`. Проверить, нет ли уже открытого PR из
   `sync/<тег>`: если есть, новый не открывать, а дописать в старый комментарий «тег всё ещё
   не влит».
2. Запустить скрипт.
   - Код 0 и `nothing to do` — закончить работу, написать в задаче рутины «нового релиза нет».
   - Код 0 и `merged` — перейти к шагу 4.
   - Код 2 — шаг 3.
   - Код 1 — остановиться, описать ошибку в задаче рутины.
3. **Конфликты.** На ветке `sync/<тег>` повторить слияние:
   `git merge --no-ff -m "Merge vendor release <тег>" <тег>`. Разрешить каждый файл:
   - куски с меткой `myrmidon(<ID>)` сохраняются, смысл вендора тоже сохраняется. Если наш
     кусок больше не ложится, перенести его на новое место с той же меткой;
   - строки DIVERGENCE.md из отчёта подсказывают, что это за правка и каким тестом она
     проверяется;
   - `pnpm-lock.yaml` руками не править: взять версию вендора (`git checkout --theirs
     pnpm-lock.yaml`) и пересобрать `pnpm install`, если наши `package.json` отличаются;
   - если непонятно, как совместить, не угадывать: `git merge --abort`, PR не открывать,
     описать файл и обе стороны в задаче рутины и позвать сопровождающего.
   
   Коммит слияния — обычный `git commit` без правки сообщения.
4. **Проверка.**
   ```sh
   pnpm install --frozen-lockfile
   pnpm -r typecheck
   pnpm test:run
   node --test 'scripts/myrmidon/**/*.test.mjs'
   ```
   Долгие команды — в фоне с выводом в файл.
5. **Push** ветки `sync/<тег>` в `myrmidon` (не `--force`).
6. **PR** из `sync/<тег>` в `main`:
   - заголовок: `R2: sync vendor release <тег>`;
   - описание: содержимое отчёта, затем разделы «Конфликты» (как разрешены, по файлам) и
     «Проверка» (команды и хвосты вывода);
   - если тесты красные — PR открыть, в заголовок добавить `[tests failing]`, в описании
     перечислить упавшие тесты и предположение о причине. **Не чинить** в этом PR наш код
     сверх разрешения конфликтов.
7. Написать в задаче рутины ссылку на PR и краткую выжимку: число коммитов, конфликты, новые
   миграции и workflow.

## Слияние PR переноса

- PR `sync/*` вливается **только merge commit**. Squash и rebase запрещены: они обрывают связь
  с историей вендора, и следующий перенос даст сплошные конфликты.
- PR сливает сопровождающий после проверки. Автослияние ботом — только по отдельному решению
  сопровождающего.
- Красный PR не сливать. Пока он открыт, следующий еженедельный запуск нового PR не создаёт
  (шаг 1).

## Что проверить сопровождающему перед слиянием

- **Workflow.** Новые workflow вендора (раздел отчёта) выключить или удалить, если они нам не
  нужны или требуют секретов вендора. Изменение — отдельным PR после переноса или в этом же PR
  отдельным коммитом.
- **Миграции.** Новые миграции вендора применятся при выкате. Перед выкатом — дамп (R4).
- **Зависимости и Dockerfile.** Проверить лицензии (проверка CI трека 1) и то, что в образ не
  попали медиа-инструменты.
- **Наши метки.** Файлы из раздела «изменения в файлах с нашими метками» — проверить, что
  тест-сторож каждой затронутой строки DIVERGENCE.md зелёный.

## Как снять нашу правку, которую закрыл вендор

После слияния переноса — **отдельный PR** на каждую снимаемую строку реестра:

1. Взять строку из раздела отчёта «Registry rows that may now be removable» и проверить её
   условие «Как снимать» по коду вендора.
2. Удалить куски с меткой `myrmidon(<ID>)`, наши файлы этой функции и то, что сказано в
   «Как снимать» про тест.
3. Строку из DIVERGENCE.md удалить, настройки из SETTINGS.md — тоже, если их больше нет.
4. Для строк `vendor:<sha>` отдельного PR обычно не нужно: при слиянии тега перенесённый
   коммит совпадёт с вендорским. Строку реестра удалить тем же отдельным PR.

## Особенность первой базы

`v2026.916.1` — хотфикс-тег на боковой ветке вендора, его нет в истории `master` вендора. При
слиянии следующего стабильного тега из `master` возможен конфликт на том же исправлении (#13562,
`keep task composer available while pause state loads`). Разрешать **в пользу вендора**
(`git checkout --theirs <файл>`), если в файле нет наших меток. Репетиция 27.09.2026 (слияние
`master` вендора на `be43c23e2`/`74508357f` в наш `main`) прошла без конфликтов.

## Тесты скрипта

`scripts/myrmidon/vendor-sync/*.test.mjs`, встроенный `node:test`, без сети: во временном
каталоге создаются поддельный «вендор» с тегами и наш «форк».

```sh
node --test 'scripts/myrmidon/**/*.test.mjs'
```

Путь-каталог (`node --test scripts/myrmidon/`) в Node 24 не работает: нужен шаблон.
