# ADR-0001: Мост TDLib для TelegramBackend

Дата: 2026-09-20
Статус: принято каркасно (обе ветки описаны), финальный выбор — ОТЛОЖЕН до сборочного образа ADM
Связанные задачи: OPE-2494 Т-2.1 (каркас TdBridge), Т-2.2–Т-2.10
План: docs/plan-v3.md раздел 4.4; раздел 5 Фаза 2

## Контекст

TelegramBackend должен работать поверх официального TDLib. В wellmagram
нет прямого пути к libtdjson в песочнице: сборочного образа ADM (Rust
toolchain + NDK + CMake + JDK 17) ещё нет, живая сборка TDLib и интеграция
`.so` отложены (решение главы домена п.4 + карточка 9a162853 — «Стартовать
Фазу 2 сразу: каркас TdBridge с моками + интерфейсы TDLib-фасада, живую
сборку отложить до образа»). При этом архитектура 4.4 допускает два
эквивалентных по функциональности моста, и план (Т-0.6/E3, отменённые в
v3 в пользу образа) требует живых метрик для выбора — метрики в песочнице
невоспроизводимы.

## Решение

1. **Каркас не зависит от выбора моста.** Вся логика жизни клиента
   (корреляция `@extra`, таймауты, реконнект-политика, порядок апдейтов,
   логирование без содержимого) написана против шва `TdClientLike`
   (lib/core/backends/telegram/td_client_seam.dart). Шов повторяет контракт
   C-интерфейса `td_json_client.h` (td_json_client_create / _send /
   _receive / _execute / _destroy; сигнатуры сверены с официальной
   документацией TDLib, core.telegram.org/tdlib/docs/td__json__client_8h).
2. **Финальный выбор варианта отложен до образа ADM.** Решающие метрики —
   живые: время холодного старта клиента, задержка апдейта, стабильность
   под нагрузкой (исходная методика Т-0.6: один экран «список чатов TG,
   200 чатов», обе реализации). В образе обе ветки подключаются как
   реализация одного и того же шва; выбор не меняет ни TdBridge, ни
   TelegramBackend.

### Вариант (i) — Dart FFI (tdlib_ex или handy_tdlib)

- Библиотека: `libtdjson.so` грузится через `dart:ffi`, приём апдейтов в
  выделенном isolate, JSON→объекты вне UI-изолята.
- Плюсы: меньше слоёв, нет Kotlin-прослойки, апдейты уже в Dart-мире,
  ежедневная синхронизация схемы TL у tdlib_ex.
- Минусы: зависимость от стороннего Dart-пакета; `td_json_client_receive`
  обязан вызываться не из двух потоков одновременно — изолят получает
  исключительную ответственность за receive-цикл; FFI-строки через
  `td_json_client_receive` возвращаются с владением у C-стороны (буфер
  живёт до следующего receive/execute — копия строки обязана быть сделана
  немедленно).
- Риски: зрелость Dart-биндингов (риск №7 реестра 8) — митигируется
  вариантом (ii) как резервом.

### Вариант (ii) — Flutter-плагин на Kotlin JNI

- Библиотека: официальные Java/JNI-биндинги `org.drinkless.tdlib.Client`
  из example/android TDLib; MethodChannel для запросов, EventChannel для
  апдейтов.
- Плюсы: официальные биндинги, TDLib-модель владения потоками решена на
  стороне Kotlin, нет зависимости от сторонних Dart-пакетов.
- Минусы: больше кода (плагин-прослойка), сериализация через EventChannel
  (платформенный канал), второй FFI-слой JNI.

### Почему выбор отложен

Метрики решающие — живые (холодный старт, задержка, стабильность), а живой
TDLib в песочнице недоступен. Оба варианта реализуют один и тот же шов
`TdClientLike`, поэтому откладывание выбора не блокирует каркас и
TelegramBackend, и не создаёт переделок: смена моста = замена адаптера
шва, TdBridge остаётся как есть.

## Последствия

- Каркас Т-2.1 готов к обоим вариантам; ADR переоткрывается в образе ADM
  по живым метрикам (reopen-условие: сборка libtdjson/libtdjni в образе +
  прогон методики Т-0.6).
- Ссылка на решение фиксируется в каждой сдаче Фазы 2 как «выбор моста
  отложен до образа (ADR-0001)».
- Производственный адаптер шва (Dart FFI или Kotlin-плагин) — отдельная
  задача образа; в песочнице все тесты идут на `MockTdClient`.

## Ограничения

- Целевая схема моков/швов Фазы 2: официальный `td/generate/scheme/td_api.tl`
  ветки master TDLib (мастер-схема), проверено по машинной сверке имён полей
  (см. docs/experiments/2026-09-20-t2-fix-schema-check.md). Отступления от
  мастер-схемы — только задокументированные легаси-пути:
  `authorizationStateWaitEncryptionKey`/`setDatabaseEncryptionKey`
  (сознательно поддержан для старых TDLib) и `user.username` в скрипте мока
  (в master уже `usernames`); `updateChatAction` без `topic_id` — минимальный
  профиль для typing-события.
- Сигнатуры `td_json_client.h` сверены по официальной документации TDLib;
  поле `database_encryption_key` в json-запросе setTdlibParameters
  передаётся как массив байт (bytes). Точное поведение биндингов
  (типизация bytes в tdlib_ex vs handy_tdlib) проверяется в образе.
- Вариант (ii) предполагает сборку libtdjni.so тем же CI-контуром
  (build-tdlib.yml из плана) — сборка артефактов в образе ADM.
